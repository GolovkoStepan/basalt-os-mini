# AGENTS.md

Репозиторий `basalt-os-mini` — терминальная ОС на **ESP32-S3**, которую мы
пишем сами (без Arduino и без FreeRTOS). Плата проекта — **LilyGO
T-Display-S3**. На PlatformIO.

**Язык:** идентификаторы в коде — английские; комментарии, README, документы и
сообщения коммитов — русские. Комментарии объясняют **почему**, а не «что».

Родственные репозитории лежат рядом, но не внутри:

| Репозиторий | Что |
|---|---|
| `esp32-lab` | правила по железу, платы без проекта, `pulsar`, скрипты `tools/` |
| `basalt-os` | ОС для Tab5, форк этого проекта в точке MVP — **на паузе** |
| `capsh` | будущий проект для Cardputer: прошивка с периферией, без своего ядра |
| `basalt-os-mini` | **этот** |

`docs/board.md` — **единственный** документ основной платы. Копий в других
репозиториях нет: измеренные данные разъезжаются, и потом не понять, какая
версия настоящая.

Документ Cardputer переехал в проект `capsh` (`capsh/docs/board.md`) — там
теперь его единственная копия. В этом репозитории его нет.

## 2. Документация по плате

- **Перед работой с платой прочитать `docs/board.md`.** Там измеренные данные,
  которые иначе придётся выяснять заново: `POWER_ON` для панели, режим PSRAM,
  частота пиксельклока, ограничения памяти.
- **Новое знание о железе — сразу в `docs/board.md`**, а не только в README или
  в переписку. Драйвер подобрался, частота не держится, пин занят — туда.
- **Проектная логика в документ платы не пишется.** Только железо: пины,
  частоты, регистры, грабли, замеры.
- Предположения помечаются словом «предположительно». Всё остальное —
  проверено на железе, в идеале с указанием, чем измерено.

## 3. Окружение

| Компонент | Версия / путь |
|---|---|
| PlatformIO Core | 6.2.0, `/opt/homebrew/bin/pio` |
| Python для PIO | Homebrew `python@3.15` (отдельно от asdf) |
| espressif32 | **8.0.0** → Arduino core 3.3.12 / IDF 6.1.0, xtensa GCC 15.2, libc — **picolibc** |
| esptool | `~/.platformio/packages/tool-esptool/esptool` |
| Редактор | Zed + **esp-clangd 21.1.3** (`~/.local/opt/esp-clangd/bin/clangd`) |
| ОС | macOS, arm64 |

Платформа фиксируется как `platform = espressif32@8.0.0`. Обновлять без причины
не нужно: версия проверена на живых платах, а смена тянет за собой новый
тулчейн и правку include-путей в `.clangd`.

### Python 3.15 и чистая установка PlatformIO

**Не чистить `~/.platformio` на этой машине, пока PIO работает на Python
3.15.** Проверено 21.10.2026 сборкой в пустом `PLATFORMIO_CORE_DIR`: установка
пакета `framework-espidf` создаёт питоновское окружение IDF и падает на сборке
`pydantic-core` из исходников:

```
error: the configured Python interpreter version (3.15) is newer than PyO3's
       maximum supported version (3.14)
ERROR: Failed building wheel for pydantic-core
ModuleNotFoundError: No module named 'idf_component_manager'
```

Причина не в проекте. `requirements.core.txt` из IDF тянет `pydantic 2.12.5`,
а тот требует ровно `pydantic-core==2.41.5`; для неё готовые колёса есть под
3.12 и 3.14, а под 3.15 нет — pip лезет собирать из исходников, и Rust-обвязка
PyO3 3.15 ещё не знает.

| Что | Готовые колёса `pydantic-core 2.41.5` |
|---|---|
| cp312, macOS arm64 и Linux | есть |
| cp314, macOS arm64 | есть |
| cp315 | **нет** |

Отсюда два следствия:

- **CI собирается** на `ubuntu-24.04` с `python-version: 3.12` — это и есть
  причина, по которой версия в workflow зафиксирована числом, а не «последняя».
- **На этой машине** PlatformIO стоит на Python 3.15 (`/opt/homebrew/bin/pio`),
  и это **уже сломалось** 05.11.2026: PlatformIO пересоздал окружение IDF
  (`.espidf-6.1.0`), а установка `idf_component_manager` в него не прошла.
  Симптом ровно тот, что в таблице грабель: CMake падает на `project()` с
  `ModuleNotFoundError`, и **сборка любого env на espidf не идёт**.

  Рабочий обход — второй PlatformIO на Python 3.14, отдельным venv:

  ```bash
  ~/.asdf/installs/python/3.14.2/bin/python3.14 -m venv ~/.venvs/pio314
  ~/.venvs/pio314/bin/pip install "platformio==6.2.0"
  ~/.venvs/pio314/bin/pio run -e tdisplay
  # или: make build PIO=~/.venvs/pio314/bin/pio
  ```

  Первый такой запуск пересоздаёт `.espidf-6.1.0` на 3.14 (сломанное
  окружение можно переименовать в `.espidf-6.1.0.broken-py315`, места оно
  почти не занимает). После этого сборка идёт, а `~/.platformio/packages`
  переустанавливать не нужно.

**Плата T-Display-S3 — с PSRAM.** 8 МБ OPI, то есть ограничение «512 КБ и ни
байтом больше» снято: кадровый буфер 108 КБ, файлы, mruby — всё это теперь
возможно. Но дисциплина остаётся, см. раздел 8.

## 4. Основные команды

Две формы записи, обе правильные: `make` короче и не требует помнить env,
`pio` — прямая и видна в логах. Логики в `Makefile` нет, он только называет
команды, поэтому `pio` остаётся полноценным способом работы.

```bash
make help                        # список целей
make                             # собрать env:tdisplay
make verify                      # то же, что CI: тесты, все env, образы
make flash ENV=bare              # собрать и залить Cardputer
make probe                       # щуп: чип, flash, PSRAM, кадровый буфер в PSRAM
make flash ENV=flash             # щуп flash: ID чипа, таблица разделов, чтение, стирание, запись
make fs                          # щуп ФС: разметка, запись, чтение, перемонтирование
make log SECONDS=30              # читать лог 30 секунд
```

```bash
pio device list                  # список портов
pio run                          # собрать default_envs (сейчас tdisplay)
pio run -e tdisplay              # основная плата: своя ОС
pio run -e bare                  # Cardputer: console, hello, bringup, bare, bare-panic
pio run -t upload                # собрать и залить
pio run -t compiledb             # пересобрать базу для clangd
pio run -t erase                 # стереть flash
pio test -e native               # тесты на маке, плата не нужна
./tools/check-image.sh           # проверить собранный env:bare по символам, без платы
./tools/smoke.sh                 # залить и сверить лог с платы (bare)
./tools/smoke.sh bare-panic      # то же для паники
./tools/reset.sh                 # вывести плату из загрузчика (USB-JTAG)
./tools/serial-read.sh 15        # прочитать лог 15 секунд
./tools/flash-backup.sh flash-id # чип, размер flash, MAC
```

`ENV` в `Makefile` и `default_envs` в `platformio.ini` совпадают: `tdisplay`.
Раньше они расходились намеренно (`bare` против `console`), но с переездом
основная плата одна, и второй ответ на вопрос «что собирать по умолчанию»
только путал бы.

`pio device monitor` работает **только в интерактивном терминале**. В скриптах,
задачах Zed и любых pipe использовать `tools/serial-read.sh` (обёртка над
pyserial из PlatformIO). Иначе порт просто не откроется.

### Тесты

Три уровня, у каждого своя цена и своё место:

| Уровень | Чем | Что проверяет | Где запускается |
|---|---|---|---|
| логика на маке | `pio test -e native` (Unity) | переносимый код: форматирование, текст, tty, парсер шелла, таблица разделов, ФС BFS, VFS | `test/`, CI |
| собранный образ | `./tools/check-image.sh` | то, чего не видит компилятор: карта памяти своя, таблица векторов выровнена на 1 КБ, куча внутри DRAM | CI |
| живая плата | `./tools/smoke.sh <env>` | лог: `ready`, тики до `tick 20`, отчёт паники, причина сброса | вручную, плата в порту |

- **На маке проверяется только переносимое.** Всё, что трогает регистры,
  проверяется на плате: `env:tdisplay` для обычной работы,
  `env:tdisplay-panic` для паники.
- **`pio test -e native` собирает не весь проект, а список файлов** из
  `build_src_filter` в `[env:native]`. Если тестируемый файл тянет `soc/...`,
  он не соберётся. Правильный ход — вынести чистую логику в отдельный файл,
  а не заводить `#ifdef` под тесты.
- **Железо подменяется заглушкой в каталоге теста.** Пример:
  `test/test_format/console_stub.c` реализует `basalt_console_write` в буфер,
  поэтому тест видит ровно тот текст, который ушёл бы в терминал.
- **Новая переносимая логика — с тестом.** Не «так принято», а потому что
  ошибка в парсере на плате стоит вечера, а на маке — секунды.
- **`tools/smoke.sh` в CI не входит:** платы на раннере нет. Это ручной прогон,
  который не даёт забыть строку из «признака успеха».
- **Смоук читает лог долго намеренно.** `tdisplay` и `bare` — 26 секунд и
  требуют `tick 20`.
  Проверка на 12 секундах проходила на прошивке, которая перезагружалась каждые
  9 секунд: сброс попадал в окно, но `tick 1` уже был напечатан. Если проверка
  смотрит только начало лога, она не отличает «работает» от «падает и
  перезапускается».

### Прошивка T-Display-S3 (основная плата)

- **Порт:** нативный USB-C, `usbmodem`. Моста UART нет.
- **Режим загрузки:** зажать **G0**, подать питание или нажать RST, отпустить.
  Обычно не нужно: `esptool` сбрасывает плату сам.
- **Перед первой своей прошивкой** снять дамп 16 МБ — `docs/board.md` §9.
- **Экран не загорится**, если не поднят `POWER_ON` (G15): прошивка при этом
  полностью рабочая, и в логе всё в порядке.

### Прошивка Cardputer (проект capsh)

- **Режим загрузки:** переключатель питания в **OFF**, зажать **G0**, подать
  питание, отпустить G0.
- **Зарядка идёт только при переключателе в ON.**
- На оригинале K132 клавиатура — матрица 8×7 через 74HC138, не TCA8418.

## 5. Правила кода

- **Пины и константы платы** — в `boards/<плата>/board_pins.h`, путь
  подставляется сборкой (`-Iboards/…` и `INCLUDE_DIRS` в `src/CMakeLists.txt`).
  Магических чисел GPIO в логике быть не должно.
- **Различие между платами решается сборкой, а не `#ifdef`.** Один пример:
  индикатор жизни — `indicator.h` с двумя реализациями
  (`indicator_ws2812.c`, `indicator_backlight.c`), выбор в `src/CMakeLists.txt`.
  Код ядра не должен знать, на какой плате он запущен.
- **Периферия — за своим интерфейсом в `drivers/`.** `drivers/lcd.h`
  (`lcd_init`, `lcd_flush`, `lcd_backlight`) не знает ни одного регистра;
  под ним `drivers/lcd_i80.c` для этой платы. Когда появится слой прерываний,
  реализация заменится на `esp_lcd` без правок в вызывающем коде. Причина, по
  которой своя реализация появилась раньше чужой, — `docs/board.md` §4.
- **`arch/` с первого дня.** Переключение контекста, trap, старт — за
  интерфейсом, без `#ifdef` по всему ядру. От этого зависит цена форка в
  `basalt-os`.
- **Текст не знает про экран.** `text/matrix.c` рисует полосу в буфер, который
  ему дали, и помечает строки изменёнными; драйвер зовёт вызывающий. Поэтому
  логика текста проверяется на маке по пикселям, а не «драйвер вызвали
  столько раз». Тот же приём понадобится для `fb`-устройства в A12.
- **Граница syscall — даже когда железо её не проверяет.** На S3 нет user mode,
  но интерфейс оформляется таблицей вызовов: на P4 изоляция включится без
  переписывания логики.
- **Сгенерированные файлы не править руками.** `text/font_5x7.h` и
  `text/font_5x7.c` перезаписываются генератором `tools/make_font.py` (данные
  в .c, объявление в .h). Менять нужно генератор, а проверить результат —
  `python3 tools/make_font.py --preview` (печатает оба алфавита ASCII-артом в
  терминал). Шрифт пиксельный, 161 глиф (ASCII + кириллица), нарисован прямо
  в скрипте: на 7 px рендер TrueType даёт кашу, а так у генератора нет
  зависимостей, кроме python3.
- **Текст принимает UTF-8.** Кириллица — два байта на символ, поэтому
  состояние разбора (`text/utf8.c`) живёт между вызовами `text_putc`. Клетка
  матрицы — `uint16_t` с code point, не байт: иначе «Ж» пришлось бы хранить
  двумя клетками. Новый поток символов — свой декодер, а не общий.
- **Line discipline не знает про экран и USB.** `tty/tty.c` принимает байты и
  отдаёт события (`CHAR`, `ERASE`, `LINE`, `INTR`, `EOF`, `BELL`), а рисует и
  передаёт программе вызывающий. Поэтому набор текста проверяется на маке
  (`test/test_tty`), а `src/tty/main.c` остаётся тонкой связкой. `Backspace`
  откатывает **целый UTF-8-символ**, а не байт: иначе от «Ж» осталась бы
  половина последовательности, и следующая буква склеилась бы с ней.
- **Шелл собирается из четырёх переносимых модулей.** `shell/lineedit.c`
  владеет строкой и курсором, `shell/history.c` — кольцом команд,
  `shell/parse.c` — разбором на слова и служебные токены, `shell/redirect.c` —
  планом выполнения (ступени конвейера, куда вывод, откуда ввод). Ни один не
  тянет `soc/...` и не знает про экран, поэтому все четыре проверяются на маке
  (`test_lineedit`, `test_history`, `test_parse`, `test_redirect`), а
  `src/shell/main.c` остаётся связкой с экраном и USB. **Редактор работает в
  raw-режиме tty**, как в настоящих терминалах: канон умеет только «дописать в
  конец», а стрелки и `Ctrl-A/E/K/U/W` требуют курсора внутри строки. Поэтому
  `tty/tty.c` не пришлось усложнять — он по-прежнему про байты.
  Курсор редактора считается **в байтах**, наружу отдаётся **в клетках**
  (`le_cursor_col`, `le_cell_cp`): «Ж» — два байта и одна клетка.
- **Служебные символы распознаёт парсер, а не шелл.** `>`, `>>`, `<`, `|` —
  такие же токены, как слова (`parse_token_kind`), потому что только во время
  разбора видно, были ли они в кавычках: `echo "a > b"` обязан остаться
  текстом. Текст служебного токена лежит в статике `parse.c`, а не в буфере
  строки, иначе ноль на месте `>` съел бы следующий символ в `a>f`; поэтому
  `argv` служебных токенов нельзя менять. Решение «куда идёт вывод» принимает
  `shell/redirect.c`, а не команда.
- **Команда не знает, куда пишет.** Вывод идёт через приёмник в
  `src/shell/main.c`: экран, файл или буфер конвейера. Команды зовут
  `out_puts`/`out_cp`, а сообщения самой оболочки и ошибки — `out_diag`: они
  идут на экран **всегда**, иначе `cat /nope > f` записал бы «не найдено» в
  файл. В файл и конвейер данные идут байтами: разбор UTF-8 нужен только
  экранной матрице (иначе `cat /big > /copy` терял половину файла).
- **Запись в файл копится в буфере.** BFS переписывает блок целиком, поэтому
  каждый мелкий `vfs_write` — отдельная запись во flash; без буфера 4 КБ
  `help > файл` пишет сотню раз и выглядит как зависание. И `> f` **не**
  усекает файл при открытии: усечение отложено до первой записи, чтобы
  `cat /a > /a` не обнулил источник (в VFS для этого есть `vfs_truncate`).
- **Файлы — только через VFS.** Команды шелла зовут `storage/vfs.h`
  (`vfs_open`, `vfs_stat`, `vfs_readdir`, …), а не `bfs_*` напрямую: путь с
  `..` разбирает VFS, иначе `cat a/../b` и `ls a/../b` однажды разойдутся.
  Новая ФС — это новый адаптер по образцу `storage/vfs_bfs.c`, а не правки в
  оболочке. Привязка ФС к разделу flash одна на всех — `storage/bfs_flash.c`;
  свою копию адаптера блочного устройства в щупе заводить не нужно.
- **Кнопка — событие, а не пин.** `drivers/button.h` (`button_down(BUTTON_…)`)
  прячет полярность и подтяжку; приложение не должно знать, что G0 замыкается
  на землю. Антидребезг живёт у вызывающего: он зависит от частоты опроса.
- Отступ — 4 пробела в C/C++, 2 в YAML/JSON/Markdown-таблицах.
- В git **не попадают**: `.pio/`, `compile_commands.json` (абсолютные пути),
  `.cache/`, `logs/`, `backup/*.bin`, `__pycache__/`, `.DS_Store`.

### Коммиты делает только автор

**Агент не делает коммитов и не пушит.** `git add`, `git commit`, `git push`,
`git reset`, `git checkout`, `git stash` — только вручную пользователем.

Разрешено: читать состояние репозитория (`git status`, `git diff`, `git log`,
`git show`) и **предлагать** текст сообщения коммита. Запрещено: создавать,
изменять и отменять коммиты, менять ветки, отправлять в удалённый репозиторий.

Сообщение коммита — по-русски, в императиве, одна законченная мысль:
«добавить драйвер ST7789», а не «added».

## 6. Редактор: clangd

Штатный clangd из Zed собран без поддержки Xtensa: падает на `-mlongcalls`,
на GCC-флагах и на `invalid constraint 'a' in asm` в заголовках IDF. Поэтому
используется сборка от Espressif.

| Что | Где |
|---|---|
| Бинарь + `--query-driver` | `~/.config/zed/settings.json` → `lsp.clangd.binary` |
| Правки флагов и include-путей | `.clangd` в корне этого репозитория |
| База компиляции | `compile_commands.json` в корне (генерируется) |

`compile_commands.json` отвечает за переход к определению в IDF, Arduino core
и библиотеках. `.clangd` чинит то, что в базе есть, но clang не понимает:
убирает флаги GCC, которых clang не знает, и добавляет `-isystem` на libc и
libstdc++ тулчейна.
Без `.clangd` clangd не «просто не помогает» — он выдаёт больше ошибок, чем
вообще без настройки.

**После правки `platformio.ini`** обязательно:

```bash
pio run -t compiledb          # база для default_envs (tdisplay)
pio run -e tdisplay -t compiledb  # база для основной платы
```

**`compiledb` собирает базу только для одного env** — того, что указан в
команде (или `default_envs`). Файл один, поэтому базы разных env'ов
перезаписывают друг друга. Правило простое: база делается под тот env, код
которого сейчас правится. Признак, что база не та: clangd не находит
`tick.h`, `format.h` или `board_pins.h` — значит, в базе нет
`-Iarch/xtensa/include` или `-Iboards/<плата>`, то есть она от Arduino-сборки.

Характерный случай: база от `tdisplay`, а открыт файл Cardputer
(`indicator_ws2812.c`). Своего входа в базе у него нет, clangd подставляет
догадку и не видит `boards/cardputer`, поэтому ругается
`use of undeclared identifier 'PIN_RGB_LED_G21'` (и на любой другой `PIN_*`).
Это не ошибка кода: пересоберите базу под тот env, файл которого правите.

**Диагностика `clangd --check` бывает двух сортов.** Строки вида
`tweak: SwapBinaryOperands ==> FAIL: The new replacement overlaps…` идут от
встроенного clang-tidy, который `--check` прогоняет на каждом токене; к сборке
они отношения не имеют и видны на файлах, которые собираются без единого
предупреждения. Настоящая ошибка выглядит иначе — `[undeclared_var_use] Line
N: …`.

Проверить, что конфиг живой, можно без редактора:

```bash
~/.local/opt/esp-clangd/bin/clangd --check=src/bare/main.c
```

Ожидаемый результат — `All checks completed, 0 errors`.

### Хрупкое место: версия в путях и picolibc

Два независимых способа сломать clangd обновлением тулчейна.

**1. Версия GCC в путях.** В `.clangd` она указана явно (`.../15.2.0/...`).
После обновления espressif32 или тулчейна её нужно поправить:

```bash
ls ~/.platformio/packages/toolchain-xtensa-esp-elf/lib/gcc/xtensa-esp-elf/
```

**2. libc — это picolibc, а не newlib.** С GCC 15 прошивка собирается с
`-specs=picolibc.specs`, и заголовки libc приходят из
`toolchain-xtensa-esp-elf/picolibc/include`. Рядом, в
`toolchain-xtensa-esp-elf/xtensa-esp-elf/include`, остаётся лежать **старый
newlib** — clangd находит его по старой привычке и разбирает не тот набор
заголовков. Диагностика характерная: `_mbstate_t unknown`, `__FILE unknown`,
`stdbool.h file not found`. Лечится сменой пути на `picolibc/include`, а не
версией GCC.

**3. `-isystem` и путь — два элемента списка.** Одной строкой
`- "-isystem /путь"` clangd 21 передаёт их одним аргументом, драйвер видит
значение с ведущим пробелом и каталога не находит. В YAML это две строки.

Если clangd перестал видеть стандартные заголовки (`<string>`, `<cstdint>`) —
почти всегда причина в одном из этих трёх мест.

## 8. Память: два вида, две дисциплины

**SRAM 512 КБ** (в проекте занято ~32.7 КБ, с текстовой матрицей и шрифтом —
43 КБ) и **PSRAM 8 МБ** — это не «много
памяти», а две разные памяти с разной ценой доступа.

| Где | Что там живёт | Почему |
|---|---|---|
| SRAM | ядро, драйверы, стеки, таблица векторов, горячие пути | без кэша, задержка предсказуемая |
| PSRAM | кадровый буфер, файловые кэши, куча приложений, mruby | идёт через кэш: дороже по латентности, дешевле по объёму |

Правила:

- **PSRAM — не оправдание для расточительства.** Это та же дисциплина, что
  понадобится на P4 с его 32 МБ: соблазн «всё в PSRAM» так же вреден, как её
  отсутствие.
- **Перед DMA из PSRAM** — `esp_cache_msync` и выравнивание адреса и длины на
  64 байта. Без этого картинка рвётся полосами, и искать причину в контроллере
  экрана бесполезно.
- **Кадровый буфер 320×170×2 = 108.8 КБ** — в PSRAM целиком, как один блок.
  В SRAM его не закладывать. Но и в PSRAM он нужен не всегда: текстовому
  режиму хватает сетки символов (901 Б) и полосы одной строки (6.4 КБ) в SRAM,
  а полный буфер — это 900 глифов поштучно в память через кэш. Правило простое:
  буфер в PSRAM заводится под то, что рисуется областями (графика, A12), а не
  под то, что можно нарисовать построчно.
- **Таблица разделов своя** (`partitions.csv`, с 06.11.2026): приложение 2 МБ,
  раздел данных `storage` 14 272 КБ, служебные разделы IDF 28 КБ. Flash
  поделён весь, свободного места вне разделов нет. Размер flash в заголовке
  образа задаётся не в `platformio.ini`, а в `sdkconfig.defaults.<плата>`.
- Бюджет памяти — в `docs/FUNCTIONALITY.md`, раздел 13.

Перед тем как закладывать крупный буфер, замерить фактический свободный блок:
`make probe` (`env:probe` в этом репозитории: чип, flash, PSRAM, крупнейший
блок, выделение кадрового буфера и сверка записи). Отдельно проверить, что
PSRAM действительно есть — у части партий T-Display-S3 её нет.

Замерено 06.11.2026: свободно 355 КБ SRAM (крупнейший блок 312 КБ) и 8189 КБ
PSRAM (крупнейший блок 8064 КБ), кадровый буфер 108 800 Б выделяется одним
блоком. Кучу заводит сама ОС — `basalt_heap_init()` в `arch/xtensa/`, вызов из
`basalt_start_c()` уже на своём стеке (порядок важен, см. грабли выше); щуп
только проверяет, что она есть. Без этой проверки цифры были бы утверждением
про щуп, а не про систему.

**Стек меряется закраской, а не на глаз.** Свой стек — 8 КБ (`start.S`), и
переполнение на xtensa не даёт внятной ошибки: оно молча затирает соседние
данные. Поэтому `basalt_stack_paint()` (первая строка `basalt_start_c`)
закрашивает свободную часть меткой, а `basalt_stack_used()` ищет первый
незакрашенный байт снизу — это максимум за всё время работы, то есть самый
глубокий вызов, а не текущая глубина в цикле событий. Число показывает
`free` и `top`. Если закраску не проводили, `basalt_stack_used()` вернёт 0 —
единственный способ отличить «не мерили» от «ничего не занято».
