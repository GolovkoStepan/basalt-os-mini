# LilyGO T-Display-S3

Макетная плата на **ESP32-S3R8** с цветным экраном 1.9″ (320×170), двумя
кнопками, аккумуляторным разъёмом и нативным USB-C. Форм-фактор — плата
размером с кредитку с «ушами» под кнопки.

| | |
|---|---|
| **Модель** | LilyGO **T-Display-S3** (не Touch, не MIDI) |
| **SoC** | ESP32-S3R8 — 2× Xtensa LX7 до 240 МГц, **8 МБ PSRAM в корпусе (OPI)** |
| **Статус** | **на своём железе ещё не проверена.** Сборка `env:tdisplay` проходит, проверка образа по символам — тоже; экран, кнопки и PSRAM ждут первого включения |
| **Документ создан** | 05.11.2026 |

> **Степень доверия.** «репозиторий LilyGO» — `pin_config.h` из официального
> `Xinyuan-LilyGO/T-Display-S3` (`examples/factory`), это то, что исполняется на
> заводской прошивке. «board-файл» — `lilygo-t-display-s3.json` из
> `espressif32@8.0.0`. «сборка» — измерено нашей сборкой. «предположительно» —
> требует проверки на плате.

---

## 1. Как опознать

Отличия от похожих плат того же семейства:

| | T-Display-S3 | T-Display-S3-**Touch** | T-Display-S3-**MIDI** |
|---|---|---|---|
| Экран | 320×170 ST7789 | 320×170 ST7789 | нет |
| Тач | нет | **CST816** (I2C) | нет |
| Кнопки | 2 (G0, G14) | 2 | MIDI-разъёмы |

Тач на обычной плате **не распаян**: пины G16/G21 в `pin_config.h` есть, но
чипа на шине нет. Если I2C-скан показывает `0x15` — это Touch-ревизия.

## 2. Характеристики

| Параметр | Значение | Источник |
|---|---|---|
| SoC | ESP32-S3R8, Xtensa LX7, 2 ядра, 240 МГц | документация |
| Архитектура | **xtensa** — та же платформа `espressif32@8.0.0`, что и у Cardputer | board-файл |
| Flash | **16 МБ**, QIO, 80 МГц | board-файл |
| PSRAM | **8 МБ OPI** (`memory_type: qio_opi`) | board-файл |
| SRAM | 512 КБ | документация |
| Экран | **ST7789**, 1.9″, **320×170**, **8-битная параллельная шина (i80/LCD_CAM)** | репозиторий LilyGO |
| Пиксельклок | 16 МГц (ниже — мерцание, выше — «мозаика» на части панелей) | заводской пример |
| Кнопки | **G0** (BOOT), **G14** | репозиторий LilyGO |
| USB | **нативный USB-C** (USB Serial/JTAG), без моста UART | `hwids 0x303A:0x1001` |
| Батарея | разъём MX1.25, зарядка на плате | документация |
| АЦП батареи | G4, делитель 2:1 | репозиторий LilyGO |
| microSD | **слота нет.** CMD/CLK/D0 = G13/G11/G12 выведены на разъём расширения — только под внешний модуль или SD Shield | репозиторий LilyGO |
| I2C | G17 (SCL) / G18 (SDA) на разъём | репозиторий LilyGO |

**Чего нет:** светодиода (ни WS2812, ни обычного), динамика, микрофона,
клавиатуры, **слота microSD** (см. ниже). Роль индикатора жизни играет подсветка
экрана.

> **Про microSD — исправлено 06.11.2026.** Раньше здесь было написано «распаян
> слот», и это неверно: строка приехала при переезде с Cardputer, у которого
> слот есть. Официальный репозиторий LilyGO говорит прямо: «SD card pins
> (SD CMD/CLK/D0) are only available on boards with the SD Shield add-on. The
> standard T-Display-S3 board does not have an onboard SD card slot», а в
> заводском `pin_config.h` эти три пина стоят под комментарием
> `/* External expansion */`. То есть на обычной T-Display-S3 карту можно
> подключить только внешним модулем на гребёнку или докупив SD Shield.

## 3. Распиновка

### Экран ST7789 — 8-битная параллельная шина

| Сигнал | Пин | Что делает |
|---|---|---|
| D0…D7 | 39, 40, 41, 42, 45, 46, 47, 48 | восемь линий данных |
| WR | 8 | такт: по фронту панель забирает байт |
| RD | 9 | чтение (не используем, но пин занят панелью) |
| DC | 7 | 0 = команда, 1 = данные |
| CS | 6 | выбор панели |
| RST | 5 | сброс |
| BL | 38 | подсветка, только вкл/выкл |
| **POWER_ON** | **15** | **питание панели и подсветки** |

> **POWER_ON — самый частый способ получить чёрный экран.** На этой плате
> панель питается отдельной линией G15, которую надо поднять **до** включения
> подсветки. Прошивка при этом полностью рабочая, в логе всё хорошо, экран
> тёмный.

Почему i80, а не SPI: у ESP32-S3 параллельный интерфейс ограничен восемью
линиями, шестнадцать на плату не разведены. Взамен — заливка вчетверо быстрее,
чем по SPI на 40 МГц, и никакой возни с `TFT_eSPI`-конфигом.

### Кнопки, батарея, разъёмы

| Что | Пин | Примечание |
|---|---|---|
| Кнопка 1 | **G0** | одновременно BOOT: зажать при подаче питания = режим загрузки |
| Кнопка 2 | G14 | — |
| АЦП батареи | G4 | делитель 2:1, то есть на входе половина напряжения |
| I2C SCL / SDA | G17 / G18 | внешние модули |
| microSD CMD / CLK / D0 | G13 / G11 / G12 | **не слот, а разъём расширения**: только под внешний модуль или SD Shield; G13 = CS в SPI-режиме |

### Пины, которых лучше не трогать

| Пины | Почему |
|---|---|
| 39–42, 45–48 | линии данных экрана |
| 5, 6, 7, 8, 9 | управление экраном (RST, CS, DC, WR, RD) |
| 15 | питание панели |
| 38 | подсветка |
| 19, 20 | USB D−/D+ (нативный), заняты портом |
| 0 | BOOT |

Свободных пинов остаётся мало: этим плата похожа на Cardputer, но по другой
причине — не клавиатура, а шина экрана.

## 4. Экран: что важно знать до написания драйвера

- **Драйвер экрана — свой, через GPIO, под чужим интерфейсом.** План от
  05.11.2026 был «взять i80 из `esp_lcd`», но 06.11.2026 выяснилось, что
  готовый драйвер i80 работает на прерываниях (`esp_intr_alloc_intrstatus` +
  `esp_intr_enable` в `esp_lcd_panel_io_i80.c`), а своя таблица векторов пока
  все прерывания уровня 1–5 ведёт в панику. Плюс `esp_lcd_new_panel_st7789()`
  в init/reset зовёт `vTaskDelay()`, а планировщика FreeRTOS в системе нет.
  Поэтому первая реализация — `drivers/lcd_i80.c`: восемь линий данных и такт
  WR через `GPIO_OUT1_*`, синхронно, без DMA и прерываний. Интерфейс
  `drivers/lcd.h` (`lcd_init`, `lcd_flush`, `lcd_backlight`) при этом не
  изменится, когда появится слой прерываний и под него положат `esp_lcd`.
- **Интерфейс свой, реализация заменяема.** В ОС живёт `drivers/lcd.h`
  (`lcd_init`, `lcd_flush`, `lcd_backlight`), под ним — `drivers/lcd_i80.c`.
  Замена реализации на `esp_lcd` не потребует правок ни в одном вызывающем
  файле.
- **Кадровый буфер 320×170×2 = 108.8 КБ** в SRAM не влезает рядом с ядром,
  зато целиком помещается в PSRAM. Сейчас заливка синхронная (процессор сам
  читает буфер), поэтому `esp_cache_msync` не нужен. Он станет обязательным,
  когда передача переедет на DMA: адрес и длина должны быть выровнены на
  строку кэша (64 Б), иначе картинка «рвётся» полосами.
- **Панель родная портретная (170×320), а видим мы альбомные 320×170.**
  Поэтому `MADCTL` обязан менять оси местами (`0x60` = MV|MX), а окно — иметь
  смещение 35 по Y: стекло уже памяти контроллера (170 из 240 столбцов).
  Замерено 06.11.2026; без MV картинка заворачивается через 240 столбцов, без
  смещения внизу остаётся полоса старого содержимого.
- **Инверсия цветов обязательна.** Стекло этой панели IPS, и без `INVON`
  (команда `0x21`) вся картинка выходит дополнением до белого: синяя рамка
  показывается жёлтой, белое — чёрным. Замерено 06.11.2026: с `INVON` порядок
  полос совпал с задуманным, BGR-бит в `MADCTL` не понадобился. Это свойство
  стекла, а не контроллера: у другой партии поведение может отличаться, поэтому
  переключатель — `DISP_INVERT_COLORS` в `board_pins.h`, а не константа в коде
  драйвера.

## 5. Питание и USB

- **USB-C нативный** (USB Serial/JTAG), моста UART нет. Консоль — тот же
  канал, что и у Cardputer. `esptool` перезагружает плату сам, но только пока
  она исполняет прошивку: сброс **из** загрузчика по RTS оставляет USB-JTAG
  мёртвым (см. ниже), поэтому своим скриптам, которые читают flash, нужен
  выход через `--before usb-reset` — как в `tools/reset.sh`.
- **USB-JTAG может «зависнуть» на стороне хоста**: узел `/dev/cu.usbmodem…`
  остаётся, но чип не отвечает — ни байта в логе, `esptool` (и `--before
  usb-reset`, и обычный) не подключается, `tools/reset.sh` падает с
  `Could not connect`. Замечено 06.11.2026 трижды: после `pio run -t erase`,
  после заливки файла по XMODEM и после `read-flash`. **Лечится только
  передёргиванием питания** (переподключить USB-кабель); после этого плата
  стартует штатно, ФС и файлы целы.
- **Что именно ломается — неизвестно; известно, как обойти.** Замерено
  06.11.2026 на чтении flash через `esptool`:

  | Что делает `esptool` после чтения | Плата |
  |---|---|
  | `--after hard-reset` (сброс по RTS) | USB-JTAG мёртв, нужен кабель |
  | `--after watchdog-reset` (сброс сторожевым таймером) | короткое чтение (10 КБ) переживает, 3 раза из 3; полный дамп раздела (96 с) — **нет** |
  | `--after no-reset`, затем `--before usb-reset --after no-reset read-mac` | поднимается сама, 2 раза из 2 |

  То есть важен не столько способ сброса, сколько то, что чип сбрасывают
  **из** загрузчика после долгой работы: `watchdog-reset` на коротком чтении
  проходил, на полном — нет. Рабочий обход — вообще не сбрасывать чип из
  загрузчика, а выйти из него **через USB-JTAG** (`--before usb-reset`, как в
  `tools/reset.sh`): линии DTR/RTS в этом не участвуют. Так и сделано в
  `tools/fsdump.py`. Предположительно хост или сам блок USB-JTAG остаётся в
  состоянии, из которого штатный сброс не выводит; разбираться в USB-стеке
  ради обхода, который уже проверен, смысла нет.
- **Режим загрузки** если автоматика не сработала: зажать **G0**, подать
  питание (или нажать RST при зажатом G0), отпустить.
- **Зарядка** идёт от USB; при питании от батареи плата работает как обычно.
- **Потребление в простое** на этой плате выше, чем у Cardputer: всегда
  включённый преобразователь подсветки. Для батарейных сценариев подсветку
  надо гасить (`basalt_indicator_set(0,0,0)`), иначе экран светит вхолостую.

## 6. Память и разделы

| Что | Значение | Откуда |
|---|---|---|
| Flash | 16 МБ | board-файл |
| PSRAM | 8 МБ OPI | board-файл |
| SRAM | 512 КБ, из них DRAM-область под кучу ~312 КБ | board-файл (`maximum_ram_size 327680`) |
| Занято прошивкой A0 | **32 756 Б RAM, 178 645 Б flash** | сборка 06.11.2026, `CONFIG_SPIRAM=y` |

**PSRAM включается в `sdkconfig.defaults`, а не в board-файле** (`CONFIG_SPIRAM`,
`CONFIG_SPIRAM_MODE_OCT`, `CONFIG_SPIRAM_SPEED_80M`). Board-файл PlatformIO
описывает flash и режим загрузки, а PSRAM — это конфиг IDF. До 06.11.2026
`CONFIG_SPIRAM` не был задан вообще: 8 МБ существовали в даташите и были
недоступны из кода. Цена включения — **+10.5 КБ flash** (драйвер `esp_psram`).

После включения PSRAM адреса в образе сдвинулись, и это нормально: драйвер
добавил код в IRAM. Сама карта памяти (`ld/memory.ld`) при этом переезда не
потребовала — именно это и была проверка гипотезы «`arch/` живёт на уровне
чипа, а не платы». На 06.11.2026 проверка образа даёт векторы `0x40375800`,
начало кучи `0x3fc99b00`, `_diram_i_start = 0x40378000`. Числа из A0 на
Cardputer (`0x40375400`, `0x3fc97ed0`) относились к сборке без PSRAM — их
совпадение с платой больше не выполняется и не должно.

**Замерено на этом экземпляре 06.11.2026** (`env:probe`, лог с платы): PSRAM
действительно есть — 8 МБ, режим OCT, 80 МГц, производитель `0x0d` (AP),
`good-die` пройден. Кадровый буфер 320×170×2 = 108 800 Б выделяется в PSRAM
одним блоком по адресу `0x3c030900` с выравниванием 64 Б; заливка `memset` —
2 840 мкс (≈38 МБ/с), сверка по байтам — 12 766 мкс, расхождений 0.

Свободная память по областям на той же сборке:

| Область | Всего | Свободно | Крупнейший блок |
|---|---|---|---|
| SRAM (`MALLOC_CAP_INTERNAL`) | 358 КБ | 355 КБ | 312 КБ |
| DMA (`MALLOC_CAP_DMA`) | 351 КБ | 348 КБ | 312 КБ |
| PSRAM (`MALLOC_CAP_SPIRAM`) | 8192 КБ | 8189 КБ | **8064 КБ** |

Разбивка SRAM по регионам (лог `heap_init`): 319 КБ с `0x3FC99B00` — это наша
куча из `ld/memory.ld`; ещё 21 КБ с `0x3FCE9710`, 32 КБ DRAM с `0x3FCF0000` и
7 КБ RTCRAM.

Кучу заводит не приложение, а сама ОС: `basalt_heap_init()` из `arch/xtensa/`
вызывается в `basalt_start_c()` уже после переезда на свой стек (`start.S`),
то есть до первого драйвера и одинаково для всех env. Порядок «сначала стек,
потом куча» — не косметика: `heap_caps_init()`, выполненная на стеке
загрузчика, оставляет в списке куч область под этим стеком и роняет систему
позже (проверено на живой плате 06.11.2026, подробности — `JOURNAL.md`).
Цифры выше сняты щупом, который теперь не заводит кучу, а только проверяет,
что её завела ОС.

**Таблица разделов — своя, с 06.11.2026** (`partitions.csv` в корне проекта):
приложение 2 МБ, дальше раздел данных `storage` — 14 272 КБ с подтипом `0x40`
(«свой формат», ФС ещё не выбрана). До этого стояла таблица IDF по умолчанию на
1 МБ приложения: видно в логе сборки `used 178645 bytes from 1048576 bytes`, и
15 МБ flash не принадлежали никому. Проверять надо с чипа, а не по файлу:
`env:flash` печатает таблицу, прочитанную из `0x8000`. Занято ровно 16 384 КБ,
свободного места вне разделов не осталось — в этом и смысл своей таблицы,
дальше место растёт только перераспределением.

### Встроенный flash: что выяснено 06.11.2026 (`env:flash`)

| Что | Значение | Чем |
|---|---|---|
| Чип | **Winbond**, JEDEC ID `0xEF4018` (16 МБ) | `esp_flash_read_id` |
| Размер | объявленный **16 384 КБ** = физический **16 384 КБ** | `esp_flash_get_size` / `get_physical_size` |
| Сектор / блок / страница | **4 КБ / 64 КБ / 256 Б** | данные ROM (`g_rom_flashchip`) |
| Чтение (SPI, без кэша) | **64 КБ за 7 989 мкс ≈ 8.0 МБ/с** | `env:flash` |
| Стирание сектора 4 КБ | **≈45 мс** (43 684–45 965 в трёх прогонах) | `env:flash` |
| Запись 4 КБ | **≈10 мс ≈ 400 КБ/с** | `env:flash` |
| Таблица разделов | `0x8000`: nvs `0x9000`/24 КБ, phy_init `0xF000`/4 КБ, factory `0x10000`/**2 МБ**, storage `0x210000`/**14 272 КБ**; вне разделов свободно **0 КБ** | `env:flash` |

Что из этого следует для хранилища (A9):

- **Стирание в 4.6 раза дороже записи того же объёма** (46 мс против 10 мс на
  4 КБ). Файловая система, которая стирает сектор на каждую запись, будет
  писать в секунду по три файла. Отсюда требование к формату: изменение не
  должно стоить «стереть и записать всё заново». BFS платит за блок, который
  действительно меняется (замеры — ниже), и не трогает остальное.
- **8 МБ/с чтения** — это потолок для `cat`: столько даёт SPI-драйвер. Кэш
  (memory-mapped чтение) может быть быстрее, но требует `spi_flash_mmap` и
  замков mmap, то есть решается отдельно, когда появится раздел данных.
- **Буфер любой операции обязан лежать в SRAM.** Драйвер работает в режиме
  no-OS: на время стирания и записи он гасит кэш, а PSRAM идёт через кэш.
  `esp_flash_read` в буфер из PSRAM вернёт `ESP_ERR_NO_MEM`, а не «медленно
  прочитает».

### Файловая система BFS на железе: что выяснено 06.11.2026 (`env:fs`)

Щуп монтирует раздел `storage`, при необходимости размечает его, пишет два
файла (`/etc/rc` — 18 Б текста, `/big` — 64 КБ узора), читает обратно, сверяет
побайтно, перемонтирует и проверяет ещё раз. Числа — с этого экземпляра.

| Что | Значение | Как |
|---|---|---|
| Раздел под ФС | `0x210000`, 14 272 КБ, **3 568 блоков** по 4 КБ | таблица разделов с чипа |
| Форматирование | **627.6 мс** | 2 сектора суперблока + 8 блоков inode-таблицы + корневой каталог |
| Монтирование пустого раздела | **5.4 мс** | обход inode-таблицы, битмап собирается в памяти |
| Монтирование с файлами | **6.5 мс** | то же плюс indirect-блоки `/big` |
| Запись 64 КБ (16 блоков) | **1 147–1 219 мс ≈ 52–55 КБ/с** | один вызов `bfs_write`, 16 коммитов |
| Чтение 64 КБ | **12.0 мс ≈ 5.3 МБ/с** | одним `bfs_read` |
| Сверка после чтения | 0 расхождений | побайтно |
| Занято после прогона | 30 блоков из 3 568 (2 суперблока, 8 inode-таблицы, 2 блока каталогов, 18 блоков данных и indirect) | `bfs_usage` |
| Файлы после сброса платы | на месте, содержимое сошлось | перемонтирование после `reset` |

**Почему запись в 7 раз медленнее чтения.** Блок 4 КБ стоит «стереть 46 мс +
записать 10 мс», то есть 56 мс из 72 мс на блок. Остальное — чтение старого
блока, COW inode-таблицы и запись суперблока. Это цена копирования при записи,
и она относится к любой записи во flash, а не к BFS: NOR-flash не пишет поверх
нестёртого. Отсюда практическое правило для VFS: **коммит один на файл, а не
на блок** — иначе каждая пачка данных оплачивает ещё и заголовок.

Чтение 5.3 МБ/с против 8.0 МБ/с у драйвера — это накладные расходы ФС (чтение
по блоку, поиск блока в карте, `memcpy` в буфер вызывающего). Для `cat`
текстового файла это незаметно; для заливки образа — заметно, и там кэш
(memory-mapped чтение) будет решаться отдельно.

**Почему объявленный размер совпал с физическим, хотя сборка ругалась.**
`Warning! Flash memory size mismatch detected. Expected 16MB, found 2MB!` —
это сравнение `board_upload.flash_size` (16 МБ) с `CONFIG_ESPTOOLPY_FLASHSIZE`
в `sdkconfig.<env>`. На драйвер это не влияло: размер он берёт из
`g_rom_flashchip`, который загрузчик заполняет по факту обнаружения чипа, а
`CONFIG_SPI_FLASH_SIZE_OVERRIDE` не задан, и подменить размер заголовком образа
некому. Но в заголовке образа стояло 2 МБ — то есть заявленный размер был
меньше реального. Исправлено 06.11.2026 вместе с таблицей разделов: размер
задаётся в `sdkconfig.defaults.tdisplay`, проверяется по заголовку
(`esptool image-info` печатает `Flash size: 16MB`).

## 7. Готовая база `platformio.ini`

```ini
[env:tdisplay]
extends = env:bare
board = lilygo-t-display-s3
board_build.flash_size = 16MB
board_upload.flash_size = 16MB
board_build.partitions = partitions.csv
board_build.cmake_extra_args = -DBASALT_BOARD_TDISPLAY=1
build_flags =
    -Iarch/xtensa/include
```

`board_build.partitions` указывает на файл в репозитории, а не на таблицу из
набора PlatformIO: своя таблица отдаёт данные тому, кто их читает — своей ФС,
а не FAT или SPIFFS. Размер flash при этом задаётся не здесь, а в
`sdkconfig.defaults.tdisplay`: `board_build.flash_size` для espidf описывает
только то, сколько заливать, а в заголовок образа и в таблицу разделов идёт
`CONFIG_ESPTOOLPY_FLASHSIZE`.

Почему `board_build.cmake_extra_args`, а не `-D`: `src/CMakeLists.txt` собирает
**разные наборы файлов** для разных плат (у каждой свой драйвер индикатора), а
список источников решается на этапе CMake, до компиляции.

Платформа в `[base]` остаётся `espressif32@8.0.0` — та же, что у Cardputer, и
это главная экономия переезда: тулчейн, `.clangd` и `ld/memory.ld` не меняются.

## 8. Грабли

| Симптом | Причина | Решение |
|---|---|---|
| Экран чёрный, в логе всё хорошо | не поднят `POWER_ON` (G15) | поднять питание панели до подсветки |
| Экран светится, изображения нет | подсветка включена, панель не инициализирована | это норма до вехи A1 |
| Картинка занимает левую половину, полосы, справа — старое содержимое | `MADCTL` без `MV`: панель портретная, запись шире 240 столбцов заворачивается в следующую строку | `DISP_MADCTL = 0x60` (MV\|MX), см. `board_pins.h` |
| Картинка на весь экран, но внизу полоса старого содержимого | окно не смещено: стекло 170 столбцов при памяти 240 | `DISP_Y_OFFSET = 35` (смещение прибавляет драйвер) |
| Картинка «мозаикой» | пиксельклок выше 16 МГц держит не каждая панель | снижать до 12–16 МГц; в текущем драйвере такт WR задан паузами `wr_settle()` |
| Картинка рвётся полосами при DMA из PSRAM | нет `esp_cache_msync` / выравнивания 64 Б | синхронизировать кэш перед запуском DMA |
| `pio run` просит другую плату | `default_envs` теперь `tdisplay` | явно `-e bare` для Cardputer |
| IDF-окружение не устанавливается: `No module named 'idf_component_manager'` | PlatformIO стоит на Python 3.15 | PIO на Python ≤ 3.14 (`~/.venvs/pio314`) или `make PIO=…` |
| Мигание подсветки вместо градаций яркости | на плате стоит повышающий преобразователь, ШИМ ему не подходит | подсветка только вкл/выкл |

Грабли, общие для обеих плат (линкер, сторожевые таймеры, USB-JTAG,
`pio device monitor` в скриптах) — в `AGENTS.md`, раздел 7.

## 9. Бэкап оригинальной прошивки

Снять **до** первой своей прошивки — на этой плате её потом не восстановить
никаким другим способом:

```bash
./tools/flash-backup.sh flash-id    # чип, размер flash, MAC
esptool --chip esp32s3 -b 115200 read_flash 0 0x1000000 backup/tdisplay-factory-16mb.bin
```

Читать на **115200**: на высокой скорости чтение отдаёт
`Corrupt data, expected 0x1000`.

Файл в `.gitignore` (`backup/`), но это единственная копия — сохранить её не
только на маке.
