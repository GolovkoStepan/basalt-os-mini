# BASALT-OS-MINI — журнал разработки

Зачем этот документ: чтобы через месяц — или через год — было понятно не
только **что** сделано, но и **почему именно так**. Роадмап говорит, куда
идём; здесь записано, как шли и на чём спотыкались.

**Кому адресован.** Тому, кто читает код и не является экспертом в
операционных системах. Каждый шаг объясняется бытовым языком: что это,
зачем нужно, что было бы без этого и как проверить, что работает.
Технические детали — в комментариях к коду, измеренные данные о железе — в
`board.md`. Записи до 05.11.2026 ссылаются на `board-cardputer.md`: тогда
платой проекта был Cardputer, а сам документ теперь уехал в проект `capsh`
(`../capsh/docs/board.md`) — здесь его больше нет. План — в
[`ROADMAP.md`](ROADMAP.md).

**Правило ведения.** Запись добавляется, когда шаг **проверен на плате**.
Предположения помечаются словом «предположительно». Записи не
переписываются задним числом: если вывод оказался неверным, он остаётся в
истории с пометкой, чем именно опровергнут — иначе нельзя понять, почему
решение когда-то казалось правильным.

## Словарь

Термины, которые встречаются ниже. Можно возвращаться сюда.

| Термин | Что это на самом деле |
|---|---|
| **SoC** | «система на кристалле» — вся электроника в одном чипе: процессор, память, USB, Wi-Fi |
| **Прошивка** | программа, которая живёт внутри микроконтроллера и запускается при включении |
| **Регистр** | ячейка размером 4 байта, через которую программа общается с железом. «Записать 1 в бит 30» = «включить такой-то блок» |
| **Бит** | один разряд: 0 или 1. Регистр состоит из 32 бит, каждый может означать отдельный переключатель |
| **Тик** | одно «щёлк» таймера. Тик системного таймера ESP32-S3 — 1/16 000 000 секунды |
| **Монотонное время** | счётчик, который только растёт и не зависит от часов. Сброс — только по перезагрузке |
| **Драйвер** | код, который умеет разговаривать с конкретным устройством: экраном, клавиатурой, USB |
| **FIFO** | буфер «первым пришёл — первым вышел». Железная очередь на несколько байт |
| **Опрос (polling)** | программа в цикле спрашивает «готово?» вместо того, чтобы ждать сигнала (прерывания) |
| **Прерывание** | сигнал, который заставляет процессор бросить текущую работу и заняться событием |
| **Паника** | аварийная остановка: программа сделала невозможное (например, делила на ноль), система печатает состояние и перезагружается |
| **Исключение** | событие «процессор заметил невозможное»: деление на ноль, обращение по нулевому адресу, несуществующая инструкция. Управление переходит обработчику, а не «просто падает» |
| **`EPC1`, `EXCVADDR`** | регистры, которые заполняет железо при исключении: адрес сбойной инструкции и адрес, к которому было обращение |
| **Watchdog** | «сторожевой пёс»: если программа зависла, он её перезагружает. Полезен в бою, мешает при отладке |
| **RTC WDT (сторожевой таймер загрузчика)** | таймер, который загрузчик включает на 9 секунд перед запуском приложения. Обычно его выключает `esp_system`; при своём старте это надо делать самому |
| **Линкер-скрипт** | файл-инструкция для компоновщика: что куда положить в памяти. Ошибка в нём = молчащая плата |
| **Таблица векторов** | список адресов: «если произошло такое-то прерывание — прыгай сюда» |
| **`VECBASE`** | регистр с адресом таблицы векторов. Младшие 10 бит он не хранит — отсюда требование выравнивания на 1 КБ |
| **Окно регистров** | регистров у процессора 64, а функция видит 16 — своё «окно». Когда окна кончаются, старое окно сбрасывается на стек; делает это железо, через отдельные векторы |
| **`EXCM`** | бит в регистре состояния `PS`: «мы внутри обработчика исключения». Пока он выставлен, новое исключение не обслуживается, а сразу становится двойным |
| **RMT** | блок в чипе, который сам выдаёт последовательность импульсов заданной длины, не отвлекаясь на программу. Им удобно гнать сигналы, где важна точность до сотен наносекунд |
| **WS2812** | адресный светодиод: один провод данных, цвет кодируется длиной импульсов. Такие ставят на модули M5 |
| **FIFO (у RMT)** | очередь на несколько слов. Записать туда и записать напрямую в память канала — разные вещи, и от этого зависит, увидит ли передатчик данные |
| **`arch/`** | каталог с кодом, который зависит от конкретного процессора. Всё, что выше, от процессора не зависит |
| **`esptool`** | утилита Espressif, которая заливает прошивку в чип по USB |
| **PlatformIO** | система сборки: собирает код, заливает прошивку, следит за библиотеками. Команда `pio` |
| **Прошивка «щуп»** | временная программа, чтобы узнать факты о железе. В финальную систему не входит |
| **Тест** | программа, которая сама проверяет код и говорит «сошлось» или «нет». В отличие от глаза, не устаёт и не забывает случай |
| **Unity** | маленькая библиотека для тестов на C: макросы `TEST_ASSERT_*`, сама считает провалы и печатает отчёт |
| **Хостовый тест** | тест, который выполняется на маке, а не на плате. Быстро и без железа, но проверяет только переносимый код |
| **Заглушка (stub)** | подмена настоящего устройства пустышкой: вместо USB-консоли — буфер в памяти. Позволяет проверить код, не имея платы |
| **CI (непрерывная сборка)** | сервис, который на каждый push сам собирает проект и гоняет тесты. Ловит «у меня работало» до того, как это увидит человек |
| **Смоук-тест** | короткая проверка «включается и не дымит»: залить прошивку и сверить несколько строк в логе |

### 20.10.2026. Подготовка: три прошивки-щупа

**Что это было.** До начала A0 нужно было узнать о плате то, что нельзя
прочитать в документации: как реально ведут себя экран, шина, клавиатура.

**Зачем щупы, а не сразу ОС.** Собственная ОС на первом шаге — это много
кода, в котором непонятно, что именно не работает: то ли драйвер, то ли
железо, то ли ошибка в старте. Щуп — маленькая программа, которая проверяет
одну вещь и печатает результат. Если щуп работает, значит железо годное, и
дальше можно строить. Три щупа:

| Щуп | Что проверял | Что дал |
|---|---|---|
| `env:hello` | жив ли чип, идёт ли вывод, работает ли светодиод | три канала обратной связи независимо друг от друга |
| `env:console` | идёт ли время, читается ли матрица клавиатуры | подтвердил, что клавиатура опрашивается |
| `env:bringup` | дисплей: последовательность инициализации, скорость шины | цифры, которые иначе пришлось бы искать вслепую |

**Что выяснилось важного.**

1. **Полный кадр 240×135 на 40 МГц передаётся за 13.2 мс.** Это 98% от
   теоретического потолка — то есть шина работает почти идеально, и на
   скорость отрисовки влияет не она, а наш код.
2. **За один раз шина больше 32 768 байт не отправит.** Кадр — 64 800
   байт, значит его придётся резать на части. Знание спасло от долгой
   отладки позже.
3. **Частота 60 МГц недостижима:** делитель считается от 80 МГц, ближайшая
   ступень вниз — 40. Запрос 60 даёт фактически 40. Без вывода фактической
   частоты это выглядело бы как «замер совпал, наверное ошибка».
4. **Свободной памяти 281 КБ** при статическом кадровом буфере 64.8 КБ.
   Для терминала с запасом.

**Польза для не-эксперта.** Все эти цифры — не любопытство. От них зависит
архитектура: например, знать, что кадр не влезает в одну передачу, значит
заранее заложить разбиение на полосы, а не переделывать драйвер экрана.

### 20–21.10.2026. Неожиданный урок: «плата сломалась» которой не было

**Что случилось.** После очередной заливки плата перестала подавать признаки
жизни: порт в системе не появлялся, экран тёмный. Полдня ушло на версии от
«сгорел USB» до «нет питания».

**Что оказалось на самом деле.** Виноват был мой же скрипт чтения лога. При
открытии порта он дёргал линии `DTR`/`RTS` — на обычных платах это сброс, а
на USB-периферии ESP32-S3 та же комбинация означает **«войти в режим
загрузчика»**. Чип послушно уходил в этот режим и оставался там: порт есть,
`esptool` отвечает, а прошивка не исполняется. Снаружи — мёртвая плата.

**Вывод, который теперь в правилах.** На этой плате **нельзя** «сбросить
плату» дёрганьем линий порта. Правильный сброс — через `esptool`:
`--after hard-reset`.

**Зачем это записано.** Это не рядовая ошибка, а ловушка, в которую легко
попасть снова: симптом («нет лога») указывает на железо, а причина — в
инструменте. Теперь в `board-cardputer.md`, раздел 12, есть таблица «что чем
проверяется», чтобы не начинать с неверной гипотезы.

**Побочный вывод.** Отсутствие лога **не означает**, что прошивка не
залилась. Поэтому в прошивках появились независимые каналы обратной связи:
светодиод и подсветка экрана — они работают без USB.

### 21.10.2026. Веха A0, шаг 1: убрать Arduino, сделать свою консоль и своё время

Прежде чем читать дальше, важно понять, **что такое A0** и зачем его
делать, если прошивка и так работала.

#### Зачем отказываться от Arduino

Arduino — это готовая обвязка: она включает консоль, считает время, умеет
работать с пинами, содержит кучу библиотек. Начинать с неё удобно. Но у неё
есть свойство, критичное для этого проекта: **она решает за нас, как всё
устроено**, и решает по-своему, для общего случая.

Для операционной системы это неприемлемо по трём причинам:

1. **Размер.** Прошивка с Arduino — 330 КБ, без него — 167 КБ. Половина
   объёма — код, который нам не нужен, но занимает место в дефицитной
   памяти.
2. **Контроль.** Когда система «сама» печатает в консоль, мы не знаем,
   когда и что она печатает. Своя ОС должна сама решать, что попадает в
   терминал — иначе невозможен ни шелл, ни tty, ни паника с дампом
   регистров.
3. **Перенос на другую плату.** Ровно этот код (`arch/`) заменяется целиком
   при переезде на M5Stack Tab5. Если он переплетён с Arduino, переезд
   превращается в переписывание всего.

Ключевое слово здесь — **`arch/`**. Это каталог «всё, что зависит от
процессора». Правило проекта: такой код живёт за чётким интерфейсом, а не
разбросан `#ifdef` по всему ядру. От этого напрямую зависит цена переезда на
`basalt-os`.

#### Что сделано: своя консоль

**Файл:** `arch/xtensa/console_usb_jtag.c`

**Задача.** Выводить текст в терминал на маке без чужой библиотеки.

**Как это устроено.** В чипе есть отдельный блок для USB-консоли. Программа
кладёт байт в регистр, железо отправляет его на компьютер; обратно — так же.
Есть два флага: «можно писать» и «есть что читать». Драйвер их проверяет.

**Почему опрос, а не прерывания.** Прерывания требуют таблицы векторов,
которой в A0 ещё нет. Опрос проще и не может «потерять» обработчик. Когда
появится планировщик (A6), прерывания станут нужны — но не раньше.

**Отдельная предосторожность.** Если терминал на маке закрыт, данные никто
не забирает. Наивная реализация в этом случае **зависла бы навсегда**: цикл
ждёт «можно писать», а оно никогда не наступит. Поэтому в ожидании есть
предел попыток: не дождались — отдаём управление дальше. Это ровно тот урок
из записи выше: молчаливое зависание нельзя отличить от мёртвой платы.

#### Что сделано: свой счётчик времени

**Файл:** `arch/xtensa/tick.c`

**Задача.** Отвечать на вопрос «сколько прошло с запуска».

**Как это устроено.** В чипе есть блок SYSTIMER — два независимых счётчика,
тик 1/16 000 000 секунды. Они тикают сами, мы только читаем.

**Почему не свой таймер.** Два альтернативных варианта: счётчик команд
процессора (32-битный — переполняется за 18 секунд, пришлось бы считать
переполнения) и прерывание по таймеру (нужны вектора, которых нет).
SYSTIMER — 64-битный и без прерываний.

**Тонкость, из-за которой код длиннее одной строки.** Счётчик 64-битный, а
регистры 32-битные: значение лежит в двух половинах. Прочитать «верх» и
«низ» подряд нельзя — между этими чтениями младшая половина может
переполниться, и получится мусор (время скакнёт на минуты). Решение встроено
в железо: перед чтением нужно «защёлкнуть» значение специальным битом, тогда
железо замораживает копию. Код делает именно это, потом ждёт флаг «готово»,
и только затем читает.

**Как из тиков получаются секунды.** Одно деление на 16 — и тики стали
микросекундами.

**Ограничение.** Это не календарное время: после перезагрузки счёт
начинается заново. Реальная дата — веха A8.

#### Что сделано: проверка паники

**Прошивка:** `env:bare-panic`

**Задача.** Убедиться, что сбой программы не превращает плату в «кирпич», а
печатает диагностику.

**Как проверяется.** Через 5 секунд после старта прошивка намеренно делит на
ноль. Что видно в терминале:

```
[panic-test] деление на ноль
Guru Meditation Error: Core 0 panic'ed (IntegerDivideByZero)
Core 0 register dump:
PC : 0x42001529  PS : 0x00060330 ...
EXCCAUSE: 0x00000006
Backtrace: ...
basalt-os boot          ← перезагрузилась и работает дальше
```

`EXCCAUSE: 0x06` — код причины сбоя, в данном случае «деление на ноль».
Плата после этого жива: заново печатает баннер и тикает.

**Важная оговорка.** Печатает пока **чужой** обработчик (из IDF). Свой —
следующий шаг A0. Но сам факт проверен: механизм диагностики на этой плате
работает, и есть с чем сравнивать, когда напишем свой.

#### Как это выглядит целиком

```
basalt-os boot
[arch] ESP32-S3, Xtensa LX7
[console] USB Serial/JTAG, свой драйвер, база 0x60038000
[tick] SYSTIMER Unit 0, 16 МГц
[led] WS2812 на G21 через RMT, 10 МГц, порядок GRB, память ok, кадр 29 мкс
[start] app_main через старт IDF, своя таблица векторов - далее
ready

tick 1  uptime 3.026 s
tick 2  uptime 4.026 s
tick 3  uptime 5.026 s
```

**Как проверить самому:**

```bash
cd ~/esp32-lab/basalt-os-mini
pio run -e bare                  # собрать
pio run -e bare -t upload        # залить
./tools/serial-read.sh 10        # смотреть
```

**Признак успеха:** номер тика прибавляется ровно на 1, `uptime` — примерно
на 1.000. Если номер скачет или uptime прыгает — цикл где-то блокируется.

**Про строку `[start]`.** Она честно говорит, что пока не так: программа
всё ещё попадает в `app_main` через чужой старт IDF, а не через свой
загрузчик. Это следующий шаг, и он намеренно оставлен напоследок: ошибка в
линкер-скрипте даёт молчащую плату без диагностики, поэтому её лучше делать
тогда, когда консоль уже своя и работает.

#### Что попутно выяснилось (чтобы не наступить снова)

| Наблюдение | Почему важно |
|---|---|
| Для `framework = espidf` опция `build_src_filter` **не работает** | сборщик генерирует список файлов сам по всему `src/`, и в сборку лезут чужие файлы. Состав задан вручную в `src/CMakeLists.txt` |
| В пакете IDF 6.1.0 не хватало питоновских модулей | `kconfgen` и `idf-component-manager` доставлены в окружение IDF |
| Штатный watchdog IDF ругался на занятый цикл | наш цикл не отдаёт управление планировщику, потому что планировщика нет. Отключён в `sdkconfig.defaults` |
| Баннер терялся при открытии терминала | добавлена пауза 2 секунды перед первым выводом |
| IDF ставит частоту процессора 160 МГц, не 240 | для A0 неважно, но помнить: заявленные 240 надо будет включать самому |
| Открытие порта перезапускает чип | поэтому `uptime` считается от открытия терминала, а не от включения платы |

#### Что осталось до закрытия A0

| Что | Зачем |
|---|---|
| Свой обработчик исключений | чтобы паника не зависела от чужого кода, и чтобы печатать **свои** поля (например, состояние своих структур) |
| Свой линкер-скрипт | контроль над картой памяти. Без него невозможно ни своё расположение разделов, ни своя файловая система |
| Своя таблица векторов и точка входа | прерывания и старт перестают быть чужими. Это и есть «металл» в названии вехи |

**Порядок не случаен:** сначала свой обработчик исключений (он безопасен и
даёт инструмент диагностики), потом линкер и вектора (они опасны и требуют
уже работающей диагностики).

### 21.10.2026. Светодиод: третий канал обратной связи, свой драйвер WS2812

#### Зачем это нужно

Сегодня уже было два случая, когда система работала, а узнать об этом было
нечем: USB-консоль молчала, и плата выглядела мёртвой. Светодиод снимает эту
слепоту — он горит независимо от того, открыт ли терминал, воткнут ли кабель.

Второе, менее очевидное: индикатор — это ещё и **диагностика сбоев**. Плата
должна уметь сказать «упала» красным, оставаясь без экрана и без лога.

#### Что сделано

**Файлы:** `arch/xtensa/led_ws2812.c`, `arch/xtensa/include/led_ws2812.h`

Два состояния:

| Когда | Что видно |
|---|---|
| каждый тик (раз в секунду) | короткая зелёная вспышка, 80 мс |
| `env:bare-panic` перед падением | красный, горит до перезагрузки |
| до первой команды | погашен: цвет от прошлой прошивки стирается явно |

#### Как это устроено

Светодиод WS2812 — не «три пина на три цвета». У него один провод данных, и
цвет кодируется **длительностью импульсов**: короткий высокий уровень — ноль,
длинный — единица. Точность — сотни наносекунд. Кадр — 24 бита, по 8 на
зелёный, красный и синий.

Отсюда единственное правильное решение: **железо RMT**, отдельный блок,
который сам выщёлкивает уровни из памяти, не отвлекаясь на прерывания. Попытка
дёргать пин в цикле на C развалилась бы на первом же тике системного таймера.

#### Три ловушки, каждая из которых даёт полное молчание

Отладка заняла весь вечер, и ни одна из трёх ошибок не выдавала себя в логе.
Записано, чтобы не повторять.

**1. Память канала вместо FIFO.** У RMT есть режим доступа: через FIFO или
напрямую к памяти. Я оставил по умолчанию FIFO — и записи «в память» тихо
уходили в очередь, а передатчик читал пустую память. Снаружи: канал рапортует
об успешной передаче, лента молчит.

**2. Два делителя частоты.** У RMT частота задаётся двумя делителями: общим на
группу каналов и отдельным на канал. Я поделил общим (8) и оставил канальный
равным 1. Рабочее сочетание, которое использует IDF, — наоборот: **общий 1,
канальный 8**. При моём варианте кадр уходил на неверной частоте: светодиод
такой сигнал не разбирает и молчит.

**3. Нулевое слово — это конец кадра.** Передатчик останавливается на слове, у
которого обе длительности нулевые. Хвост блока памяти нужно явно заполнять
нулями, иначе после цвета в линию пойдёт мусор из незаписанных слов.

#### Как удалось понять, что дело не в железе

Проверок по порядку:

1. **Распиновка.** Взял заводскую таблицу пинов M5Unified: `board_M5Cardputer →
   GPIO_NUM_21`. Это снимает вопрос «а может, светодиод на других пинах» —
   встречающаяся в интернете схема G25/G26/G27 относится к другой плате.
2. **Контрольный опыт.** Залил `env:hello` на Arduino, где светодиодом
   управляет готовая библиотека. Мигает → железо исправно, виноват мой код.
   Это единственный способ не чинить то, что не сломано.
3. **Тайминги.** Сверил с M5Unified: 300/900 нс при 10 МГц. У меня было то же
   самое — значит не тайминги.
4. **Замер вместо догадок.** Добавил в драйвер измерение длительности кадра по
   регистру состояния. 24 бита по 1.2 мкс = 28.8 мкс; замерено 29. Это число
   сразу показывает, верна ли частота, и остаётся в логе после каждой сборки.

**Ловушка в самом замере:** сначала я ждал «канал вернулся в простой» и получал
1 мкс — автомат ещё не вышел из простоя в момент проверки. Правильный признак
конца кадра — адрес чтения дошёл до нулевого слова-терминатора.

#### Что теперь видно при старте

```
[led] WS2812 на G21 через RMT, 10 МГц, порядок GRB, память ok, кадр 29 мкс
```

Одна строка отвечает на два вопроса: пишется ли память канала и с какой
частотой уходят кадры. Если светодиод когда-нибудь снова замолчит, начинать
надо с неё, а не с паяльника.

#### Как проверить самому

```bash
pio run -e bare -t upload
```

**Признак успеха:** раз в секунду короткая зелёная вспышка, одновременно со
строкой `tick N`.

**Ограничение:** светодиод питается от линии подсветки G38, поэтому его
инициализация включает и подсветку экрана. Пока драйвера экрана нет, экран
светится серым — это ожидаемо, а не неисправность.

**Красный при панике** в `env:bare-panic` на тот момент не проверялся —
проверен в следующей записи.

### 21.10.2026. Паника: свой обработчик исключений

**Файлы:** `arch/xtensa/panic.c`, `arch/xtensa/include/panic.h`,
`arch/xtensa/format.c`, `arch/xtensa/include/format.h`, `src/bare/main.c`

**Прошивка:** `env:bare-panic`

**Задача.** Забрать у IDF обработку исключений: чтобы при сбое печаталось
понятное человеку объяснение, горел красный светодиод, и плата сама
перезагружалась.

#### Что такое исключение и почему это важно

Процессор умеет замечать, что программа сделала невозможное: поделила на
ноль, полезла по нулевому адресу, выполнила несуществующую инструкцию. В этот
момент он не падает молча — он передаёт управление **обработчику
исключений**, заранее известной функции, и прикладывает к ней «кадр»: все
регистры и адрес инструкции, на которой всё сломалось.

Пока обработчик чужой, мы не управляем ни форматом, ни набором полей. Свой
даёт три вещи:

1. **Текст по-русски.** Не `EXCCAUSE: 0x00000006`, а «причина 6: деление на
   ноль», и рядом объяснение, что означает каждое поле.
2. **Красный светодиод до сброса.** Лог может не дойти до компьютера —
   кабель отключён, терминал закрыт, — а цвет видно всегда. Это ровно та же
   мысль, что и зелёная вспышка на тик, только для сбоя.
3. **Независимость.** Файл не вызывает ни одной функции IDF: только регистры
   и свои драйверы. При форке платформы его не придётся переписывать.

#### Как это включено

В IDF есть таблица `_xt_exception_table` — массив указателей, по одному на
каждую пару «причина, ядро»: 64 причины × 2 ядра = 128 записей. Изначально
все они указывают на чужой обработчик. Свой пишется в таблицу при старте, до
всей остальной работы с периферией:

```c
for (int cause = 0; cause < 64; ++cause)
    for (int core = 0; core < 2; ++core)
        _xt_exception_table[cause * 2 + core] = panic_handler;
```

Таблица — обычные данные в ОЗУ, поэтому подмена не требует ни своей таблицы
векторов, ни линкер-скрипта. Это и есть причина, по которой паника делается
**до** них: она не зависит от того, что мы ещё не написали.

#### Что печатается

```
!!!!!! PANIC !!!!!!
причина 6: деление на ноль
EPC1     0x420014ae  адрес инструкции, на которой всё остановилось
EXCVADDR 0x00000000  адрес, к которому было обращение (0 - не про адрес)
PS       0x00060330  SAR 0x0000000a
A0  0x8200626e  A1  0x3fc966f0
...
сброс через 3 с
```

Три поля стоит знать:

| Поле | Что это |
|---|---|
| `EPC1` | адрес сбойной инструкции. По нему в карте прошивки находится строка кода |
| `EXCVADDR` | адрес, к которому было обращение. Ноль при делении на ноль — норма: сбой не про память |
| `PS` | регистр состояния процессора: уровень прерываний, режим |

`EPC1` проверяется одной командой:

```bash
~/.platformio/packages/toolchain-xtensa-esp-elf/bin/xtensa-esp32s3-elf-addr2line \
    -pfiaC -e .pio/build/bare-panic/firmware.elf 0x420014ae
# → app_main at src/bare/main.c:84
```

Строка 84 — та самая, где стоит деление. То есть напечатанный адрес не
«какой-то», а правильный, и по нему действительно находится место сбоя.

#### Первый опыт: сброс делал не наш код

Первая версия печатала дамп и падала в паузу на 3 секунды — а причина сброса
в ROM-логе приходила `rst:0x8 (TG1WDT_SYS_RST)`. Это сторожевой таймер IDF:
он ждёт, что код периодически подаёт признак жизни, и через ~300 мс
перезапускает чип. Пока мы «стоим в панике», кормить его некому.

Практический вывод: **пауза перед сбросом бессмысленна, пока сторожевые
таймеры включены** — они срабатывают раньше, и наш собственный код сброса
вообще не исполняется (то есть и не проверяется). Поэтому перед паузой
паника выключает три таймера: TG1 (прерываний), TG0 (задач) и RTC. Запись
защищена ключом `0x50D83AA1` — без него регистр игнорируется.

После этого причина сброса стала `rst:0x3 (RTC_SW_SYS_RST)` — это уже наш
сброс через регистр `RTC_CNTL_OPTIONS0`. Регистр, а не `esp_restart`: паника
может случиться до того, как поднялись планировщик и сервисы, на которых
`esp_restart` держится.

#### Замер паузы

По логу с отметками времени:

```
  7.251  !!!!!! PANIC !!!!!!
  7.254  сброс через 3 с
 10.254  ESP-ROM:esp32s3-20210327
 10.255  rst:0x3 (RTC_SW_SYS_RST)
```

Между строкой «сброс через 3 с» и стартом ROM — 3.000 с. Пауза настоящая, а
не «мы надеемся, что она есть».

#### Грабля при чтении лога паники

Пока проверял, получил несколько пустых логов и чуть не начал искать ошибку
в коде. Причина оказалась в измерительном приборе: **открытие порта само
перезапускает чип** (`rst:0x15 USB_UART_CHIP_RESET`). При чтении короткими
окнами по 3 секунды каждое окно открывало порт заново, чип стартовал с нуля,
и в кадр попадали только баннер и `tick 1` — паника на 7-й секунде не
успевала случиться. Читать надо **одним окном не короче 10 секунд**.

#### Что осталось от чужого

- `app_main` вызывается стартом IDF, а не нашей точкой входа;
- линкер-скрипт штатный;
- таблица векторов (там, где процессор ищет обработчик исключения) тоже
  чужая — мы подменили только содержимое таблицы обработчиков.

Это следующий и последний шаг A0.

#### Как проверить самому

```bash
pio run -e bare-panic -t upload
./tools/serial-read.sh 15
```

**Признак успеха:** 4 зелёные вспышки (тики 3–6 с), затем красный светодиод
и дамп в терминале; красный держится ~3 с, затем плата перезагружается, и
всё повторяется. В ROM-логе после дампа — `rst:0x3 (RTC_SW_SYS_RST)`.

**Рабочая прошивка** — `env:bare`: она без теста паники, светодиод мигает
зелёным и ничего не перезагружается.

### 21.10.2026. Своя точка входа: сделана. Своя таблица векторов: не вышло, и это правильно

**Файлы:** `arch/xtensa/start.S`, `arch/xtensa/start.c`,
`arch/xtensa/include/start.h`, `arch/xtensa/panic.c` (переписан),
`arch/xtensa/include/panic.h`, `src/bare/main.c`

**Прошивка:** `env:bare`

**Задача.** Забрать у IDF запуск приложения: своя точка входа, свой стек,
своя таблица векторов. Последнее - оказалось задачей не этого шага.

#### Что такое точка входа и где она в цепочке

При включении чип никого не спрашивает, что запускать: он прыгает на адрес из
таблицы загрузки. Дальше работает чужой загрузчик второй ступени: грузит образ
из флеша в память, проверяет его и передаёт управление в `call_start_cpu0` -
функцию порта IDF. Она делает то, без чего дальше некуда: включает кэш,
настраивает MMU, поднимает частоту, стирает BSS.

Затем IDF вызывает `start_cpu0`. И вот здесь важно: в IDF эта функция
объявлена **weak** - то есть «если кто-то предложит свою, берите её». Это
штатная точка расширения, а не взлом. Мы её перекрыли, и с этого момента
управление в IDF не возвращается: планировщик FreeRTOS не запускается,
`main_task` не создаётся, `app_main` не вызывается. Наша система - это цикл в
`basalt_main`.

```
загрузчик (чужой) → call_start_cpu0 (чужой: кэш, MMU, BSS) → start_cpu0 (наш)
                                                                   ↓
                                                            basalt_start (свой стек)
                                                                   ↓
                                                            basalt_main (наш цикл)
```

Зачем отдельная `basalt_start` на ассемблере: указатель стека нельзя менять из
C. Пока компилятор считает, что локальные переменные лежат по старому
указателю, любая следующая функция будет писать в чужую память. Поэтому
переезд на свой стек - отдельная функция, в которой на старом стеке не остаётся
ничего живого.

**Проверено на плате:** баннер печатается, тики идут, паника работает
(`причина 6: деление на ноль`, сброс через 3 с, `rst:0x3 RTC_SW_SYS_RST`).
Строка `[start]` в баннере это подтверждает.

#### Таблица векторов: три попытки и что из них вышло

Таблица векторов - это первый 1 КБ памяти, на который указывает регистр
`VECBASE`. Процессор при сбое не ищет обработчик, а прыгает строго на
`VECBASE + смещение`; смещения заданы архитектурой (0x300 - исключение ядра,
0x340 - пользователя, 0x180..0x240 - прерывания уровней 2..5 и так далее).

Написать её - не проблема. Проблема - **положить** её так, чтобы она работала.
`VECBASE` не хранит младшие 10 бит адреса, значит нужно выравнивание на 1 КБ.
Дальше начались три отказа подряд, и каждый дал по факту о железе:

1. **Свой раздел в IRAM с выравниванием на 1 КБ.** Выравнивание поднялось у
   всего раздела `.iram0.text`, в начале IRAM появилась дыра, образ развалился
   на лишний сегмент. Плата перестала доходить даже до первого сообщения IDF -
   светодиод не горел, лог обрывался на последней строке загрузчика.
2. **Таблица в `.text` и копирование в IRAM.** Здесь помогло то, что я заранее
   перевёл консоль IDF на USB: иначе был бы виден только цикл `rst:0xc` без
   текста. Дамп сказал: `EXCCAUSE 3` (LoadStoreError), `EXCVADDR 0x42001f0c` -
   адрес самой таблицы. То есть регион кода (`0x42000020`, IROM) **не читается
   как данные**, только исполняется.
3. **Таблица в `.rodata` и копирование.** Скопировать уже можно, но
   скопированный код не работает: тела обработчиков используют относительные
   переходы и литералы, а их адреса посчитаны от места линковки, а не от места
   копии.

**Вывод.** Своя таблица векторов возможна только со своим линкер-скриптом, где
1 КБ под неё вырезаны в IRAM заранее. Пока раскладка IRAM чужая, любая попытка
вклиниться ломает либо образ, либо адресацию. В роадмапе порядок шагов был
верный (`линкер → вектора`), а я его нарушил: начал с векторов, потому что
казалось, что «таблица - это просто данные».

Это и есть главный результат шага: не «сделано», а «выяснено, в каком порядке
делать». Свой обработчик исключений при этом остаётся: он ставится в таблицу
**обработчиков** IDF (`_xt_exception_table`), и это работает без своего
линкера - проверено дампом на живой плате.

#### Побочные знания, которые дороже самой задачи

| Что | Почему важно |
|---|---|
| Паника IDF печатает в UART0 (GPIO43/44), а туда ничего не подключено | при сбое видно только цикл сбросов без текста; чтобы увидеть дамп, консоль IDF надо перевести на USB |
| IROM (`0x42000020`) нельзя читать как данные | отсюда `LoadStoreError` при попытке скопировать что-то из `.text` |
| Открытие USB-порта само перезапускает чип | короткие окна чтения ловят только начало старта; для паники нужен один длинный сеанс |

| clangd 21 перестал видеть `<stdbool.h>`, `_mbstate_t`, `__FILE` | в `.clangd` пути вели на newlib, а прошивка с GCC 15 собирается с picolibc; плюс `-isystem` и путь были одной строкой вместо двух | пути — в `toolchain-xtensa-esp-elf/picolibc/include`, каждый `-isystem` отдельным элементом списка (подробно в `AGENTS.md`, раздел 6) |

### 21.10.2026. Таблица векторов: сделана. Шесть пустых слотов, которых не хватало

сбое. Предыдущая запись кончалась выводом «без своего линкера нельзя».

#### Что теперь своё

`VECBASE` переключается на нашу таблицу в `basalt_vectors_init` и читается
обратно: `[vectors] VECBASE 0x40375400 совпадает`. Дальше любое исключение и
любое прерывание обслуживает наш код:

- **таблица** - раздел `.iram1.basalt_vectors` с `.align 1024` в `vectors.S`.
  Линкер кладёт её в IRAM: `0x40375400`, блок 1232 Б. Исполняется на месте,
  копирования нет;
- **шесть слотов окон** (`0x000`…`0x140`) - канонические тела Xtensa;
- **остальные слоты** (2–10) ведут в один вход: спрятать `a1..a4` в
  `EXCSAVE_1..5`, переехать на аварийный стек, собрать кадр;
- **кадр** свой, 88 байт: 16 регистров, `PS`, `PC`, `EXCCAUSE`, `EXCVADDR`,
  `SAR`, номер слота. Смещения сверяются `_Static_assert` с ассемблером, потому
  что раскладка задана в двух местах;
- **аварийный стек** - 8 КБ в DRAM, отдельно от стека сбоя;
- **C** вызывается через `callx4`, указатель на кадр - в `a6`;
- **паника** печатает отчёт, красит светодиод в красный, держит 3 с и
  сбрасывает чип через `RTC_CNTL_SW_SYS_RST`.

#### Почему прошлый раз «не вышло», а теперь вышло

Дело было не в линкере, а в **имени раздела**. `.align 1024` на существующем
`.iram0.text` поднимал выравнивание у всего раздела - в начале IRAM появлялась
дыра, образ разваливался на лишний сегмент. Новый раздел
`.iram1.basalt_vectors` линкер кладёт отдельным куском и выравнивает только его:
правки линкер-скрипта не нужны. Цена своей таблицы - один новый раздел, а не
1 КБ, вырезанный заранее.

#### Молчаливое зависание: окна регистров

Первая сборка с таблицей стартовала и висела молча сразу после
`[vectors] готово`. Виновата была не таблица: слоты 2..10 работали, а шесть
слотов окон остались нулями.

Почему это смертельно: ABI оконный (`entry`/`retw`), физических регистров 64,
окна по 16. Как только потомку нужен регистр занятого окна, аппаратура поднимает
переполнение окна и требует сбросить старое окно на стек - **в обычной работе**,
а не только при сбое. Переход на нулевой адрес дал двойное исключение, и плата
встала без единого байта в консоль. Симптом обманчивый: «сбой после
инициализации таблицы», хотя таблица была права, а неполна.

Нашлось это только дампом в RTC-память: голые `s32i` в `0x50000000` до переезда
на стек, потом `esptool read-mem`. Обычная DRAM для этого не годится - её
затирает стек загрузчика при сбросе.

#### Вторая находка: `entry` при `EXCM=1`

Когда дамп показал, что обработчик доходит до вызова C, выяснилось, что C не
начинает работать вообще: первая инструкция любой C-функции - `entry`, и при
`PS.EXCM=1` она даёт двойное исключение. Проверено тремя пробными вызовами:
функция без кадра работает, с ручным кадром (`addi a1, a1, -32`) работает, с
`entry` - нет.

Причина: `entry` может потребовать освобождения окна, а при `EXCM=1` обычные
векторы не обслуживаются. Значит C надо звать с **снятым** `EXCM`. Смотрим, как
это делает IDF (`components/esp_system/port/arch/xtensa/panic_handler_asm.S`), и
повторяем:

```asm
movi a0, PS_INTLEVEL(XCHAL_DEBUGLEVEL-2) | PS_UM | PS_WOE
wsr  a0, ps
mov  a6, sp
call4 panicHandler
```

Отсюда же третья поправка: **`call4`, а не `call0`**. `call0` не поворачивает
окно, и пролог вызываемой функции видит окно занятым - то есть требует
переполнения, которого после `SPILL_ALL_WINDOWS` быть не должно.
`call4` поворачивает окно, пролог получает свободное, а первый аргумент
приходит в `a2` (передан в `a6`). После этого паника заработала целиком с
первого запуска.

#### Третья находка: кадр - на свой стек, а не на стек сбоя

Первая же попытка писать кадр «на место аварии» дала бесконечный цикл двойных
исключений: если стек сбоя испорчен, каждое сохранение кадра падает снова.
Отдельный аварийный стек делает отчёт независимым от состояния стека сбоя.
Кадр кладётся **внутрь** блока (`top - FRAME_SIZE`), а не над вершиной: над
вершиной уже чужая память.

#### Что видно в логе (`env:bare-panic`)

```
[panic-test] деление на ноль

[сбой] слот 9, причина 6, EPC1 0x42001456, EXCVADDR 0x00000000


!!!!!! PANIC !!!!!!
причина 6: деление на ноль
вектор  9  исключение пользователя
EPC1     0x42001456  адрес инструкции, на которой всё остановилось
EXCVADDR 0x00000000  адрес, к которому было обращение (0 - не про адрес)
PS       0x00060b30  SAR 0x0000000a
INTENABLE 0x00000000  INTERRUPT 0x00018040
A0  0x820020a2  A1  0x3fc974d0
...
сброс через 3 с
rst:0x3 (RTC_SW_SYS_RST)
```

Первая строка (`[сбой] …`) печатается до полного разбора. Она нарочно короткая:
это страховка на случай, если сам разбор не переживёт сбой. Первые три сбоя она
печатает, дальше молчит - иначе цикл двойных исключений забивает лог.

#### Побочные знания

| Что | Почему важно |
|---|---|
| `PS.UM=1` у обычного кода → исключение приходит в слот `0x340`, а не `0x300` | деление на ноль дало `PS 0x00060b30` и слот 9 «пользовательское»; оставить `0x340` пустым - не увидеть сбоев обычного кода вообще |
| `entry` при `EXCM=1` → двойное исключение | из обработчика нельзя звать C, не сняв `EXCM` |
| `call0` в C-функцию оконного ABI → пролог требует переполнения окна | отсюда `callx4` и аргумент в `a6` |
| DRAM сброс не переживает, RTC-память (`0x50000000`) - переживает | единственный способ увидеть «докуда дошло», когда консоль молчит |
| `s32e`/`l32e` в слотах окон пишут в кадр предка по базе `a5`/`a9`/`a13` | поэтому шесть слотов нельзя заменить «своей логикой» - базы заданы ABI |

#### Как проверить самому

```bash
pio run -e bare -t upload && ./tools/serial-read.sh 10
pio run -e bare-panic -t upload && ./tools/serial-read.sh 12
```

**Признак успеха:** в обычной прошивке перед баннером идут четыре строки
`[vectors]` - адрес таблицы в IRAM, «пул … сходится», «VECBASE … совпадает»,
«готово»; дальше тики. В `bare-panic` через 5 секунд - строка `[сбой]`, полный
`PANIC` с регистрами, красный светодиод на 3 секунды и загрузка с
`rst:0x3 (RTC_SW_SYS_RST)`.

### 21.10.2026. Своя карта памяти: веха A0 закрыта

**Файлы:** `ld/memory.ld`, `platformio.ini`, `src/bare/main.c`

**Прошивки:** `env:bare`, `env:bare-panic`

**Задача.** Последний пункт A0: карта памяти должна лежать в репозитории, а не
появляться при каждой сборке в `.pio/build/<env>/memory.ld` из шаблона IDF.

#### Как включается

Одна строка в `[env:bare]`:

```ini
board_build.ldscript = ld/memory.ld
```

PlatformIO видит, что линкер-скрипт задан, и не генерирует свой: берёт наш файл
и подставляет его в линковку вместо сгенерированного `memory.ld`. `sections.ld`
при этом остаётся чужим - там каталог секций компонентов, которые мы всё ещё
используем.

Тонкость, которая видна только в `build.ninja`: там всё ещё встречается
`-T memory.ld`, но это правило IDF для своего промежуточного `*.elf`, которое
в нашей сборке не выполняется (файла `.pio/build/bare/esp-idf/esp_system/ld/memory.ld`
просто нет). Образ для платы - `firmware.elf` - PlatformIO линкует сам, своим
`LDSCRIPT_PATH`, то есть нашим файлом.

Проверено не на слово: намеренная опечатка в файле останавливает сборку строкой
`ld/memory.ld:68: syntax error`, то есть без него `firmware.elf` не собирается.

Обратная сторона того же механизма: PlatformIO вешает зависимость
`firmware.elf` от линкер-скрипта только когда генерирует его сам. Наш файл в
зависимостях не числится, поэтому правка `ld/memory.ld` сама по себе ничего не
пересобирает - нужен `pio run -t clean` или удаление `firmware.elf`.

#### Что в файле

Семь областей в `MEMORY`, символы (`_diram_i_start`, `_heap_start`,
`_heap_end`), четыре `REGION_ALIAS` - их ждёт `sections.ld`, который обращается
к роли области, а не к её имени - и пять `ASSERT`-самопроверок.

| Область | Адрес | Размер | Что |
|---|---|---|---|
| `iram0_0_seg` | `0x40374000` | `0x57700` | код без кэша, векторы, аварийный стек |
| `iram0_2_seg` | `0x42000020` | `0x7FFFE0` | код во flash |
| `dram0_0_seg` | `0x3FC88000` | `0x53700` | `.data`, `.bss`, стеки |
| `drom0_0_seg` | `0x3C000020` | `0x1FFFFE0` | постоянные данные во flash |
| `rtc_iram_seg` | `0x600FE000` | `0x1FE8` | RTC-память минус 24 байта |
| `rtc_reserved_seg` | `0x600FFFE8` | `24` | счётчик RTC-таймера IDF |
| `rtc_slow_seg` | `0x50000000` | `0x2000` | медленная RTC-память |

Откуда числа - в `docs/board-cardputer.md`, раздел «Память и разделы». Коротко: начало
IRAM сдвинуто на `0x4000` (кэш инструкций), общий блок кода и данных -
`0x53700`, потому что IRAM и DRAM это одна физическая память с двух сторон
(`0x40378000` и `0x3FC88000` - один и тот же байт).

#### Почему `sections.ld` остался чужим

В нём 1089 строк: какая секция какого компонента IDF куда кладётся. Переписать
его - значит заодно взять на себя ожидания кода, который мы всё ещё используем:
инициализацию кучи, `_bss_start`, newlib, раскладку кэша. Своя карта памяти
отвечает на вопрос «где физически память», `sections.ld` - на вопрос «что в неё
кладём»; первый ответ нам нужен свой уже сейчас, второй - только вместе с
отказом от старта IDF (`call_start_cpu0`). Это отдельная работа, и она не про
линкер.

#### Грабли

| Симптом | Причина | Решение |
|---|---|---|
| `undefined symbol` на `#define`-имена, `invalid origin for memory region` | файл не проходит препроцессор C: PlatformIO отдаёт его линкеру как есть, а `#` в ld - начало комментария | числа задавать символами ld: `NAME = 0x40378000;` вне `SECTIONS`, их видно в `MEMORY` |
| правка `ld/memory.ld` ничего не пересобирает | PlatformIO вешает зависимость `firmware.elf` от линкер-скрипта только для своего сгенерированного файла | после правки удалить `.pio/build/<env>/firmware.elf` или `pio run -t clean` |
| `ASSERT` проходит при заведомо испорченном числе | сравнивали с тем же символом, из которого считаются размеры: `ASSERT(… == SRAM_END)` верно всегда | сравнивать с литералом: `ASSERT(ORIGIN(iram0_0_seg) == 0x40374000, …)` |

Третий пункт - из этой же работы: первая версия самопроверок была тавтологией
и не поймала подменённую верхнюю границу. Поймала только после замены на
литералы.

#### Что видно в логе

Ничего не сдвинулось - это и есть признак успеха. Символы в образе те же, что
были с линкером IDF: `basalt_vectors 0x40375400`, `_heap_start 0x3fc97ee0`,
`_heap_end 0x40000000`, `_diram_i_start 0x40378000`. В баннере добавилась одна
строка:

```
[ld] своя карта памяти: ld/memory.ld, числа проверены при сборке
```

`env:bare` тикает, `env:bare-panic` падает как раньше: слот 9, причина 6,
полный отчёт, `rst:0x3 (RTC_SW_SYS_RST)`. Остальные env (`console`, `hello`,
`bringup`) собираются.

#### Как проверить самому

```bash
pio run -e bare -t upload && ./tools/serial-read.sh 10
```

**Признак успеха:** строка `[ld]` в баннере и тики. Самопроверки проверяются
порчей числа в `ld/memory.ld` - сборка должна упасть с сообщением на русском:

```
SRAM_END = 0x403CB800;      /* вместо 0x403CB700 */
rm -f .pio/build/bare/firmware.elf && pio run -e bare
→ iram0_0_seg кончается не там, где кончается статическая IRAM (0x403CB700).
```

### 21.10.2026. Тесты и CI: три уровня проверки, у каждого своя цена

**Файлы:** `platformio.ini`, `test/test_format/*`, `tools/check-image.sh`,
`tools/smoke.sh`, `tools/reset.sh`, `tools/serial-read.py`, `Makefile`,
`.github/workflows/build.yml`, `ld/memory.ld`

**Зачем именно сейчас.** С A0 закончился «металл»: код перестал быть
одноразовым щупом. Дальше идут вещи, где ошибка не видна глазом, — парсер
строки, FAT32, планировщик. Проверять их заливкой на плату и чтением лога
дорого: цикл «правка → прошивка → лог» занимает минуты, а ошибку в разборе
имени файла так и не увидишь, пока не дойдёшь до неё руками.

Отсюда три уровня, а не один. Уровень выбирается по вопросу, на который надо
ответить, а не по привычке.

#### Уровень 1: тесты на маке

`pio test -e native` — новый env на `platform = native`, тест-фреймворк Unity,
файлы в `test/`. Проверяется код, которому не нужны регистры.

Первый подопытный — `arch/xtensa/format.c`: вывод чисел в консоль. Выбор не
случаен: этот код работает во время паники, то есть тогда, когда всё уже
сломалось и повторить опыт дорого. Крайние значения (ноль, `UINT64_MAX`,
младший разряд hex, усечение миллисекунд) — ровно те места, где самодельное
форматирование обычно и ошибается.

Подмена железа — заглушка в каталоге теста:
`test/test_format/console_stub.c` реализует `basalt_console_write` в буфер.
Тест видит ровно тот текст, который ушёл бы в терминал, а не «результат
преобразования в вакууме».

**Шестнадцать проверок, все проходят.** Проверено, что они действительно
ловят: подменённое `'0'` на `'a'` в `format.c` дало 7 провалов, возврат файла
— снова 16 из 16.

#### Уровень 2: проверка образа без платы

`./tools/check-image.sh` читает таблицу символов собранного `firmware.elf` и
сверяет то, чего компилятор не видит:

| Что проверяется | Почему это может сломаться молча |
|---|---|
| `basalt_memory_map_version` есть в образе | связали чужим `memory.ld` — и не заметили |
| `basalt_vectors` внутри IRAM | таблица уехала в DRAM: `VECBASE` её примет, но исполнять оттуда нельзя |
| `basalt_vectors` на границе 1 КБ | `VECBASE` младшие 10 бит не хранит: таблица тихо съедет на начало блока |
| `_heap_start` внутри DRAM | куча начинается в чужой области — порча памяти при первом же `malloc` |
| `_diram_i_start = 0x40378000` | сдвинулось схождение IRAM и DRAM — разъедутся размеры областей |

Для первой проверки в `ld/memory.ld` появился символ-отметка
`basalt_memory_map_version = 1;`. Он не нужен ни коду, ни плате: это подпись
«образ связан этой картой». Проверено на чужом образе (`env:console`) —
скрипт честно ругается и возвращает 1.

#### Уровень 3: смоук на живой плате

`./tools/smoke.sh <env>` заливает прошивку, читает лог и сверяет строки из
«признака успеха» в этом же журнале. Строки заданы в скрипте, поэтому признак
успеха теперь в двух местах — но иначе нельзя: журнал читает человек, а
скрипт должен знать, что искать.

**Побочная находка, которая стоила замены `tools/serial-read.py`.** Первый
прогон смоука упал на `OSError: [Errno 6] Device not configured`. Причина:
открытие порта перезапускает чип, USB-устройство на это время исчезает, и
уже открытый дескриптор умирает. Старый скрипт падал ровно в этот момент —
то есть до того, как в логе появится хоть строка. Теперь порт переоткрывается
сам, пока не выйдет время чтения, и в конце печатает число переоткрытий.
Это была не ошибка смоука, а старая ошибка прибора, которую он вскрыл.

#### Смоук вскрыл ещё одну вещь про плату

`env:hello` из смоука пришлось убрать. После его заливки лог пуст и `esptool`
не подключается вообще — ни с `--before default-reset`, ни с `usb-reset`.
Предположительно приложение заняло USB Serial/JTAG и не отдаёт его обратно,
либо зависло до первой печати. Плата при этом жива: порт `303A:1001` на месте,
заливка проходит с проверкой хеша.

Заодно выяснилось, почему после ручного G0 прошивка «не запускается»: `esptool`
сбрасывает чип через RTS, а на Cardputer RTS к выводу сброса не подключён.
Сброс, который действительно работает, — через USB-JTAG:
`esptool --before usb-reset --after no-reset read-mac`. Обе вещи записаны в
`docs/board-cardputer.md` §9 и §12, а `tools/smoke.sh` теперь сам распознаёт
`waiting for download` в логе и делает этот сброс без участия человека.

#### Где всё это запускается: CI

`.github/workflows/build.yml`, две задачи:

- **tests** — `pio test -e native`. Быстро, без платформы ESP32.
- **firmware** — сборка всех пяти env и `check-image.sh`. `all envs`, а не
  `default_envs`: сломанный env, который собирается только вручную, узнаёт об
  этом через неделю.

Кэш по `hashFiles('platformio.ini')`: меняются платформы или библиотеки —
кэш пересобирается, иначе тянем заново около гигабайта пакетов. Версия
PlatformIO зафиксирована числом, чтобы сборка зависела от кода, а не от того,
что вышло на PyPI вчера.

#### Чистая сборка: чем она оказалась полезна

Чтобы не узнать о проблеме на первом же push, сборка `env:bare` была прогнана в
пустом `PLATFORMIO_CORE_DIR` — то есть так, как её увидит раннер: без моих
локальных пакетов.

**Первый вывод: проект тут не виноват, виноват питон.** Установка
`framework-espidf` создаёт питоновское окружение IDF и падает:

```
error: the configured Python interpreter version (3.15) is newer than PyO3's
       maximum supported version (3.14)
ERROR: Failed building wheel for pydantic-core
ModuleNotFoundError: No module named 'idf_component_manager'
```

Цепочка такая: `requirements.core.txt` из IDF → `pydantic 2.12.5` →
ровно `pydantic-core==2.41.5`. Готовые колёса для неё есть под 3.12 и 3.14, а
под 3.15 нет, поэтому pip лезет собирать из исходников, а Rust-обвязка PyO3
3.15 ещё не поддерживает. Проверено запросом колёс с явными `--python-version`.

**Второй вывод: локальное окружение держится на честном слове.** Здесь
PlatformIO стоит на Homebrew `python@3.15`, и сборка работает только потому,
что окружение IDF было создано раньше, когда пины в IDF были другие. Стоит
почистить `~/.platformio` — и `env:bare` перестанет собираться, а сообщение
будет про `idf_component_manager`, то есть про что угодно, кроме настоящей
причины. Записано в `AGENTS.md` раздел 3 вместе с лечением: PlatformIO на
Python ≤ 3.14.

**Третий вывод, приятный: CI на этом не спотыкается.** На `ubuntu-24.04` с
`python-version: 3.12` нужное колесо есть, и версия питона в workflow
зафиксирована числом именно поэтому, а не «чтобы было аккуратно».

**Четвёртый вывод: сборка воспроизводится.** Повторный прогон на Python 3.14
(`~/.asdf/installs/python/3.14.2`) в пустом каталоге собрал `env:bare` за 47
секунд, и образ вышел в точности тем же: `basalt_vectors 0x40375400`,
`_heap_start 0x3fc97ee0`, `check-image.sh` — пять «ok». То есть сборка зависит
от кода и версий, а не от того, что лежало в моём `~/.platformio`.

**Пятый, уже местный: чистый каталог нельзя держать в `/tmp`.** С
`PLATFORMIO_CORE_DIR=/tmp/pio-clean` сборка падает на шаге линкер-скрипта с
`*** [/Users/tmp] /Users/tmp: Permission denied`. Трассировка показала, что
SCons пытается создать `/Users/tmp/pio-clean/packages/...`, то есть склеивает
путь с потерей первого уровня — `tmp` принимается за домашний каталог. С
каталогом в `~/` та же сборка проходит. На CI этого не бывает: там всё лежит
под `/home/runner`. Записано в `AGENTS.md` §7, чтобы не искать заново.

**Чего в CI нет и почему.** Проверок на живой плате. Тики, `VECBASE` и отчёт
паники видны только в логе с платы; раннера с Cardputer нет. Делать вид, что
CI что-то проверил на железе, — хуже, чем не проверять вовсе.

**Первый прогон на GitHub прошёл зелёным.** Обе задачи, `tests` и `firmware`,
с первого раза и без правок workflow, то есть вывод про `pydantic-core` и
`python-version: 3.12` подтвердился не рассуждением, а раннером. Бейдж добавлен
в `README.md`; он же служит ответом на вопрос «а у вас собирается?» без
пересказа.

**Честная оговорка про цену.** Первый прогон без кэша тянет тулчейн и IDF —
это десятки минут и около гигабайта. Кэш по `hashFiles('platformio.ini')`
снимает это со второго раза, но правка `platformio.ini` снова делает прогон
долгим. Это нормально: долгий прогон после смены платформы лучше, чем
необнаруженная поломка.

#### Грабли (все пройдены лично)

| Симптом | Причина | Решение |
|---|---|---|
| `Unknown board ID 'esp32-s3-devkitc-1'` в native | секция `[env]` достаётся **всем** env'ам, включая тестовый | общие настройки прошивок вынести в `[base]`, env'ы подключают через `extends` |
| `BoardConfig: Board is not defined` | попытка погасить доску строкой `board =` | убрать `board` вообще: без `extends = base` он и не появится |
| `undefined reference to basalt_put` в тесте | тестовая сборка по умолчанию берёт только `test/`, без `src/` | `test_build_src = yes` |
| `src_dir` в `[env:native]` — «unknown configuration option» | это опция `[platformio]`, а не env | `test_build_src = yes` + `build_src_filter = +<../файл>` |
| файл из `arch/` не попадает в тестовую сборку | `build_src_filter` считается от `src/` | путь с `../`: `+<../arch/xtensa/format.c>` |
| после заливки `env:hello` лог пуст, `esptool` не подключается | предположительно приложение заняло USB Serial/JTAG и не отдаёт | G0 при включении, затем `esptool --before usb-reset` (см. `board-cardputer.md` §12) |
| прошивка залита, а плата пишет `waiting for download` после каждого сброса | чип попал в загрузчик вручную и `esptool` сбрасывает через RTS, а RTS на Cardputer к сбросу не подключён | `esptool --before usb-reset --after no-reset read-mac` — запускает прошивку без кнопок |
| `clangd` не находит `tick.h` и `format.h` | `compiledb` собирает базу под один env, и последняя была от Arduino-сборки | `pio run -e bare -t compiledb` |

#### Как проверить самому

Проверки собраны в `Makefile`, чтобы не помнить env у каждой: `make help`
печатает список. Логики в нём нет, он только называет команды — `pio` и
скрипты остаются доступны напрямую.

```bash
make verify                 # то же, что CI: тесты, все env, проверка образа

pio test -e native          # 16 из 16, около секунды
pio run -e bare && ./tools/check-image.sh
./tools/smoke.sh            # плата в порту, около 25 секунд
./tools/smoke.sh bare-panic # то же для паники, около 30 секунд
```

`make verify` — это ровно то, что сделает CI после push, поэтому его удобно
прогнать до коммита: разница между «у меня собралось» и «собирается везде».

**Признак успеха:** тест печатает `16 succeeded` и возвращает 0;
`check-image.sh` — пять строк `ok` и «образ соответствует карте памяти»;
`smoke.sh` — `smoke прошёл` и файл лога в `/tmp`.

**Что осталось за кадром.** Тесты пока покрывают один файл — тот, что уже
написан и переносим. Настоящая польза начнётся на A3 (парсер шелла) и A4
(FAT32), где логика большая и без платы проверяется целиком. Добавлять тесты
к драйверам смысла нет: они проверяются только на железе.

### 21.10.2026. Сторожевой таймер загрузчика: плата перезагружалась каждые 9 секунд

**Файлы:** `arch/xtensa/start.c`, `tools/smoke.sh`

**Как это выглядело.** Плата работает, светодиод мигает раз в секунду — и
примерно на седьмой вспышке перезагружается. И так по кругу. В логе при этом
каждый раз:

```
rst:0x15 (USB_UART_CHIP_RESET),boot:0x2b (SPI_FAST_FLASH_BOOT)
Saved PC:0x4200165b
```

Строка `rst:0x15` означает «сброс сделал USB», и это **неправда**. Полвечера
поиск шёл в USB: проверялось, не дёргает ли линии сам скрипт чтения, не
переполняется ли FIFO консоли, не сбивает ли что-то светодиод через RMT.

**Что помогло найти причину.** Не догадка, а три опыта подряд:

| Опыт | Результат | Вывод |
|---|---|---|
| Arduino-прошивка `env:console` на 40 секунд | 39 тиков, ни одной перезагрузки | дело не в плате, не в кабеле и не в хосте |
| Прошивка-пустышка: только `for (;;)`, без консоли и светодиода | всё равно перезагружается | дело не в коде приложения |
| Отключить сторожевой таймер RTC по регистрам | 30 секунд, ни одной перезагрузки | он и есть причина |

Плюс совпадение числа: в `sdkconfig.bare` стоит
`CONFIG_BOOTLOADER_WDT_TIME_MS=9000`, а перезагрузка приходила на девятой
секунде. Именно загрузчик включает этот таймер и рассчитывает, что дальше его
либо выключит `esp_system`, либо будет кормить планировщик.

**Почему у нас он не выключался.** У `env:bare` свой старт: `esp_system` не
запускается, FreeRTOS не запускается, планировщика нет. Кормить таймер некому,
и через девять секунд он делает то, для чего сделан, — перезагружает чип.
Обычная прошивка этого не замечает, потому что за неё это делает IDF.

**Лечение.** В `start_cpu0`, самым первым действием своего кода:

```c
WRITE_PERI_REG(RTC_CNTL_WDTWPROTECT_REG, 0x50D83AA1u);  // снять защиту
CLEAR_PERI_REG_MASK(RTC_CNTL_WDTCONFIG0_REG, RTC_CNTL_WDT_EN);
WRITE_PERI_REG(RTC_CNTL_WDTWPROTECT_REG, 0);
```

Правка одной строки в `sdkconfig.defaults`
(`CONFIG_BOOTLOADER_WDT_ENABLE=n`) эффекта не дала: загрузчик с новым конфигом
не пересобрался, и объяснять это будущему читателю было бы дороже, чем
выключить таймер там, где нам действительно нужно, — в своём старте.
Предположительно помог бы `rm -f .pio/build/bare/bootloader.bin`.

**Урок про проверки, и он неприятный.** `smoke.sh` в это время печатал «smoke
прошёл»: он читал лог 12 секунд и искал `tick 1`, а прошивка успевала прожить
7 тиков и перезагрузиться — то есть проверка проходила **на сломанной
прошивке**. Смоук, который смотрит только начало лога, не отличает «работает»
от «падает и перезапускается».

Теперь `bare` читается 26 секунд и обязан дойти до `tick 20`. Проверено, что
это ловит регрессию: с закомментированным выключением таймера смоук печатает
`smoke не прошёл` и возвращает 1, с исправлением — 0.

#### Как проверить самому

```bash
./tools/smoke.sh bare    # около 40 секунд: заливка и 26 секунд чтения
```

**Признак успеха:** строки `tick 1` и `tick 20`, `smoke прошёл`. Если в логе
есть несколько `basalt-os boot` или `rst:0x`, прошивка перезагружается.

## Итог на 21.10.2026

**Веха A0 закрыта.** Своё: точка входа (свой стек, свой `basalt_main`,
FreeRTOS не запускается), консоль, время, светодиод, обработчик исключений,
**таблица векторов** и **карта памяти** (`ld/memory.ld`). Чужое осталось одно:
`call_start_cpu0` (кэш, MMU, BSS) и каталог секций `sections.ld` - оба уходят
только вместе с отказом от старта IDF.

**Почему таблица всё-таки вышла без своего линкера.** Прошлый вывод был
неверным: дело не в линкере, а в разделе - `.iram1.basalt_vectors` линкер
выравнивает сам, не ломая остальной IRAM. Проверено на живой плате: таблица на
`0x40375400`, `VECBASE` переключён и прочитан обратно, сбои ловит наш код.

**Главный урок вехи** - про окна регистров. Таблица из шестнадцати слотов, у
которой заполнены четырнадцать, работает не «на 87 %», а ноль: первое же
переполнение окна уходит в мусор, и плата молча висит. Оконный ABI - не деталь
реализации компилятора, а часть машины, которую надо обслуживать с первого дня.

**Второй урок** - про `EXCM`: обработчик исключения не может просто «вызвать
функцию на C». Нужно снять `EXCM`, освободить окна и позвать через `call4`.
Три попытки подряд упирались именно в это.

**Что это даёт на практике.** Сбой теперь объясняется по-русски: причина
словами, слот словами, адрес инструкции, адрес обращения, состояние прерываний
и все 16 регистров; плюс красный светодиод, если терминала рядом нет, и
предсказуемый сброс через `RTC_CNTL_SW_SYS_RST` вместо цикла перезагрузок.

**Чем закрыта A0.** Своим `ld/memory.ld`: карта памяти теперь описана в
репозитории явными числами, с объяснением откуда они, и проверяется пятью
`ASSERT` при линковке. Порча числа останавливает сборку, а не плату.

**Что специально оставлено чужим.** `call_start_cpu0` (кэш, MMU, обнуление BSS)
и `sections.ld` - каталог секций компонентов IDF. Оба уходят вместе: пока
работает чужой старт, он ждёт свою раскладку памяти, и переписывать каталог
секций в одиночку - только риск.

**Чем проверяется.** Три уровня, каждый отвечает на свой вопрос: тесты на маке
(`pio test -e native`, 16 проверок форматирования), проверка собранного образа
по символам (`tools/check-image.sh` — карта своя, векторы выровнены, куча в
DRAM) и смоук на живой плате (`tools/smoke.sh` — сверяет строки лога). Первые
два гоняются в CI на каждый push; третий остаётся ручным, потому что платы на
раннере нет.

**Что тесты дали сразу.** Старую ошибку прибора: `tools/serial-read.py` падал
на `Device not configured`, когда чип перезапускался от открытия порта, — то
есть лог не читался вообще. Глазами это выглядело как «плата молчит».

### 05.11.2026. Переезд на T-Display-S3 и разделение проектов

**Что решили и почему.** Дальше писать ОС на Cardputer стало слишком дорого:
у платы нет PSRAM, и весь проект был построен вокруг этого — полоса рендера
в одну строку вместо кадрового буфера, mruby/c вместо mruby, 8 МБ flash
вместо шестнадцати. Каждая веха упиралась не в задачу, а в потолок.

Плата выбиралась по одному признаку: **сколько нового кода нужно, чтобы моя
система напечатала первую строку** — то есть сколько будет стоить отладка
вслепую. Из того, что было под рукой:

| Плата | Почему да или нет |
|---|---|
| **T-Display-S3** (ESP32-S3R8, 8 МБ PSRAM) | **выбрана**: тот же чип, что у Cardputer, значит весь `arch/` переезжает; 8 МБ PSRAM; 16 МБ flash; USB-C нативный; распиновка официальная |
| TTGO T-Display (ESP32 LX6) | экран и кнопки, но это другой чип: `arch/` пришлось бы переписывать целиком. Идеальный **второй** target позже |
| ESP32 + OLED + 18650 | корпус хорош, но распиновка неизвестна — самая дорогая категория платы |
| ESP32-CAM | нет USB вообще, камера на 12 пинов DVP — не для ОС |
| ESP32 Type-C CH340C | экрана нет; остаётся как надёжный консольный стенд |

**Что дал переезд на практике.** Это была проверка главной гипотезы проекта:
«`arch/` живёт на уровне чипа, а не платы». Она сошлась.

- `arch/xtensa` (старт, векторы, консоль, тик, паника) — **без правок**.
- `ld/memory.ld` — **без правок**, проверка образа дала те же адреса:
  векторы `0x40375400`, куча `0x3fc97ed0`, `_diram_i_start = 0x40378000`.
- Тулчейн, `.clangd`, `espressif32@8.0.0`, все скрипты `tools/` — без правок.
- В `platformio.ini` плата определяется готовым board-файлом
  `lilygo-t-display-s3` (16 МБ flash, `memory_type: qio_opi`), то есть даже
  PSRAM включается без ручной правки `sdkconfig`.

Переехало не всё: у T-Display-S3 нет WS2812, поэтому индикатор жизни стал
интерфейсом.

**Почему интерфейс, а не `#ifdef`.** Различие между платами ровно одно — чем
сигналить «система жива». Если бы это решалось `#ifdef` в коде, `arch/` начал
бы знать про обе платы сразу, а он не должен. Поэтому:

```
arch/xtensa/include/indicator.h      basalt_indicator_init/set/ready/name
arch/xtensa/indicator_ws2812.c       Cardputer: WS2812 через RMT
arch/xtensa/indicator_backlight.c    T-Display-S3: подсветка экрана
src/CMakeLists.txt                   выбирает один из двух по флагу сборки
```

Побочная выгода: в лог попала строка `[indicator] <описание>` — теперь лог
описывает ту плату, которая реально собрана, а не ту, что была вчера.

**Тот же приём с пинами.** `include/board_pins.h` переехал в
`boards/<плата>/board_pins.h`, путь подставляется сборкой (`-Iboards/…` и
`INCLUDE_DIRS` в `src/CMakeLists.txt`). Это ровно то, что записано в правилах
«пины платы — в одном файле», и теперь это ещё и физически один файл на плату.

**Что стало не нужно на новой плате.** Матричная клавиатура через 74HC138 и
слой `Fn` (ввод идёт с мака по USB, две кнопки закрывают `Ctrl-C` и `Esc`),
звук (динамика и микрофона нет), ИК-передатчик. Освободившиеся вехи заняты
тем, чего Cardputer не мог: A9 — файловая система в 15 МБ неиспользуемого
flash, A11 — полный mruby, A12 — `fb`-устройство в PSRAM.

**Что за цену.** Экран этой платы висит не на SPI, а на 8-битной
параллельной шине (i80/`LCD_CAM`). Свой драйвер i80 стоит дороже, чем весь
остальной `arch/`, а учит меньше, поэтому **решено брать `esp_lcd`**, но
держать свой интерфейс `drivers/lcd.h`: замена реализации не потребует правок
ни в одном вызывающем файле. Это тот же принцип, что записан для Tab5
(«bring-up берём из BSP и явно помечаем»), и то же исключение из правила
«пишем всё сами».

**Грабли, на которые наступили сразу.** PlatformIO на этой машине стоит на
Python 3.15, и при сборке он пересоздал окружение IDF, а собрать в него
`idf_component_manager` не смог: под 3.15 нет готового колеса
`pydantic-core==2.41.5`. Симптом обманчивый — CMake падает на `project()`, и
выглядит так, будто виноват `platformio.ini` или моя правка. Лечится вторым
PlatformIO на Python 3.14 (`~/.venvs/pio314`); подробности — в `AGENTS.md`,
раздел 3.

**Как проверить.** Плата в порту:

```bash
make smoke ENV=tdisplay        # заливка + 26 секунд лога: ready, tick 20
make smoke ENV=tdisplay-panic  # падение на 5-й секунде и отчёт
```

Признак успеха: `tick 1`, `tick 20`, `smoke прошёл`, и раз в секунду
включается подсветка экрана. Если экран остаётся чёрным — это **ожидаемо**:
драйвера экрана ещё нет, A1 впереди. Индикатор работает потому, что подсветка
это отдельный пин, а не сам экран.

**Что осталось на потом.** Первым делом на живой плате — проверить, что PSRAM
действительно есть и её 8 МБ (`env:probe`): у части партий она отсутствует,
и тогда бюджет памяти считается заново. Затем дамп оригинальной прошивки
16 МБ — до первой своей.

## Разделение проектов на 05.11.2026

Решения, которые касаются не кода этого репозитория, а того, что вокруг него.

| Проект | Решение | Причина |
|---|---|---|
| **basalt-os-mini** (этот) | остаётся ОС с нуля, переезжает на T-Display-S3 | свой кернел — то, ради чего проект существует; новая плата снимает потолок памяти |
| **capsh** (новый, Cardputer) | «прошивка с периферией», linux-like, **без своего ядра** | периферия Cardputer уже изучена; готовая прошивка полезна сама по себе и стоит дешевле, чем ядро |
| **basalt-os** (Tab5) | **на паузе** | плата заказана, код не начат; решение «своё ядро или готовое» не принято |
| **idDOS** | читать как пример функциональности, код не копировать | лицензия PolyForm Noncommercial 1.0.0: идеи и структуру брать можно, файлы — нет |

**Чем `capsh` отличается от этого репозитория.** Там нет `arch/`, нет
планировщика, нет таблицы syscalls — вместо ядра Arduino core и M5Unified.
Зато есть `vfs/`, `tty/`, `shell/`, `apps/`, и они пишутся так, чтобы не
знать про Arduino: только `bsp/` имеет право подключать `Arduino.h`. Это
делает код переносимым сюда, в `basalt-os-mini`, если однажды понадобится.

**Что это значит для правил.** В `capsh` нельзя протаскивать «настоящую ОС»
(MMU, вытеснение, syscalls) — иначе он превратится в третий незакрытый
проект. Обратное тоже верно: сюда нельзя тащить Arduino и M5Unified. Граница
проходит по вопросу «есть ли здесь своё ядро», и она записана в `AGENTS.md`
обоих проектов.

### 06.11.2026. Щуп `env:probe`: PSRAM есть, а кучи нет

**Файлы:** `src/probe/main.c`, `src/CMakeLists.txt`, `platformio.ini`,
`sdkconfig.defaults`, `Makefile`, `.github/workflows/build.yml`, документация.

**Прошивки:** `env:probe` на живой плате; `make verify` — восемь env зелёные,
16 хостовых тестов проходят.

**Задача.** До первой строчки драйвера экрана надо было ответить на вопрос, от
которого зависит вся веха A1: PSRAM на этом экземпляре есть, её правда 8 МБ, и
кадровый буфер 108.8 КБ ложится в неё одним куском? У части партий
T-Display-S3 PSRAM отсутствует, и тогда рисовать пришлось бы полосой в одну
строку, как на Cardputer, — то есть писать другой драйвер.

#### Почему отдельный env, а не флаг в `env:tdisplay`

Замер — это не работа системы, а вопрос к железу: его хочется повторить на
новой плате и после каждой смены `sdkconfig`, а не «когда вспомнят». Поэтому
`env:probe` — своя прошивка с тем же `arch/`, той же консолью и тем же тиком,
но другим `main.c`. Выбор приложения идёт CMake-переменной
`BASALT_APP_PROBE` (так же, как `BASALT_BOARD_TDISPLAY`), а не `#ifdef` в
коде: список файлов решается до компиляции, и второй копии `arch/` не
появляется.

#### Почему PSRAM включается в `sdkconfig.defaults`

`board`-файл PlatformIO описывает flash и режим загрузки, а PSRAM — это конфиг
IDF. До 06.11.2026 `CONFIG_SPIRAM` не был задан вообще: 8 МБ существовали в
даташите и были недоступны из кода (`SPIRAM = False` в
`.pio/build/tdisplay/config/sdkconfig.json`).

Отдельного `sdkconfig` для tdisplay нет вынужденно: PlatformIO 6.2 читает
только `sdkconfig.defaults`, а разделитель списка `;` в `platformio.ini` —
начало комментария, поэтому `-DSDKCONFIG_DEFAULTS=файл1;файл2` не выразить.
Значит файл один на обе платы, и `CONFIG_SPIRAM_IGNORE_NOTFOUND=y` тут не
роскошь: у Cardputer (`env:bare`, `bare-panic`) PSRAM физически нет, и без
этого флага `esp_psram_chip_init()` на её старте делает `abort()` — плата
просто не поднимается. С флагом она пишет в лог «Failed to init external RAM»
и работает дальше, как раньше. Когда `env:bare` уедет в `capsh` вместе с
платой, флаг надо убрать: честнее падать, если PSRAM не нашлась.

#### Первый запуск: «PSRAM есть» и «кучи нет» одновременно

```
[probe] чип: ESP32-S3, ревизия v0.2, ядер 2
[probe] flash: размер не прочитался
[probe] PSRAM: 8 МБ (8388608 Б), режим OCT (8 линий), 80 МГц
[probe] heap SRAM: нет
[probe] heap DMA: нет
[probe] heap PSRAM: нет
[probe] кадровый буфер 320x170x2 = 108800 Б: в PSRAM не выделился
[probe] вывод: полного кадра в PSRAM нет - рисовать полосой в одну строку
```

Две строки противоречили друг другу. Причина не в железе и не в PSRAM, а в
своём старте.

**Что происходит на самом деле.** В IDF `call_start_cpu0` делает минимум —
кэш, MMU, MSPI, и в том числе физически поднимает PSRAM, — а дальше зовёт
`start_cpu0`, которую мы перекрыли своей. Штатная `start_cpu0_default` перед
запуском приложения вызывает `do_core_init()`, а это перечень
`ESP_SYSTEM_INIT_FN` — функций инициализации компонентов. В нём, по
приоритетам:

| Приоритет | Что | Без него |
|---|---|---|
| 100 | `heap_caps_init()` | ни одной кучи, `malloc` не работает |
| 103 | `esp_psram_extram_add_to_heap_allocator()` | PSRAM размечена, но в кучу не добавлена |
| 130 | `esp_flash_init_default_chip()` | `esp_flash_get_size(NULL)` возвращает ошибку |

A0 этого не замечала: там всё на статических буферах, `heap_caps` никто не
звал. Кадровый буфер — первое место, где нужен аллокатор, и он оказался пуст.
Хорошая новость: маппинг PSRAM (`esp_psram_init()`) выполняется раньше, внутри
`mspi_init()`, поэтому `esp_psram_is_initialized()` и размер были верными с
самого начала.

#### Что сделали

Щуп заводит кучу сам — теми же двумя вызовами и в том же порядке, что IDF:

```c
heap_caps_init();
esp_psram_extram_add_to_heap_allocator();
```

Второй вызов живёт в приватном заголовке (`esp_private/esp_psram_extram.h`):
публичного способа добавить PSRAM в кучу нет, `esp_psram_init()` этого не
делает — он только размечает и отображает память. Это осознанный компромисс:
заголовок приватный, зато поведение ровно то же, что у IDF, и цифры щупа
сравнимы с тем, что будет в системе.

Размер flash взят из `g_rom_flashchip.chip_size`, а не из драйвера: драйвер
живёт в том же пропущенном `do_core_init()` (приоритет 130), а значение
заполняет загрузчик — в его логе видна та же цифра, два источника сходятся.

#### Цифры с платы

```
[probe] чип: ESP32-S3, ревизия v0.2, ядер 2
[probe] flash: 16 МБ (16777216 Б), по данным ROM
[probe] PSRAM: 8 МБ (8388608 Б), режим OCT (8 линий), 80 МГц
[probe] куча: heap_caps_init выполнен, PSRAM в куче есть
[probe] heap SRAM: всего 358 КБ, свободно 355 КБ, крупнейший блок 312 КБ
[probe] heap DMA: всего 351 КБ, свободно 348 КБ, крупнейший блок 312 КБ
[probe] heap PSRAM: всего 8192 КБ, свободно 8189 КБ, крупнейший блок 8064 КБ
[probe] кадровый буфер 320x170x2 = 108800 Б: адрес 0x3c030900, выравнивание 64 Б ok
[probe] заливка 2840 мкс, сверка 12766 мкс, расхождений 0
[probe] вывод: полный кадр в PSRAM помещается, A1 можно строить на кадровом буфере
ready
```

Про PSRAM из лога загрузчика: производитель `0x0d` (AP), density `0x03`
(64 Мбит), `good-die` пройден, 80 МГц. То есть чип не «похоже, есть», а
опознан.

Заливка 108.8 КБ за 2 840 мкс — это ≈38 МБ/с записи в PSRAM через кэш. Полный
кадр на 60 Гц — 6.5 МБ/с, запас есть. Сверка дольше (12 766 мкс) потому, что
читает побайтово через `volatile`, а не `memcmp`; для оценки скорости чтения
эта цифра не годится и в документацию как замер не пошла.

#### Что это значит для A1

1. **Кадровый буфер — можно.** Полоса в одну строку больше не обязательна.
2. **Кучу надо завести в самой ОС.** Место вызова — вопрос A1, а не щупа.
   Очевидное: `arch/xtensa/start.c`, рядом с остальными вызовами IDF, до
   любого драйвера. Решение касается всех env сразу, поэтому принимается
   осознанно, а не «добавим в main первого приложения».
3. **Адреса в образе сдвинулись.** Включение PSRAM добавило драйвер
   `esp_psram` в IRAM: прошивка +10.5 КБ (168 113 → 178 645 Б), векторы
   `0x40375400` → `0x40375800`, начало кучи `0x3fc97ed0` → `0x3fc99b00`.
   `tools/check-image.sh` это пережил: он проверяет выравнивание и попадание
   в область, а не конкретные числа, — ровно поэтому так и написан.

#### Грабли (все пройдены лично)

| Симптом | Причина | Решение |
|---|---|---|
| правка `sdkconfig.defaults` не подействовала: `SPIRAM = False` в сборке | PlatformIO держит рядом готовый `sdkconfig.<env>` и копирует defaults только если он старше | удалить `sdkconfig.<env>` (он в `.gitignore`) и пересобрать |
| `-DSDKCONFIG_DEFAULTS=файл1;файл2` не задаётся | `;` в `platformio.ini` — начало комментария | один общий файл + `IGNORE_NOTFOUND`, см. выше |
| `esp_flash_get_size(NULL)` возвращает ошибку | драйвер flash инициализируется в `do_core_init()`, которого при своём старте нет | брать размер из ROM или инициализировать драйвер самому |
| `heap_caps_*` возвращает 0, `heap_caps_aligned_alloc` — `NULL` | то же: `heap_caps_init()` не вызывался ни разу за всю историю проекта | завести кучу до первого `heap_caps_*` |

#### Проверка

```bash
make probe PIO=~/.venvs/pio314/bin/pio   # залить и прочитать замеры
make verify PIO=~/.venvs/pio314/bin/pio  # восемь env + проверка образов
pio test -e native                       # 16 тестов на маке
```

Признак успеха — строка `[probe] вывод: полный кадр в PSRAM помещается` и
`tick` в логе после неё. Если вместо этого `heap SRAM: нет` — значит кучу
опять никто не завёл.

### 06.11.2026. Куча переезжает в ОС: крэш на стеке загрузчика

**Файлы:** `arch/xtensa/heap.c` (новый), `arch/xtensa/include/heap.h` (новый),
`arch/xtensa/start.c`, `arch/xtensa/start.S`, `src/CMakeLists.txt`,
`src/probe/main.c`, документация.

**Прошивки:** `env:probe` на живой плате (дважды — падение и успех),
`make verify` — восемь env зелёные, проверка образов `tdisplay` и `bare` ok,
16 хостовых тестов проходят.

**Задача.** Предыдущая запись кончилась тем, что щуп заводит кучу сам, а в
`env:tdisplay` её нет. Это годилось на один вечер: первый же драйвер экрана
вызывает `heap_caps_calloc()` внутри `esp_lcd_new_panel_io_i80()`, то есть без
кучи он не «медленный», а возвращает `NULL`. Значит кучу обязана заводить
сама ОС, и делать это надо до любого драйвера.

#### Почему в `arch/`, а не в `main` приложения

Куча — не служба приложения. Если её заводит `main`, то каждый следующий
`main.c` (щуп, `env:lcd`, потом `capsh`) обязан помнить про вызов, а забыть
легко: код компилируется, линкуется и падает потом, далеко от причины. В
`arch/` вызов один на всех, и на P4 он будет свой собственный — код выше
`arch/` о куче не знает вообще. Отсюда `basalt_heap_init()`.

Содержимое — два вызова, как в IDF: `heap_caps_init()` и
`esp_psram_extram_add_to_heap_allocator()` под `if (esp_psram_is_initialized())`.
Никакой условной компиляции: у Cardputer PSRAM нет, условие просто не
выполнится, и плата поднимется как раньше. Приватный заголовок
`esp_private/esp_psram_extram.h` остаётся осознанной ценой — публичного способа
добавить PSRAM в кучу в IDF нет.

#### Первая попытка: падение на стеке загрузчика

Сначала вызов лёг в `start_cpu0`, рядом с `rtc_wdt_disable()` — ровно туда,
куда и просилось по смыслу: этот слой и так знает про IDF. Плата ответила
двойным исключением на второй же строке щупа:

```
[probe] куча: заведена, PSRAM в куче есть
[probe] heap SRAM: всего 
[сбой] слот 10, причина 29, EPC1 0x4200187b, EXCVADDR 0xffffffe0
...
A1  0x3fc990d0
```

Расшифровка. `EPC1` через `addr2line` — `tx_ready` в
`arch/xtensa/console_usb_jtag.c`, то есть сбой случился при попытке печати
очередной строки. `A1` совпал с `basalt_stack_top` байт в байт. `EXCVADDR`
`0xffffffe0` — это `-32`, смещение от нуля, типичный признак обращения через
испорченный указатель на структуру.

Причина — **на каком стеке** вызвана куча. `heap_caps_init()` регистрирует в
куче все области DRAM, которые ядро оставило свободными, а стек загрузчика
лежит именно в такой области: своего стека у нас в этот момент ещё нет, и
стеком служит память ROM. Куча получает область, поверх которой лежат чужие
кадры. Дальше `heap SRAM: всего` — первое же `heap_caps_get_info()` идёт по
этой области, портит активно используемый стек, и следующий вызов консоли
падает. То есть проблема не в самих цифрах и не в PSRAM, а в порядке: **куча
не имеет права заводиться на стеке, который она же забирает под себя.**

#### Исправление: `basalt_start_c`

`start.S` уже переносил стек строкой `movi a1, basalt_stack_top`, но сразу
звал `basalt_main`. Добавлена промежуточная C-функция `basalt_start_c()`,
и вызывается она уже после переезда:

```asm
    movi    a1, basalt_stack_top
    call0   basalt_start_c
```

а в ней:

```c
void basalt_start_c(void)
{
    basalt_heap_init();
    basalt_main();
}
```

Почему отдельная функция, а не два вызова из ассемблера: «что делать до
приложения» должно быть написано на C, где его прочтут и изменят. Ассемблеру
остаётся ровно одно, чего в C не сделать, — сменить указатель стека. Порядок
«стек, потом куча» теперь держится одной строкой `call0`, а не соглашением
между файлами. `start_cpu0` снова делает только `rtc_wdt_disable()` и
`basalt_start()`.

#### Щуп стал проверкой, а не инициатором

`probe_heap_init()` удалён, вместо него `report_heap_init()`:

```
[probe] куча: заведена, PSRAM в куче есть
```

Это ответ по факту, а не по коду возврата: проверяется
`heap_caps_get_total_size(MALLOC_CAP_INTERNAL) != 0` и
`heap_caps_get_total_size(MALLOC_CAP_SPIRAM) != 0`. Если кучу опять перестанут
заводить, щуп напечатает `НЕ ЗАВЕДЕНА - проверить basalt_heap_init в
arch/xtensa/start.c`. Раньше он в такой ситуации молча заводил кучу сам и
показывал красивые цифры про себя, а не про систему.

#### Цифры сошлись

Все числа совпали с прошлым замером до последнего килобайта: SRAM 358/355/312,
DMA 351/348/312, PSRAM 8192/8189/**8064**, кадровый буфер `0x3c030900`,
заливка 2 839 мкс, сверка 12 767 мкс, расхождений 0. Это и есть проверка, что
`basalt_heap_init()` делает ровно то же, что делал щуп, — не «похоже», а
по тем же областям с теми же границами. `tick 1…5` после этого идут, то есть
система живёт с кучей, заведённой ОС, а не падает через строку.

#### Грабли

| Симптом | Причина | Решение |
|---|---|---|
| двойное исключение (`слот 10`) на первом же `heap_caps_*` при старте, `A1 == basalt_stack_top`, `EXCVADDR 0xffffffe0` | `heap_caps_init()` вызвана на стеке загрузчика и забирает под кучу область, в которой этот стек лежит | звать кучу из `basalt_start_c()`, после `movi a1, basalt_stack_top` |
| после переноса вызова «всё равно падает» | вызов остался в `start_cpu0` — туда управление приходит **до** переезда на свой стек | проверить, что зовёт именно `basalt_start_c`, а не `start_cpu0` |

#### Проверка

```bash
make probe PIO=~/.venvs/pio314/bin/pio   # залить и прочитать замеры
make verify PIO=~/.venvs/pio314/bin/pio  # восемь env + проверка образов
```

Признак успеха — `[probe] куча: заведена, PSRAM в куче есть`, цифры SRAM и
PSRAM совпадают с таблицей в `board.md` §6, и `tick` идут дальше. Если щуп
печатает `НЕ ЗАВЕДЕНА` — вызов уехал из `basalt_start_c()`.

### 06.11.2026. Экран заговорил: i80 через GPIO, три подгонки по глазам

**Файлы:** `drivers/lcd.h` (новый), `drivers/lcd_i80.c` (новый),
`src/lcd/main.c` (новый), `boards/tdisplay_s3/board_pins.h`,
`src/CMakeLists.txt`, `platformio.ini`, `Makefile`,
`.github/workflows/build.yml`, документация.

**Прошивки:** `env:lcd` на живой плате (четыре прогона),
`make verify` — девять env зелёные, проверка образов `tdisplay` и `bare` ok,
`clangd --check` на `lcd_i80.c` и `lcd/main.c` — 0 ошибок.

**Задача.** Экран — первая периферия, которую видно без терминала. До этого
вечера про панель было известно из чужого примера: ST7789, 320×170, восемь
линий данных. Проверить это можно только картинкой.

#### Почему не `esp_lcd`, хотя решили «берём чужой»

Решение от 05.11.2026 звучало разумно: готовый драйвер i80 дешевле своего.
Перед первой строкой кода оно рассыпалось на двух фактах, оба — из чтения
исходников IDF:

1. `esp_lcd_new_i80_bus()` ставит обработчик прерывания и включает его в
   `esp_lcd_panel_io_tx_color()`, а сама передача идёт в фоне. У нас своя
   таблица векторов все уровни 1..5 ведёт в панику — прерываний в системе
   ещё нет. Первый `flush` уронил бы плату, и не потому, что драйвер плохой.
2. `esp_lcd_new_panel_st7789()` в `reset`/`init` зовёт `vTaskDelay()`, а
   планировщика FreeRTOS в системе нет.

Значит транспорт пришлось сделать свой. Не «по регистрам `LCD_CAM`» — это
блок с очередью транзакций и DMA, его настройка дороже всего остального
`arch/`. i80 как таковой — это восемь линий данных и такт `WR`, то есть
обычный параллельный порт: выставили байт, дёрнули `WR`, панель забрала.
Пишем в `GPIO_OUT1_*` напрямую.

Цена честно: заливка синхронная, процессор занят 32 мс на полный кадр. Для
текста с dirty-строками это неважно, а когда появится слой прерываний,
`esp_lcd` ляжет под тот же `drivers/lcd.h` без правок выше интерфейса.

#### Как устроен драйвер

Мелочь, которая экономит половину времени передачи: маски на каждый из 256
байт считаются один раз в `lcd_init`. В горячем цикле остаются две записи в
регистры (`W1TS` на поднять биты, `W1TC` на опустить) вместо восьми проверок
на байт. Плюс `wr_settle()` — три `nop` между фронтами: панель держит не
больше ~15 МГц, а четыре записи в регистры при 240 МГц укладываются в ~20 нс.
Без паузы байты уходят вдвое быстрее паспорта, и часть панелей отвечает
мозаикой.

Порядок байт в пикселе пришлось разворачивать: в памяти `uint16_t` лежит
младшим байтом вперёд, а ST7789 ждёт старший первым. Скопировать «как есть» —
и красный меняется местами с синим.

#### 1. Половина экрана и «старая картинка»

Первая заливка показала полосы на левой половине, а правая осталась от
предыдущей прошивки. Это не помехи и не плохой контакт: **панель родная
портретная (170×320), а памяти у неё 240×320**. Мы писали 320 пикселей в
строку, которой помещается 240, — лишние 80 заворачивались в следующую
строку, и картинка рассыпалась на полосы, а правый край не заполнялся вовсе.

Лечится `MADCTL` с битом `MV` (обмен осей): `0x60` = `MV|MX`. После этого
полосы заняли всю ширину.

#### 2. Полоса старого содержимого внизу

Картинка встала, но внизу осталась полоса с артефактами. Причина та же
арифметика: стекло 170 столбцов, память 240 — по 35 невидимых столбцов с
каждой стороны. В альбомной ориентации они становятся строками, и окно
`RASET` без смещения не доходит до низа экрана.

Смещение `Y +35` (и `X +0`) прибавляется в `lcd_set_window`, а не вызывающим:
тот мыслит в пикселях видимой области, а невидимые столбцы памяти — забота
драйвера.

#### 3. Синяя рамка оказалась жёлтой

Проверку калибровки сделали синей рамкой в два пикселя по краю: у полос край
не отличить от «ещё одной полосы», а рамка сразу показывает, ровные ли все
четыре стороны. Рамка вышла **жёлтой**.

Жёлтый — это ровно дополнение синего до белого. То есть панель показывала
инвертированные цвета целиком, и по полосам это было незаметно: набор
оставался разноцветным. Стекло этой панели IPS, и ей нужен `INVON`
(команда `0x21`) — как в заводском примере LilyGO. После него рамка стала
синей, а порядок полос совпал с задуманным: красный, зелёный, синий, белый,
чёрный, жёлтый, голубой, пурпурный. BGR-бит в `MADCTL` не понадобился.

Вывод на будущее: **цвет проверять по известному эталону, а не «красиво ли
выглядит»**. Разноцветные полосы выглядели совершенно нормально, будучи
инвертированными.

#### Цифры с платы

```
[lcd] панель 320x170, RGB565, подсветка включена
[lcd] кадровый буфер 108800 Б, адрес 0x3c030900
[lcd] полный кадр 32116 мкс, до 31 кадров/с
tick 1  uptime 3.680 s, кадр 32100 мкс
```

108 800 Б за 32.1 мс — ≈3.4 МБ/с, 31 кадр/с полной перерисовки. Для текста
это с большим запасом: строка 320×2 = 640 Б уходит примерно за 0.19 мс.

#### Что осталось в конфиге и почему

`MADCTL`, смещение и инверсия лежат в `board_pins.h`, а не в коде драйвера:
это свойства конкретного стекла, а не алгоритма. Другая партия может
потребовать других чисел, и менять их надо в файле платы, как и остальные
пины.

#### Грабли

| Симптом | Причина | Решение |
|---|---|---|
| картинка на левой половине, справа старое содержимое | `MADCTL` без `MV`: панель портретная, запись шире 240 столбцов заворачивается в следующую строку | `DISP_MADCTL = 0x60` |
| картинка на весь экран, внизу полоса артефактов | окно без смещения: стекло 170 столбцов при памяти 240 | `DISP_Y_OFFSET = 35` |
| синяя рамка вышла жёлтой, белое — чёрным | стекло IPS требует `INVON`; без него изображение — дополнение до белого | `DISP_INVERT_COLORS = 1` (команда `0x21`) |
| `lvalue required as left operand of assignment` на `GPIO_OUT1_W1TS_REG = ...` | в IDF это адрес регистра, а не переменная | `REG_WRITE(GPIO_OUT1_W1TS_REG, ...)` |

#### Геометрия: 53×17 — следствие клетки, а не «сколько влезло»

Панель 320×170. Клетка 6×10: глиф 5×7 плюс по пикселю справа и снизу.
53 клетки по 6 = 318, по пикселю поля слева и справа — ровно 320. 17 строк
по 10 = ровно 170. Ничего не остаётся в остатке, и это удобно: не нужно
решать, куда девать крайние четыре пикселя, и последняя строка не обрезается
наполовину.

Глиф сидит в клетке со сдвигом вниз на 1 пиксель. Под ним остаются две
свободные строки — там рисуется курсор, и он не закрывает саму букву.

#### Шрифт: пиксельный, руками, в генераторе

Была мысль взять пульсовский `make_font.py`, который рендерит TrueType через
Pillow. Он там работает на 13 и 22 px. На 7 px с хинтингом получается каша:
буквы слипаются, `m` и `w` превращаются в пятно.

Поэтому глифы нарисованы ASCII-артом прямо в `tools/make_font.py` — по семь
строк на букву, `#` это точка. Видно глазами в исходнике, правится одной
строкой, и в заголовок попадает уже упакованное. Плюс уходит зависимость от
`.fontenv` и Pillow: `python3 tools/make_font.py` работает где угодно,
включая CI.

Генератор проверяет геометрию до записи файла: ровно 5 на 7, только два
символа, ровно 95 глифов от 0x20 до 0x7E. Проверка сразу поймала опечатку —
у `t` последняя строка была четыре символа вместо пяти. На экране это
выглядело бы как «шрифт поехал», и искать причину начали бы в рендерере, а не
в данных.

Есть и `--preview`: печатает весь набор таблицей в терминал. Это единственная
проверка формы, которая есть, поэтому она встроена в генератор, а не оставлена
на «посмотреть на плате».

#### Отступление от роадмапа: кадровый буфер тексту не нужен

В роадмапе под A1 записан кадровый буфер 108.8 КБ в PSRAM — так было
задумано под `esp_lcd` с DMA. Со своим синхронным драйвером он только вредит:
экран — это 900 глифов, то есть 31 тысяча мелких записей в PSRAM через кэш.
Дорого и без всякой пользы, потому что передать всё равно надо целиком.

Вышло иначе:

| Что | Где | Размер |
|---|---|---|
| сетка символов 53×17 | SRAM | 901 Б |
| полоса одной строки 320×10 | SRAM | 6400 Б |
| **итого** | SRAM | **~7.3 КБ** |

Прокрутка — `memmove` 901 Б сетки и одна полная перерисовка (36 мс), которая
случается раз в 17 строк вывода. Полный кадровый буфер вернётся с графикой
(A12), где он нужен по существу: там картинка собирается из спрайтов и
областей, а не из готовых глифов.

#### Граница слоя: матрица не знает про экран

`text/matrix.c` не зовёт `lcd_flush` и не знает ни одного регистра. Он рисует
строку в буфер, который ему дали, и помечает строки изменёнными. Кто читает
эти флаги и кто передаёт полосу — дело вызывающего.

Цена: одна лишняя функция на строку в одном месте. Выигрыш: вся логика текста
проверяется на маке без платы. Тест смотрит пиксели полосы — то есть видит,
что буква попала в нужную клетку и не перевёрнута, а не «драйвер вызвали
столько раз».

#### Dirty-строки: почему это важно для скорости

Полная перерисовка — 36 мс. Если бы строка состояния внизу перерисовывала весь
экран раз в секунду, это было бы незаметно глазу, но на A2 каждый набранный
символ стоил бы 36 мс, и эхо клавиатуры стало бы вязким. Поэтому матрица
держит флаг на каждую строку, а `present_dirty()` передаёт только их.

Проверка простая и она в логе: на тик печатается число переданных строк.
Должна быть единица. Семнадцать означали бы, что флаги не работают.

#### Цифры с платы

```

[text] полный кадр: 17 строк за 36511 мкс

tick 1  строк передано 1, строка 1826 мкс
```

Отсюда рабочая цифра для A2: эхо одного символа — 1.8 мс, прокрутка — 36 мс

### 06.11.2026. Кириллица: клетка на символ, UTF-8 отдельным модулем

**Файлы:** `tools/make_font.py` (два новых набора глифов), `text/font_5x7.h`
и `text/font_5x7.c` (генерируются), `text/utf8.h`, `text/utf8.c` (новые),
`text/matrix.c` + `matrix.h`, `src/text/main.c`,
`test/test_text/test_matrix.c`, `test/test_utf8/` (новые),
`platformio.ini`, `src/CMakeLists.txt`.

**Прошивки:** `env:text` на живой плате, `pio test -e native` — **56 тестов**
(было 34), читаемость букв проверена глазами.

**Задача.** Кириллица нужна не «когда-нибудь»: A2 — это ввод с мака, и эхо
набранного показывало бы `?` на каждой русской букве. Поэтому сделали её
до ввода, а не после.

#### Клетка стала 16-битной

Матрица хранила `char`, и «Ж» пришлось бы складывать из двух клеток. Сетка
теперь `uint16_t`: 1802 Б вместо 901 Б. Плата за это — килобайт SRAM; взамен
один символ всегда занимает одну клетку, и позиция курсора не зависит от
того, что было напечатано раньше.

#### UTF-8 — отдельный модуль, а не разбор внутри матрицы

Кириллица в UTF-8 занимает два байта. Байты приходят из USB по одному, и
граница символа может попасть на границу двух вызовов `text_putc`. Значит
между вызовами нужно помнить «сколько байт ещё ждём» — и это состояние проще
проверить на маке, где видно конкретный код, чем на плате, где видно «буква
не та» через несколько символов после сбоя.

`text/utf8.c` не знает ни про экран, ни про шрифт: он отдаёт `uint32_t` и
состояние `PENDING`/`DONE`/`INVALID`. Состояние живёт у вызывающего
(`text/matrix.c`), а не внутри модуля: когда в A2 появится второй поток,
у него будет свой декодер, и недособранные буквы двух потоков не склеятся.

Что отвергается, и почему именно это:

| Случай | Почему нельзя принять |
|---|---|
| байт-продолжение без головки | не символ, а мусор от сбоя |
| головки `0xC0`, `0xC1` | ими кодируются только overlong-записи |
| overlong (тот же символ лишними байтами) | классический способ протащить NUL мимо фильтра |
| суррогаты `0xD800…0xDFFF` | так кодировали в UTF-16, в UTF-8 это не символы |
| > `0x10FFFF` | за пределами Unicode |

Отдельно: **управляющий байт сбрасывает недособранную букву**. Без этого
`\n`, пришедший посреди последовательности, оставил бы головку, и хвост
следующей буквы склеился бы с ней — на экране появилась бы буква из воздуха.

#### Шрифт: две таблицы вместо одной

ASCII и кириллица занимают непрерывные блоки кодов (0x20–0x7E и 0x410–0x44F),
поэтому глиф ищется вычитанием, без поиска по таблице. Ё и ё стоят вне блока
(0x401 и 0x451) — им хватило двух отдельных массивов, а не поиска по 161
элементу на каждый символ.

Данные переехали из заголовка в `text/font_5x7.c`. Заголовок теперь содержит
только объявление `font_glyph(cp)`; таблицы `static const` в .c — это flash,
и каждая единица трансляции их больше не копирует.

161 глиф по 7 Б = **1127 Б** — ровно бюджет из `FUNCTIONALITY.md` §13.

#### Символ без глифа рисуется как `?`

Эмодзи, греческий, армянский — глифов нет. Пропускать молча нельзя: в живом
потоке пустая клетка выглядит как пропавшая буква, и непонятно, где кончается
шрифт, а где начинается приём. `?` честно говорит «символ есть, нарисовать
нечем».

#### Грабли

| Симптом | Причина | Решение |
|---|---|---|
| два набора тестов в одном каталоге | PlatformIO собирает весь каталог в один бинарник, а `main`/`setUp` в двух файлах дают duplicate symbol | по каталогу на набор: `test/test_text`, `test/test_utf8` |
| тест ждал `PENDING` на `0xC0` | головка `0xC0` отвергается сразу, это и есть защита от overlong | ожидание в тесте исправлено, код не менялся |
| «всё читается», но верхняя строка буквы пуста | проверял не ту строку глифа: у «А» нижняя строка - ноги по краям, в середине пусто | проверять поперечину (среднюю строку), а не низ |

#### Проверка

```bash

pio test -e native                        # 56 тестов
make flash ENV=text PIO=~/.venvs/pio314/bin/pio
```

Признак успеха — вторая строка `привет, базальт-ос!`, ниже весь алфавит двумя
строками (по 33 буквы), и это без лишних клеток между буквами: каждый символ
занимает ровно одну. Проверено на живой плате 06.11.2026, читаются и Ж, Ш, Щ,
Ю, Ы, Ъ — самые тесные в клетке 5 px.

курсор в своей строке).

**Задача.** A2: набранное на маке должно появляться на экране. Клавиатуры на
плате нет, порт USB Serial/JTAG уже умел и писать, и читать (`env:bare` эхал
байты), значит не хватало ровно одного слоя — того, который решает, когда
нажатие становится символом, когда строкой и что из этого надо нарисовать.

#### Line discipline отдельно от всего

`tty/tty.c` не знает ни про экран, ни про USB: он принимает байты и отдаёт
события — `CHAR`, `ERASE`, `LINE`, `INTR`, `EOF`, `BELL`. Рисует и
передаёт программе вызывающий.

Причина та же, что у матрицы: набор текста — это последовательность, и ошибка
видна только при определённом сочетании (Backspace после кириллицы, `Ctrl-D`
на пустой строке, переполнение буфера). На маке такое сочетание стоит одну
строку теста, на плате — минуту набора руками, и ещё надо догадаться, что
искать.

#### Backspace стирает символ, а не байт

В UTF-8 «Ж» — два байта. Если откатывать строку на один байт, от буквы
останется половина последовательности, и следующая буква склеится с ней: на
экране появится чужая буква посреди слова, а в команде — мусор, которого не
видно. Поэтому `trim_last_cp()` идёт назад, пока байты имеют старшие биты
`10`, то есть пока это продолжения.

#### Битая последовательность вырезается из буфера

`utf8_feed` узнаёт, что последовательность битая, только когда приходит не тот
байт. К этому моменту байты уже лежат в строке. Первый вариант оставлял их
там, и тест `test_invalid_utf8_leaves_no_residue` поймал это сразу: в строке
оказалось 4 байта вместо 3. Появилась `drop_partial()` — откат к началу
последовательности перед разбором любого байта, который не является
продолжением.

#### Зеркало — весь поток, а не только ввод

Сначала зеркало повторяло в USB только принятые символы. На проверке выяснилось,
что тогда ответ на команду (`uptime`, `help`) виден только на экранчике, а в
терминале — нет: проверить команду можно глазами, но не логом, и сверить поток
скриптом невозможно.

Модель стала честнее: экран и USB-терминал — **два вывода одного tty**, и
зеркало дублирует всё, что tty выводит. Команда `mirror off` выключает именно
этот второй вывод; в `raw` он выключается сам, потому что там нет эха по
определению.

#### `Ctrl-C` и кнопка G0

`pio device monitor` перехватывает `Ctrl-C` сам и закрывает монитор — до платы
байт `0x03` не доходит. Проверить прерывание и выйти из raw-режима было бы
нечем, кроме перепрошивки. Поэтому G0 (он же BOOT) отдаёт `tty_input(0x03)`:
фронт с антидребезгом 20 мс, чтобы удержание не сыпало прерываниями. Кнопки
живут за `drivers/button.h` — приложение спрашивает «нажата ли», а не помнит,
что G0 замыкается на землю.

#### Курсор рисовался в каждой строке

На живой плате при наборе экран покрылся чёрточками под первым символом каждой
строки. Причина в матрице: подчёркивание курсора рисовалось в полосе **любой**
перерисовываемой строки, без проверки `row == s_row`. В `env:text` это было
незаметно — строки там почти не перерисовывались, — а при наборе каждая новая
строка перерисовывается сразу. Лечение: одно условие и тест
`test_cursor_only_on_its_row`, который проверяет обе строки: в своей
подчёркивание есть, в соседней нет.

#### Грабли

| Симптом | Причина | Решение |
|---|---|---|
| `Could not open /dev/cu.usbmodem…: port is busy` при заливке | порт держит открытый `pio device monitor` | закрыть монитор; `serial-read.sh` порт не держит только пока читает |
| `Ctrl-C` в мониторе закрывает монитор, плата не реагирует | `Ctrl-C` обрабатывает сам `pio device monitor` | кнопка G0 как `Ctrl-C`, либо `screen /dev/cu.usbmodem… 115200` |

**Задача.** A3 — это командная строка: набрать, исправить, вспомнить прошлую,

#### Enter приходит двумя байтами, а нажатие одно

Первый же вечер за монитором показал: после каждой команды появлялась лишняя
пустая строка и второе приглашение. Выглядело как «echo дважды выполнился»,
хотя плата была права — она честно получила два конца строки.

Причина в хосте. `pio device monitor` по умолчанию работает с `EOL=CRLF`, а
терминал мака на Enter отдаёт `\r` — вместе получается пара `\r\n`. `tty_input`
принимал и CR, и LF как конец строки (правильно: скрипты шлют `\n`), и на паре
срабатывал дважды: первая строка уходила в разбор, вторая — пустая. Отсюда
пустая строка и второе приглашение.

Проверено не на глаз: виртуальный порт (монитор открывает одну pty, мы читаем
другую) показал, что на Enter в плату уходит ровно `b'\r\n'`.

Лечение — в `tty/tty.c`, а не в хосте: `tty_input` запоминает, что предыдущий
байт был CR, и LF сразу за ним не отдаёт никому. Так это работает с любым
терминалом, а не только с `pio`: `screen`, `minicom` и чужие скрипты тоже любят
CRLF. Шесть тестов на маке: `test_canon_crlf_is_one_enter`,
`test_canon_crlf_next_line_clean`, `test_canon_cr_then_letter_not_swallowed`,
`test_canon_lf_alone_still_enter`, `test_canon_two_crs_two_lines`,
`test_raw_crlf_is_one_enter`.

Отдельная ловушка рядом: `monitor_filters` по умолчанию (`NoTerminal` из
pyserial) заменяет управляющие символы «картинками» Unicode — ESC становится
`␛`, BEL — `␇`. Шелл, который говорит с терминалом по-настоящему (`\x1b[K`,
`\b`), с этим фильтром показывал `␛[K` после каждой буквы. В `platformio.ini`
стоит `monitor_filters = direct`.

#### Строкой владеет редактор, а tty остаётся про байты

Канонический режим tty умеет ровно две вещи: дописать символ в конец и стереть
последний. Этого хватает, чтобы набрать команду, но не хватает, чтобы её
исправить: стрелки, `Ctrl-A/E/K/U/W` и история требуют курсора **внутри**
строки. Поэтому `env:shell` переводит tty в raw и редактирует строку сам —
ровно так устроены настоящие терминалы.

Соблазн был добавить это в `tty/tty.c`, но тогда драйвер начал бы знать про
клавиши, а первая же следующая программа (редактор файлов) попросила бы третий
режим. Граница осталась прежней: tty превращает байты в символы, редактор —
символы в строку, приложение рисует. Цена: в raw нет ни эха, ни строк, поэтому
`src/shell/main.c` обязан сам и рисовать, и зеркалить в USB — около сотни строк
на всё про всё.

#### Кольцо истории: пустая строка — не команда

История — массив на 8 записей по 256 Б, и в нём две политики, которые проще
проверить тестом, чем заметить глазами:

- пустая строка не запоминается — иначе `Enter` без текста вытеснял бы из
  кольца настоящие команды;
- повтор последней не запоминается — иначе после `free`, `free`, `free` в
  истории осталась бы одна запись, и «сходить на две назад» стало бы некуда.

Черновик хранится отдельно. Нажав `↑` и передумав, надо вернуть ровно то, что
было набрано, а не пустую строку; поэтому при первом `↑` набранное копируется в
`draft`, а `↓` за пределами списка возвращает его обратно. Это одна из тех
мелочей, которые замечают только когда их нет.

#### Разбор без malloc

`parse_line` работает **в самом буфере**: слова разделяются нулями, `argv`
указывает внутрь строки. Куча у нас есть, но команда, которая падает от
нехватки памяти при разборе собственных аргументов, — плохая команда. Цена:
строка должна быть изменяемой и жить, пока жив `argv`.

Кавычки — то место, где ошибки живут незаметно. Правила взяты как в `sh` и
проверены 23 тестами: `'...'` буквально всё, в `"..."` обратная косая черта
экранирует только `"` и `\`, вне кавычек — любой следующий символ. Отдельно
решили две вещи, которые обычно делают «на глазок»:

- **незакрытая кавычка — ошибка**, а не «додумаем сами». Иначе `echo "a b`
  неотличимо от `echo "a b"`, и опечатка видна только по неверному выводу;
- **больше 16 слов — ошибка**, а не молчаливое обрезание: команда выполнилась
  бы не с теми аргументами, которые набраны.

#### Стек: 992 Б из 8192 — и почему это число важно

`top` по критерию обязан показывать остаток стека, но «остаток» — это не
текущая глубина: в цикле событий она почти постоянна и ничего не говорит о том,
насколько близко подошёл самый глубокий вызов. На xtensa переполнение стека не
даёт внятной ошибки — оно молча затирает соседние данные, и потом причину ищут
в другом месте.

Поэтому при старте (`basalt_stack_paint()`, первая строка `basalt_start_c`)
свободная часть стека закрашивается меткой `0xA5A5A5A5`, а `basalt_stack_used()`
ищет первый незакрашенный байт снизу. Это максимум за всё время работы.

Замер на живой плате сразу после старта: **992 Б из 8192 (12%), остаток 7200 Б**.
Больше всего съедают старт, инициализация панели и первый разбор — но до
переполнения запас шестикратный, и теперь это число, а не надежда.

#### Паника должна называть причину

Проверка паники командой `crash` (запись по нулевому адресу) сразу нашла
дырку: в логе было `причина 29: неизвестная`. Это самый обычный сбой в C —
разыменованный `NULL` или указатель на освобождённую память, — и называть его
«неизвестной» значит оставить человека без главной подсказки. В таблице причин
не хватало 28 и 29.

Заодно поправили подсказку у `EXCVADDR`: там было «0 — не про адрес», и при
разыменованном `NULL` это уводило в сторону. Теперь текст зависит от причины:
для сбоев доступа это «адрес, к которому было обращение» (ноль — законное
значение), для остальных — «этой причиной не используется».

После правки паника читается так:

```
причина 29: запись по недопустимому адресу
вектор  9  исключение пользователя
EPC1     0x42001e38  адрес инструкции, на которой всё остановилось
EXCVADDR 0x00000000  адрес, к которому было обращение
сброс через 3 с
```

и через три секунды `rst:0x3 (RTC_SW_SYS_RST)`, после чего шелл поднимается и
печатает `ready` — система жива.

#### На экране после сброса оставался прошлый кадр

На плате заметили: после `reboot` на экране ещё несколько секунд висел текст
прошлой сессии, и это выглядело так, будто система восстановила состояние.
Ничего не восстанавливалось: **панель ST7789 хранит кадр в своей памяти, пока
на ней есть питание**, а прошивка первые две секунды панель вообще не трогает —
стоит пауза, чтобы хост успел открыть порт. Всё это время на экране жил старый
кадр.

Лечение — порядок строк: `lcd_init` + `text_init` + заливка чистого экрана
**до** паузы, векторы — после неё (их отчёт печатается в консоль, а порт ещё не
открыт). Сделано в `env:shell`, `env:tty` и `env:text` одинаково: разница в
поведении экрана при сбросе — ровно то, чего не ждёшь от «одинаковых» прошивок.

Отдельно стоит помнить: если выдернуть кабель, плата обесточится и картинка
пропадёт — а вот **терминал на маке** текст сохранит, потому что это свойство
терминала, а не платы.

#### Грабли

| Симптом | Причина | Решение |
|---|---|---|
| после сброса на экране текст прошлой сессии | панель хранит кадр в GRAM, а мы 2 с её не трогаем | `lcd_init` + `text_init` + `present_dirty()` до паузы |
| `причина 29: неизвестная` при `NULL` | в таблице причин не было 28 и 29 | дописаны: 28 — чтение, 29 — запись по недопустимому адресу |

| набор тестов не линкуется: `basalt_console_write` | в сборку набора попадает `format.c`, а заглушка живёт в соседнем каталоге | свой `console_sink.c` в каждом новом наборе |
| в `make monitor` после каждой буквы печатается `␛[K`, а `Delete` даёт `␇` | `pio device monitor` по умолчанию ставит фильтр `default` (`NoTerminal` из pyserial): он заменяет управляющие символы «картинками» Unicode — ESC становится `␛`, BEL — `␇`. Нашему шеллу это ломает всё зеркало, потому что он говорит с терминалом по-настоящему | `monitor_filters = direct` в `[base]`: байты уходят в терминал как есть. Проверено на виртуальном порту: до правки `\r> ls␛[K\b\b␇`, после — `\r> ls\x1b[K\b\b\x07` |

ответить на четыре вопроса: заводится ли драйвер при нашем старте, сколько
места в чипе на самом деле, сколько стоит стирание и запись, и какая сейчас
таблица разделов.

#### Почему драйвер flash приходится заводить самим

Драйвер flash в IDF — это `ESP_SYSTEM_INIT_FN(init_flash, …, 130)` внутри
`do_core_init()`. Мы перекрыли `start_cpu0` и `do_core_init()` не зовём, значит
`esp_flash_default_chip` остаётся `NULL`: `esp_flash_get_size(NULL)` возвращает
ошибку, а `esp_flash_read` без аргумента падает. Это уже было в граблях
`AGENTS.md`, но пока flash не нужен был по-настоящему, цена была не видна.

Заводим в `arch/xtensa/flash.c` — там же, где куча: это свойство чипа, а не
платы, и при форке в `basalt-os` заменяется вместе с остальным `arch/`.

#### Почему режим no-OS, а не `esp_flash_app_init()`

У IDF два набора OS-функций для flash, и выбор между ними — не косметика:

| Что | Что делает | Годится ли нам |
|---|---|---|
| `esp_flash_app_init()` + `esp_flash_app_enable_os_functions` | рекурсивный мьютекс FreeRTOS, замки mmap, IPC на второе ядро, защита разделов по таблице | нет: планировщика нет, IPC не работает |
| `esp_flash_noos_functions` (стоят в `default_chip` по умолчанию, как у загрузчика) | гасит кэш через `cache_hal_suspend`, никаких замков | **да** |

Поэтому вызывается только `esp_flash_init_default_chip()` из
`esp_private/esp_flash_internal.h` — та же функция, которой пользуется
загрузчик. Приватный заголовок здесь такая же осознанная цена, как
`esp_private/esp_psram_extram.h` в `heap.c`: публичного «заведи flash» в IDF
нет, потому что в штатной прошивке это делает `do_core_init()`.

У режима no-OS есть цена, и её надо помнить: **на время стирания и записи кэш
выключен, а PSRAM идёт через кэш.** Буфер операции обязан лежать в SRAM;
`esp_flash_read` в буфер из PSRAM вернёт `ESP_ERR_NO_MEM` (временный буфер в
этом режиме не выделяется). В граблях `AGENTS.md` это записано отдельной
строкой.

#### Что показал замер

```

I (2690) spi_flash: flash io: dio
[flash] драйвер: заведён, JEDEC ID 0xef4018
[flash] размер: объявлен 16384 КБ, физический 16384 КБ
[flash] вывод: объявленный размер совпадает с физическим
[flash] ROM: сектор 4 КБ, блок 64 КБ, страница 256 Б

[flash]   0x00f000  4 КБ  тип 1/1  phy_init

[flash]   дальше контрольная сумма MD5 - конец таблицы
```

Три числа, из которых складывается вся дальнейшая конструкция ФС:

1. **Стирание сектора 46 мс против записи тех же 4 КБ за 10 мс.** Стирать на

2. **Чтение 8 МБ/с** — потолок SPI-драйвера. Кэш (memory-mapped чтение) может
   быть быстрее, но требует `spi_flash_mmap` с его замками, то есть того
   самого app-режима. Вопрос открыт до появления раздела данных.
3. **Свободно 15 296 КБ вне разделов** — это бюджет A9. Утверждённая на бумаге
   цифра «~14 МБ» совпала с измеренной.

#### Почему таблица разделов разобрана своим кодом

`esp_partition_*` читает таблицу через `spi_flash_mmap`, а mmap требует замков,
которые заводит `esp_flash_app_init()` — того самого, от которого мы отказались.
Поэтому таблица разбирается по формату: 32-байтные записи с `0x8000`, magic
`0x50AA`, конец — запись MD5 с magic `0xEBEB`. Двадцать строк кода, и они всё
равно понадобятся: в A9 таблица будет своя, и читать её будет свой код.

#### Что осталось на следующий шаг

Своя таблица разделов (`board_build.partitions`: приложение 2 МБ, остальное —
данные) и `CONFIG_ESPTOOLPY_FLASHSIZE_16MB`. Второе лечит не нынешнюю работу
драйвера (размер он берёт из `g_rom_flashchip`, и там правильные 16 МБ), а
заголовок образа: сейчас в нём записано 2 МБ, отсюда и
`Warning! Flash memory size mismatch detected. Expected 16MB, found 2MB!` на
каждой сборке. Разбираться с этим отдельно, вместе с таблицей, — чтобы правка
`platformio.ini` и `sdkconfig` была одна и с причиной.

#### Грабли

| Симптом | Причина | Решение |
|---|---|---|
| щуп пишет `запись 3: чужой magic 0xebeb` | после записей таблицы идёт не раздел, а контрольная сумма MD5 (`ESP_PARTITION_MAGIC_MD5`) | считать `0xEBEB` концом таблицы, а не мусором |
| `esp_flash_read` возвращает `ESP_ERR_NO_MEM` при свободной PSRAM | режим no-OS: кэш выключен, PSRAM недоступна, временный буфер не выделяется | буфер операции — только в SRAM |
| `[flash] размер: объявлен 2 МБ` на плате с 16 МБ | в `sdkconfig` стоит `CONFIG_ESPTOOLPY_FLASHSIZE="2MB"`, а `CONFIG_SPI_FLASH_SIZE_OVERRIDE` включён | приводить размер в `sdkconfig` в порядок вместе с таблицей разделов |

#### Проверка

```bash

```

Признак успеха — строки `[flash]` с ID чипа, таблицей разделов, числами
замеров, `сверка: расхождений 0` и выводом «драйвер рабочий», затем `ready` и
тики. Сектор `0x009000` после щупа стёрт обратно в `0xFF` — щуп не оставляет
следов.

### 06.11.2026. Своя таблица разделов: 2 МБ приложению, 14 МБ данным

**Файлы:** `partitions.csv`, `sdkconfig.defaults.tdisplay`,
`sdkconfig.defaults.cardputer`, `CMakeLists.txt`, `platformio.ini`,
`storage/parttable.h`, `storage/parttable.c`, `test/test_parttable/`,
`src/flash/main.c` (переведён на модуль, ширина hex в отчёте), `src/CMakeLists.txt`,
`.gitignore`, `docs/board.md` §6 и §10, `docs/ROADMAP.md` A9,
`docs/FUNCTIONALITY.md` §4 и §13, `AGENTS.md`.

**Прошивки:** `env:flash` и `env:tdisplay` на живой плате; `make verify` —
тринадцать env и 166 хостовых тестов.

**Задача.** Драйвер flash есть, но пользоваться им было нечем: таблица разделов
по умолчанию отдаёт приложению 1 МБ и больше ничего не описывает, то есть 15 МБ
из 16 не принадлежат никому. Нужно было назвать место под данные — и заодно
убрать расхождение в 2 МБ, из-за которого в заголовке образа стоял неверный
размер flash.

#### Что в таблице и почему именно так

```
nvs        data nvs   0x009000   24 КБ
phy_init   data phy   0x00f000    4 КБ
factory    app  app   0x010000    2 МБ
storage    data 0x40  0x210000   14 272 КБ
```

- **2 МБ приложению, а не 1.** Сейчас образ 182 КБ, но граница раздела — это и
  граница, за которую образ не выйдет при переполнении; 2 МБ дают
  восьмикратный запас (mruby, программы A11) ценой 1 МБ из данных.
- **Подтип `storage` — `0x40`, «свой формат».** Не `fat` (0x81), не `spiffs`
  (0x82) и не `littlefs` (0x83): ФС ещё не выбрана, а объявить раздел чужой
  файловой системой — соврать в таблице, которую потом читает свой же код.
- **nvs и phy_init оставлены как были.** Проект их не использует, но 28 КБ
  дешевле, чем однажды выяснять, кто из компонентов IDF ищет раздел по имени.

Места вне разделов не осталось: 0x210000 + 0xDF0000 = 0x1000000 ровно.
Это и есть смысл своей таблицы — дальше место только перераспределяется.

#### Размер flash: два файла умолчаний вместо одного

`Warning! Flash memory size mismatch detected. Expected 16MB, found 2MB!`
шёл на каждой сборке espidf. Причина: `board_build.flash_size` для espidf
описывает только то, сколько заливать, а размер в заголовке образа и в таблице
разделов берётся из `CONFIG_ESPTOOLPY_FLASHSIZE`. В `sdkconfig.<env>` стоял
дефолт IDF — 2 МБ.

Правильный ход — файл умолчаний на плату. Через `platformio.ini` это не
задаётся: там «;» — начало комментария, и список `файл1;файл2` обрезается до
первого элемента. Но IDF умеет читать несколько файлов умолчаний, и выбрать их
можно в `CMakeLists.txt` — там `BASALT_BOARD_TDISPLAY` уже известен:

```cmake
set(SDKCONFIG_DEFAULTS
    "${CMAKE_CURRENT_LIST_DIR}/sdkconfig.defaults"
    "${CMAKE_CURRENT_LIST_DIR}/sdkconfig.defaults.tdisplay")
```

Так появились `sdkconfig.defaults.tdisplay` (16 МБ) и `sdkconfig.defaults.cardputer`
(8 МБ). Карпьютеру второе число ничего не меняет (у него и было 2 МБ в
заголовке), но теперь у обеих плат в заголовке правда, а не «дефолт, который
никто не выбрал».

Проверено по заголовку, а не по логу сборки:

```
$ esptool image-info .pio/build/tdisplay/firmware.bin | grep "Flash size"
Flash size: 16MB
$ esptool image-info .pio/build/bare/firmware.bin | grep "Flash size"
Flash size: 8MB
```

Цена механизма: PlatformIO следит за временем правки только общего
`sdkconfig.defaults`, файл платы подключён мимо этой проверки. После его правки
`sdkconfig.<env>` надо удалить руками — строка в граблях `AGENTS.md`.

#### Что показал щуп после переразметки

```
[flash] разделы с 0x8000:
[flash]   0x009000  24 КБ  тип 1/2  nvs
[flash]   0x00f000  4 КБ  тип 1/1  phy_init
[flash]   0x010000  2048 КБ  тип 0/0  factory
[flash]   0x210000  14272 КБ  тип 1/64  storage
[flash]   дальше контрольная сумма MD5 - конец таблицы
[flash] всего разделов 4, за последним (0x01000000) свободно 0 КБ - разделы занимают весь чип
```

Таблица читается **с чипа**, а не из `partitions.csv`: это разные вещи, и
именно поэтому щуп полезен — файл мог не попасть в образ, а заливка могла не
тронуть `0x8000`.

#### Разбор таблицы вынесен в `storage/parttable.c`

Пока таблицу читал один щуп, разбор жил прямо в `src/flash/main.c`. Но читать
её будут двое: щуп и файловая система (найти раздел `storage`). Формат не наш
(IDF), ошибиться в смещениях полей легко, а цена ошибки — раздел с мусорным
адресом, то есть запись в чужое место flash.

Поэтому разбор переехал в `storage/parttable.c`: `basalt_parttable_get()` и
`basalt_parttable_find()`. Модуль работает только с байтами, которые уже в
памяти, — ни регистров, ни `esp_flash`. Значит, он проверяется на маке
(`test/test_parttable`, 14 тестов), а не «на плате и повезёт». Чтение с чипа
осталось у вызывающего: щупу нужен один `basalt_flash_read`, ФС будет делать
то же самое.

Два решения в интерфейсе, которые стоит помнить:

- **Конец таблицы — это два разных исхода**, `END_FF` (стёртая flash) и
  `END_MD5` (контрольная сумма, которую всегда дописывает `gen_esp32part.py`).
  Для поиска разницы нет, а в отчёте щупа есть: строка «дальше контрольная
  сумма MD5» в логе и есть `END_MD5`.
- **Поиск идёт по метке, а не по номеру записи.** Порядок разделов — не
  контракт, его меняют при переразметке; имя раздела остаётся.

`storage/` заведён сейчас, а не «когда понадобится»: это место для ФС и VFS, и
граница модуля видна сразу — переносимая логика в `storage/`, работа с чипом в
`arch/xtensa/`.

#### Грабли

| Симптом | Причина | Решение |
|---|---|---|
| `за последним (0x000000) свободно 0 КБ` при полной таблице | конец таблицы равен размеру чипа (`0x1000000` — семь разрядов), а печаталось шесть, и старший разряд отбрасывался | `basalt_put_hex(end, 8)` в отчёте щупа |
| `SDKCONFIG_DEFAULTS=файл1;файл2` в `platformio.ini` не работает | в INI «;» — начало комментария | список задаётся в `CMakeLists.txt` |
| Правка `sdkconfig.defaults.<плата>` не подействовала | PlatformIO следит за mtime только общего файла | удалить `sdkconfig.<env>` и пересобрать |
| `partitions.csv` не подхватился | путь в `board_build.partitions` считается от корня проекта, а имя ищется и в наборе PlatformIO | проверить лог: `Generating partitions .pio/build/<env>/partitions.bin`; разложить бинарник `gen_esp32part.py` |

### 06.11.2026. BFS: своя файловая система с копированием при записи

**Файлы:** `storage/bfs.h`, `storage/bfs.c`, `test/test_bfs/`, `src/fs/main.c`,
`src/CMakeLists.txt`, `platformio.ini`, `Makefile`,
`.github/workflows/build.yml`, `docs/`.

**Прошивки:** `env:fs` на живой плате; все 14 env собираются; 210 хостовых
тестов проходят (из них 30 — на BFS).

**Задача.** Раздел `storage` на 14 МБ размечен, драйвер flash проверен, но
хранить файлы негде: система по-прежнему живёт в `.bss`, а `/etc/rc`
приходилось бы придумывать заново после каждой перезагрузки. Нужен формат на
диске и операции над ним, и нужен такой, чтобы крах в любой момент не оставлял
раздел в состоянии «половина файла».

#### Почему своя, а не `littlefs`/SPIFFS/FAT из IDF

Все три приходят через `esp_partition_*`, а он читает таблицу разделов через
`spi_flash_mmap`. mmap требует замков, которые заводит `esp_flash_app_init`,
то есть FreeRTOS, — а планировщика у нас нет (запись от 06.11.2026 про драйвер
flash). Плюс каждая из них тянет свой слой блочного устройства и свою отладку.
Свой формат можно разобрать по байтам с дампа flash и проверить на маке, не
имея платы в руках, — а именно это и нужно, когда плата не отвечает.

#### Почему копирование при записи (COW), а не журнал (WAL)

Стояли два варианта, оба честные. Выбрано копирование при записи: блоки
метаданных никогда не переписываются на месте, изменение — это новые блоки
плюс новый суперблок, который на них указывает. Атомарность даёт переключение
копии суперблока.

- **Нет replay.** У журнала монтирование обязано писать: применить хвост
  журнала и пометить его применённым. Значит ошибка в коде монтирования может
  испортить ФС, а проверить этот код можно только после настоящего краха. У
  COW монтирование **только читает**: ошибка в нём ничего не портит.
- **Крах в любой момент = откат к предыдущему коммиту.** Старый суперблок цел,
  пока новый не записан целиком (иначе не сойдётся CRC). Нет состояния
  «журнал применён, но не очищен».
- **Нет третьей сущности.** В журнале их три (журнал, домашние блоки, очистка)
  и переходы между ними; здесь одна — какой суперблок новее.

Цена: каждый изменённый блок стоит стирания сектора. При записи во flash
стирание всё равно неизбежно, COW его не добавляет, а только делает явным.

#### Как устроено (подробности — в шапке `storage/bfs.h`)

| Что | Где | Размер |
|---|---|---|
| Суперблок: кольцо из 32 слотов по 128 Б в двух секторах | блоки 0–1 | 8 КБ |
| Inode-таблица: 8 блоков по 32 inode | номера блоков лежат в суперблоке | 32 КБ, 256 узлов |
| Данные, каталоги, indirect | остальное | ~14 МБ |

- **Битмап занятости не хранится на диске.** Он собирается при монтировании
  обходом inode-таблицы. Расходиться с деревом ему не с чем — а это целый
  класс ошибок «после сброса блок выдан дважды».
- **Освобождение откладывается до коммита.** Пока новый суперблок не записан,
  на диске живёт старый, который ссылается на блок. Отдать его под запись
  раньше — значит стереть данные, на которые ещё указывает рабочая копия.
- **Два сектора суперблока именно из-за стирания:** пока стирается один,
  второй держит последнюю живую копию. Слот пишется без стирания, сектор — раз
  в 32 коммита.
- **Три 4-КБ буфера в статике, а не один общий.** Функции вложены: разбор
  каталога держит свой блок, пока карта блоков читает indirect в свой. Один
  общий буфер дал бы порчу данных через месяц, а не ошибку компиляции; стек
  8 КБ 4-КБ массив тоже не вместит.
- **Удаление в каталоге — надгробие** (`inode = 0`), а не сдвиг содержимого:
  удаление стоит одной записи, а пустые места переиспользуются при добавлении.

#### Что нашли тесты

Тесты на маке писались вместе с кодом и нашли две настоящие ошибки — обе
такие, которые на плате выглядели бы как «ФС иногда врёт»:

| Симптом | Причина | Решение |
|---|---|---|
| segfault на `bfs_stat("/")` | `path_resolve` писал `*idx`, а `stat` и `read` передают туда `NULL` — индекс им не нужен | `if (idx != NULL)`; в `bfs.h` записано, что допускается `NULL` |
| после `rename` в том же каталоге старое имя оставалось | `from_parent` и `to_parent` — две копии одного inode; удаление делалось в первой, а записывалась вторая, без него | при совпадении каталогов работа идёт с одной копией и пишется один раз |

Третий тест — не про ошибку, а про главное свойство формата: **обрыв
питания**. RAM-диск «выключается» после N операций стирания и записи (молча, как
в жизни — кода ошибки при пропаже питания никто не возвращает), после чего ФС
обязана смонтироваться, а файл — быть либо целиком старым, либо целиком новым.
Проверяются все N от 0 до 24. Половинки не было ни разу.

**Запись 52–55 КБ/с — это не медленно, а честно.** Блок 4 КБ стоит «стереть

старого блока, COW inode-таблицы и запись суперблока. Отсюда правило для VFS:
**один коммит на файл, а не на блок.** Сейчас `bfs_write` коммитит на каждый

по блоку, поиск блока в карте, `memcpy` в буфер вызывающего. Для `cat`
незаметно; для заливки образа понадобится кэш (memory-mapped чтение), и это
отдельное решение, а не «ускорим потом».

**Монтирование 6.5 мс** на 30 занятых блоках. Цена растёт с числом файлов,
потому что битмап собирается обходом inode-таблицы; мерить надо, когда их
станет сотни.

### 06.11.2026. VFS и файловые команды: путь разбирает VFS, а не каждая команда

**Файлы:** `storage/vfs.h`, `storage/vfs.c`, `storage/vfs_bfs.h`,
`storage/vfs_bfs.c`, `storage/bfs_flash.h`, `storage/bfs_flash.c`,
`test/test_vfs/`, `src/shell/main.c`, `src/fs/main.c`, `src/CMakeLists.txt`,
`platformio.ini`, `tools/smoke.sh`, `docs/`.

**Прошивки:** `env:shell` и `env:fs` на живой плате; все 14 env собираются;
236 хостовых тестов проходят (из них 25 — на VFS, 31 — на BFS).

**Задача.** BFS умеет читать и писать inode по полному пути, но путём с `..`
она не умеет ходить принципиально: у inode нет ссылки на родителя. Кроме
того, у системы ещё появятся `/tmp` (ramdisk) и `/dev` (таблица устройств), и
команды не должны узнать об этом ни строкой. Значит, нужен слой между
командой и ФС: он канонизирует путь, держит текущий каталог и решает, какая
ФС отвечает за этот путь.

#### Почему VFS — таблица точек, а не «ФС и есть корень»

Соблазн был простой: раз ФС одна, пусть `ls` зовёт `bfs_readdir`, а `cd`
хранит строку. Но тогда разбор `..` пришлось бы повторять в каждой команде,
и `cat a/../b` однажды открыл бы не тот файл, что `ls a/../b`. Теперь путь
разбирает одно место — `vfs_normalize`, — и оно проверено на маке гуще всего:
именно ошибка в разборе пути выглядит как «файл пропал» через месяц.

Точка монтирования — это префикс (`/`, позже `/tmp`) и таблица операций. Поиск
берёт **самый длинный** подходящий префикс, поэтому `/tmp` внутри `/` — норма,
а не конфликт. Запрещена только вторая точка с тем же префиксом: «смонтировать
поверх» — это размонтирование, которого в интерфейсе нет.

#### Три файла вместо одного

| Файл | Что знает | Чего не знает |
|---|---|---|
| `vfs.c` | пути, cwd, точки, открытые файлы | ни одного типа BFS |
| `vfs_bfs.c` | как позвать BFS и как перевести её коды | ни одного пути и cwd |
| `bfs_flash.c` | где раздел `storage`, как читать и стирать flash | ни одного пути и ни одной команды |

Разделение не ради красоты: `bfs.h` не включает `vfs.h`, поэтому ФС можно
проверять на маке одна, без VFS. Цена — адаптер на десяток строк, где каждая
операция переводит код и тип явно. Это дешевле, чем обнаружить, что ramdisk в
`/tmp` не влезает в интерфейс, заточенный под BFS.

**Привязка к разделу вынесена из щупа.** `env:fs` больше не держит свою копию
адаптера блочного устройства: и щуп, и шелл зовут `basalt_fs_mount`. Иначе
«в щупе работает» перестало бы значить «в системе работает».

#### Команды в шелле

`ls`, `cat`, `cd`, `pwd`, `stat`, `mkdir`, `rm`, `rmdir`, `cp`, `mv`, `df`.
Что стоит помнить о реализации:

- **`cat` держит свой UTF-8-декодер** между кусками чтения: буква на границе
  двух чтений иначе рассыпалась бы. Буфер 512 Б — файл не тянется в память
  целиком.
- **`cp` читает и пишет блоками по 4 КБ**, по размеру блока BFS: один вызов
  `bfs_write` — один коммит ФС, мельче буфер означал бы больше коммитов на тот
  же файл. Отдельная проверка «откуда и куда — один файл»: иначе `O_TRUNC`
  обнулил бы источник до чтения.
- **`mv` через границу точек отвергается** и говорит об этом словами:
  `VFS_ERR_ARG` в VFS значит ещё и другие вещи, но эта — единственная, которую
  пользователь может получить на `mv`.
- **`df` считает в байтах**: VFS отдаёт байты, адаптер BFS пересчитывает свои
  блоки. Размер блока — дело ФС, оболочка его знать не должна.

Корень монтируется при старте (`fs_mount_root`): если раздел не размечен —
размечается, иначе просто монтируется. Отказ хранилища не валит систему: шелл
поднимается без файлов, а причина печатается и на экран, и в лог.

### 06.11.2026. Перенаправления и конвейер: `echo текст > файл`

**Файлы:** `shell/parse.h`, `shell/parse.c`, `shell/redirect.h` (новый),
`shell/redirect.c` (новый), `test/test_parse/`, `test/test_redirect/` (новый),

`src/CMakeLists.txt`, `platformio.ini`, `docs/`.

**Прошивки:** `env:shell` на живой плате (восемь заливок за вечер); все env
собираются; 271 хостовый тест проходит (добавлено 7 на разбор и 27 на план
выполнения, плюс один на `vfs_truncate`).

**Задача.** До этого вечера файл с содержимым нельзя было создать на самом
устройстве: `echo` печатал, а записать это в файл было нечем. Отсюда и
незакрытый P0-критерий A9 — «создать файл прямо на устройстве».

#### Почему служебные символы распознаёт парсер, а не шелл

Соблазн был очевидный: в шелле пройтись по `argv` и поискать `>` и `|`. Но
`echo "a > b"` обязан напечатать `a > b`, а `echo '>'` — один символ. Знание
«этот `>` был в кавычках» существует ровно в одном месте и ровно на время
разбора: после него остаётся строка без кавычек, и отличить её от настоящего
перенаправления уже нельзя. Поэтому токен получил вид (`PARSE_TOK_WORD`,
`OUT`, `APPEND`, `IN`, `PIPE`), а не только текст.

Второе следствие того же решения — **текст служебного токена лежит в статике
модуля**, а не в буфере строки. Если записать ноль на место `>` в `a>f`, то
съешь следующий символ и получишь слово `a` и файл `f`, которого нет.
Служебный `argv` поэтому нельзя ни менять, ни освобождать — это записано в
`parse.h`, потому что выглядит как обычный `char*`.

#### Почему план выполнения — отдельный модуль

`shell/redirect.c` ничего не выполняет: он превращает список токенов в
ступени (команда + куда вывод + откуда ввод) и отказывается от бессмысленного.
Решает чистая функция, поэтому её 27 тестов на маке стоят секунды. Ошибка в
этом месте на плате выглядит не как «не собралось», а как «`echo a > f`
напечатал на экран» — то есть её ищут глазами по логу.

Где мы сознательно **не как в sh**:

- **Два `>` в одной ступени — ошибка.** В sh побеждает последний, а первый
  файл создаётся пустым. Молча созданный пустой файл хуже отказа.
- **Ступень без команды — ошибка**: `| ls`, `ls |`, `ls | | wc`, а также
  строка из одних перенаправлений `> f`.
- **Служебный символ не может быть именем файла**: `echo a > > f`.

#### Почему конвейер без процессов

Процессов у нас нет, поэтому ступени идут по очереди, а вывод предыдущей
копится целиком в буфере **64 КБ** (два буфера, потому что одна ступень
читает из одного и пишет в другой). Буферы — в PSRAM: это ровно тот случай,
для которого она нужна, и 128 КБ из 8 МБ незаметны. Если PSRAM на плате нет,
берётся обычная память. Переполнение — честная ошибка с числом: обрезанный
вывод выглядит как правильный, и ошибку в нём ищут глазами.

Буферы выделяются при первом конвейере, а не при старте: `|` нужен не каждой
сессии, а 128 КБ — не то, что стоит держать занятым «на всякий случай».

#### Три приёмника вместо одного дескриптора

`src/shell/main.c` перед выполнением ступени выбирает, куда идут `out_puts` и
`out_cp`: экран (матрица + зеркало в USB), файл или буфер конвейера. Команды
про перенаправления не знают — и не должны: `ls`, `cat`, `df` пишут «в свой
вывод», а куда он идёт, решает оболочка.

Отсюда отдельная функция **`out_diag`**: сообщения самой оболочки и ошибки
команд идут на экран **всегда**. `cat /nope > f` должен ругаться на экране, а
не писать «не найдено» в новый файл. В настоящем шелле для этого есть второй
поток (`2>`), у нас его нет — значит нужна отдельная функция, а не флаг.

#### Что нашлось только на плате

Три ошибки, которых не было видно на маке, и все три — про объём и порядок.

1. **`help > файл` «зависал».** Вывод шёл в BFS кусками по 2–10 байт, а BFS
   переписывает блок целиком: больше сотни записей во flash по десятки
   миллисекунд. Со стороны это минуты без признаков жизни, и Ctrl-C не
   помогает — оболочка в этот момент не читает ввод. Лечится буфером записи
   4 КБ в приёмнике: `help > файл` стал 0.2 с вместо «не дождался».
2. **`cat` в файл терял половину данных.** `cat` разбирал поток как UTF-8 и
   собирал обратно — правильно для экранной матрицы, которая знает только
   code point, и катастрофа для файла: всё, что не является корректной
   последовательностью, пропадало. `cat /big > /copy` давал 35 073 Б вместо
   65 536 Б, и заметить это можно было только по размеру. Теперь в файл и
   конвейер байты идут как есть, декодер остался только на экране.
3. **`cat /a > /a` обнулял файл.** Усечение делалось при открытии, то есть до
   того, как команда увидит, что читает тот же файл. Теперь оно **отложено до
   первой записи**: `cat` успевает отказаться, и файл остаётся целым. Пустой
   вывод по-прежнему даёт пустой файл — усечение делается в конце ступени,
   если писать так и не начали. Для этого в VFS появился `vfs_truncate`
   отдельной операцией: `O_TRUNC` при открытии — это ровно то, чего нельзя
   делать заранее.

### 06.11.2026. `/etc/rc`: система при первом запуске обустраивает себя сама

**Файлы:** `src/shell/main.c`, `tools/smoke.sh`, `docs/`.

**Прошивки:** `env:shell` на живой плате, `pio run -t erase` + заливка;
`./tools/smoke.sh shell` проходит с новой строкой; 271 хостовый тест
проходит.

**Задача.** Критерий A9 требовал, чтобы после `pio run -t erase` система
поднималась с пустым корнем и **сама** создавала `/etc/rc`. До этого вечера
на чистом разделе не было ни каталогов, ни файлов: система работала, но
записать «что делать при старте» было некуда, и первый запуск ничем не
отличался от второго.

#### Почему файл создаёт система, а не команда

`mkfs`-подобная команда потребовала бы, чтобы пользователь знал о её
существовании и вспомнил про неё на чистой плате. А `/etc/rc` — это не
пользовательский файл, а часть договора: «здесь лежит то, что выполняется при
старте». Договор должен выполняться без участия человека, иначе он не
договор.

Каталог `/etc` создаётся первым: `vfs_mkdir("/etc")`, и «уже есть» — не
ошибка. Файл создаётся только если его нет: перезапись шаблоном стёрла бы
настройки при обновлении прошивки — самый неприятный вид потери данных,
потому что замечают её через неделю.

#### Почему строки исполняются, а не просто лежат

Файл, который никто не читает, — это не «задел на будущее», а обман: он
выглядит как рабочий механизм. Поэтому `/etc/rc` выполняется при каждом
старте, до `ready`. Нового кода для этого почти не понадобилось: строки
отдаются тому же `run_command`, что и ввод с клавиатуры, — то есть rc умеет
ровно то же, что шелл, и разойтись с ним не может.

Свой разбор строк, а не общий `parse_line`: файл приходит с мака, где конец
строки — CRLF, и `\r`, оставшийся в конце команды, приклеился бы к последнему
слову (`rm /x\r`). Строка длиннее 255 байт пропускается целиком: обрезанная
команда выполнилась бы не с теми аргументами.

#### Что видно в логе

```
[shell] ФС storage: смонтирована
[shell] экран 53x17, tty raw, стек 8192 Б
[shell] /etc/rc: строк: 3
ready
```

«Строк», а не «команд»: комментарии и пустые строки тоже считаются, и
называть их выполненными командами было бы неправдой.

#### Проверено на плате

1. `pio run -e shell -t erase` + заливка: корень пуст, система создаёт `/etc` и
   `/etc/rc` (225 Б шаблона), `ls /` показывает `etc/`, `ls /etc` — `rc`.
2. `rm /etc/rc` + перезагрузка: файл создан заново, шаблон тот же.
3. `echo echo привет из rc > /etc/rc` и `echo echo вторая строка >> /etc/rc`,
   перезагрузка: в логе перед `ready` появляются обе строки, затем
   `[shell] /etc/rc: строк: 2`. То есть rc работает на настоящих командах, а
   не только на комментариях.

#### Грабли

| Симптом | Причина | Решение |
|---|---|---|
| после `pio run -t erase` + заливки в логе `смонтирована`, хотя корень пуст и только что создан | заливка оканчивается сбросом: первая загрузка (та, что форматирует и пишет `/etc/rc`) проходит **до** того, как `serial-read.sh` откроет порт и сбросит плату ещё раз; в кадр попадает уже вторая загрузка | это не ошибка: `размечена заново` видно, только если поймать самый первый старт; проверять наличие `/etc/rc`, а не строку лога |
| плата перестала отвечать на esptool после `-t erase` или после заливки файла по XMODEM, порт открывается, байтов нет | чип остался в состоянии, из которого USB-JTAG не выводит; `reset.sh` тоже не подключается | переподключить USB-кабель (передёрнуть питание), затем `reset.sh` — проверено; в `docs/board.md` §5 |

### 06.11.2026. Заливка файлов по консоли: XMODEM и `tools/xsend.sh`

**Файлы:** `shell/xmodem.c`, `shell/xmodem.h`, `src/shell/main.c`,
`src/CMakeLists.txt`, `platformio.ini`, `test/test_xmodem/`, `tools/xsend.py`,
`tools/xsend.sh`, `docs/`.

**Прошивки:** `env:shell` на живой плате. 291 хостовый тест (20 из них —
`test_xmodem`), 15 env собираются, `clangd --check` по `src/shell/main.c` и
`shell/xmodem.c` — 0 ошибок.

**Задача.** Критерий A9 требовал, чтобы файл, залитый по консоли, появился в
`ls` и пережил перезагрузку. До этого вечера файл на плату можно было
положить только прошивкой или руками через `echo`, а перенаправления писали
только текст.

#### Почему XMODEM и почему свой приёмник

Канал один — USB Serial/JTAG, он же консоль. XMODEM поверх него даёт ровно
то, что нужно: пакет с номером, CRC и подтверждение на каждый пакет. Потеря
или порча байта не превращается в тихо испорченный файл, а заканчивается
повтором пакета или честной ошибкой.

Приёмник — отдельный модуль `shell/xmodem.c`, который знает только байты и
три колбэка (`put`, `get`, `sink`, `finish`). Поэтому `test_xmodem` на маке
проверяет то, что на плате не повторить: потерянный ACK (пакет пришёл
дважды), битую CRC, пропавший пакет (номер разъехался), отмену по `CAN CAN`,
молчание отправителя, переход номеров через 255. Плата остаётся проводом:
`src/shell/main.c` даёт модулю консоль, тик и VFS.

Пакеты — по 1 КБ (`STX`), хотя классический XMODEM — 128 байт: на 100 КБ это
100 подтверждений вместо 800, а накладные расходы падают с 4 % до 0,5 %.
Отправитель на маке — `tools/xsend.py` (обёртка `tools/xsend.sh` берёт питон
из PlatformIO, где есть pyserial). Он сам открывает порт, ждёт `ready`, сам
набирает `rz <путь>` (порт занят им, руками набрать негде) и шлёт файл.

#### Грабля, которую нашла плата, а не тест

Первая версия подтверждала EOT **до** записи остатка из буфера обмена: файл
дописывался уже после того, как отправитель получил ACK. На глаз это не
видно — между ACK и записью проходят миллисекунды. Видно стало на
автоматической проверке: скрипт сразу после `xsend.sh` открывал порт, плата
перезагружалась, и файл в 3 байта оказывался пустым при честном «принято».

Лечение — колбэк `finish` в `xmodem_io`: он зовётся на EOT **до** ACK и
дописывает буфер. Теперь «отправитель получил подтверждение» и «файл лежит во
flash» — одно событие. В тесте это закреплено: в момент `finish` ACK за EOT
ещё не отправлен.

#### Дополнение 0x1A

XMODEM не передаёт длину файла: последний пакет дополняется байтом `0x1A`
(наследие CP/M EOF). Приёмник его выбрасывает, придерживая хвост до первого
не-`0x1A` байта, а на EOT просто забывает. Цена честная: файл, который
по-настоящему кончается на `0x1A`, потеряет эти байты. Так устроен протокол, и
это записано в шапке `tools/xsend.py`. Проверено на плате: `abc\x1a\x1a` даёт
файл в 3 байта, а `ab\x1a cd` — все пять.

#### Замеры

| Что | Размер | Время | Скорость |
|---|---|---|---|
| текстовый файл | 51 Б | 0,01 с | — (один пакет) |
| средний файл | 100 КБ | 4,4 с | 22,9 КБ/с |
| крупный файл | 512 КБ | 24,6 с | 20,8 КБ/с |

Упирается не во flash: 64-байтовые пакеты USB CDC и запись блока во flash
идут последовательно. Перекрыть их можно только приёмом в прерывании или
DMA — это отдельная задача, не A9. Для настроек и образов в сотни килобайт
двадцать килобайт в секунду достаточно: 100 КБ — четыре секунды.

#### Проверено на плате

1. `note.txt` (51 Б): `ls`, `stat` и `cat` показывают текст.
2. `big.bin` (100 400 Б) и `big512.bin` (524 288 Б): `stat` после
   перезагрузки, `cat` через консоль — байт в байт.
3. Перезапись существующего файла меньшим: `O_TRUNC` работает, 524 288 Б
   превращаются в 51 Б.
4. Пустой файл: создаётся файл в 0 Б, приём это переживает.
5. `rz /nodir/x`: «не найдено», передачи нет.
6. `rz` без отправителя: 15,5 с (пять `C` по 3 с), `CAN CAN`, ошибка, файла
   нет.
7. Отмена `CAN CAN` от отправителя: ошибка, недописанный файл удалён.
8. `rz` без имени и `rz > /x`: понятные ошибки, передачи нет.

#### Грабли

| Симптом | Причина | Решение |
|---|---|---|
| файл в несколько байт после заливки оказывается пустым | ACK на EOT уходил до `rz_flush`, а следующее открытие порта перезагружало плату | колбэк `finish` до ACK, тест на порядок |

| `rz > /x` отвечает «нужно имя файла» | проверка `argc` стояла раньше проверки перенаправления | проверять перенаправление первым: причина важнее симптома |
| `xsend.sh` не видит плату | открытие порта перезагружает чип, порт на секунду исчезает | переоткрывать в цикле до `ready`, как `serial-read.py` |
| после `xsend.sh` плата замолкает: порт есть, байтов нет, `reset.sh` не подключается | не прошивка и не протокол: файл на плате записан верно (проверено `stat` и `cat` после передёргивания). Причина — сброс из загрузчика по DTR/RTS, см. `docs/board.md` §5 | переподключить USB-кабель. В своих скриптах не сбрасывать чип из загрузчика, а выходить из него через `--before usb-reset` (как `fsdump.py` и `reset.sh`) |

### 06.11.2026. Разбор ФС на маке: `tools/fsdump.py`

**Файлы:** `tools/fsdump.py`, `docs/`.

**Проверки:** живая плата, дамп раздела `storage` (14 272 КБ), сверка с `df`
и с файлами в ФС.

**Задача.** Закрыть A9: формат BFS описан на диске байтами, значит содержимое
можно прочитать и тогда, когда прошивка не работает. Единственный инструмент,
который не зависит от нашей прошивки, — `esptool` над загрузчиком: он читает
flash, не исполняя наш код.

#### Почему чтение одним куском

Замерено: `esptool` отдаёт около 175 КБ/с и тратит примерно 6 секунд на каждый
запуск (сброс, синхронизация, загрузка заглушки). Восемь мелких чтений — это
48 секунд накладных, а полный раздел одним вызовом — 110 секунд при
согласованном снимке: пока идёт чтение, прошивка не работает и ничего не
меняет. Второй раз дамп не нужен — `--save` оставляет файл, `--read` разбирает
его мгновенно.

Сначала скрипт читает только таблицу разделов (0x8000, 3 КБ) — на 6 секунд, —
и уже из неё берёт адрес и размер `storage`. Размер из `partitions.csv` не
подставляется намеренно: таблицу могли переразметить, а файл в репозитории —
нет.

#### Что проверено

| Проверка | Результат |
|---|---|
| дерево ФС по дампу | `etc/`, `etc/rc` 225 Б — как `ls` на плате |
| `--super` против `df` | 13 занятых блоков (52,0 КБ) против «занято 52 КБ» на плате |
| файл 100 КБ через `-o` | совпал с исходником байт в байт |
| учёт блоков после 100 КБ | 39 блоков = 26 (файл + indirect) + 1 (rc) + 1 (etc) + 1 (/) + 8 (таблица inode) + 2 (суперблок) |
| дамп обрезан | предупреждение «дамп короче раздела», файлы за границей не читаются |
| не BFS / не тот файл | «раздел storage в дампе не найден», код возврата 1 |

Таблица разделов и суперблок на плате читаются с первого раза и каждый раз
одинаково — два чтения одного куска дали побайтно тот же файл.

#### Грабля: сброс из загрузчика убивает USB-JTAG

Первый дамп стоил трёх передёргиваний кабеля. Картина каждый раз одна: порт
`/dev/cu.usbmodem1101` есть, но ни байта в логе, `esptool` не подключается,
`reset.sh` падает с `Could not connect`. До этого то же случалось после
`pio run -t erase` и после `xsend.sh`, и оба раза списывалось на «USB-JTAG
иногда зависает».

Оказалось, дело не в загрузчике, а в способе выйти из него. Первый вывод был
неполным: короткое чтение (10 КБ) с `--after watchdog-reset` плата переживала
три раза из трёх, и рецепт записали в документацию. Следующий же полный дамп
раздела (96 с) с тем же `watchdog-reset` плату убил — значит, дело не в том,
кто именно сбрасывает чип, а в том, что сброс идёт **из** загрузчика.

Проверено на живой плате тем же полным дампом:

| Режим | Что с платой |
|---|---|
| `--after hard-reset` (сброс по RTS) | USB-JTAG мёртв, нужен кабель |
| `--after watchdog-reset` | короткое чтение переживает, полный дамп — нет |
| `--after no-reset`, затем `--before usb-reset --after no-reset read-mac` | поднимается сама, 2 раза из 2 |

Поэтому `fsdump.py` после чтения **не сбрасывает** чип (`--after no-reset`), а
потом отдельным вызовом выводит плату из загрузчика через USB-JTAG — тот же
приём, что в `tools/reset.sh`. Дороже на один запуск `esptool` (~6 с из 110),
зато плата живая без передёргивания кабеля. Сброс стоит в `finally`: если
чтение упало уже после входа в загрузчик, плату всё равно надо вернуть.

Записано в `docs/board.md` §5 — это свойство платы, а не проекта.

Урок на будущее: «проверено трижды» на коротком опыте не переносится на
длинный. Признак, который стоило заметить сразу, — в первом опыте читалось
10 КБ из 14 МБ, то есть проверялось совсем не то, что делает настоящий дамп.

Разметка строки живёт в `shell/hexdump.c` и проверена на маке: ошибка в ней
выглядит не как «не собралось», а как «колонки разъехались на неполной строке»,
и искать её пришлось бы глазами по экрану платы. Обещание ширины закреплено
тестом (`test_line_fits_known_width`), чтобы будущая правка не сломала его
молча.

Что решили сознательно:

- **Неполная строка дополняется пробелами в hex-части** — иначе ASCII-колонка
  прыгает на последней строке файла, и глаз цепляется за это раньше, чем за
  содержимое.
- **Отказ вместо обрезки.** `len == 0`, `len > 8`, маленький буфер и NULL
  возвращают 0 и ничего не пишут: обрезанная строка дампа сходит за настоящие
  данные.
- **Непечатаемое — точкой.** ESC особенно важен: попав в терминал как есть, он
  съел бы часть строки.

#### `less`: страница собирается в клетках, а не печатается сразу

Печать прямо в матрицу не оставляет пути назад: если строка не влезла в
остаток страницы, её начало уже нарисовано, и вернуться нечем. Поэтому страница
собирается в 16×53 клеток и рисуется одной операцией, а «назад» — это повторное
чтение потока с сохранённого смещения.

Разметка (`shell/pager.c`) переносимая и проверена на маке 19 тестами. Там же
пойманы три настоящие ошибки, которые на плате стоили бы вечера:

| Ошибка | Как выглядела бы |
|---|---|
| пустая строка внутри файла пропадала | текст съезжал, строки в файле и на экране расходились |
| табуляция у правого края считалась от неверной колонки | текст после таба съезжал влево |
| смещение следующей страницы бралось от буфера, а не от файла | после первой страницы «вперёд» показывал не то место |

Последняя ошибка повторилась уже на плате, в другом виде: у конвейера нет
`seek`, и «назад» сообщал об отказе, но листал **вперёд** — поток уже ушёл.
Показывать не ту страницу хуже, чем отказать, поэтому теперь отказ завершает
просмотр, а не подменяет данные.

#### Что решили сознательно

- **16 строк, а не 17.** Последняя строка экрана — состояние: без неё не видно
  ни того, что файл длиннее страницы, ни того, что дальше уже конец.
- **CRLF не показывается.** Файлы заливаются с мака, и `^M` в конце каждой
  строки сделал бы чтение бессмысленным.
- **Табуляция — восемь клеток, как в матрице.** Иначе один и тот же файл в
  `less` и в `cat` выглядел бы по-разному.
- **Управляющие байты — `?`.** Пропустить их значило бы сдвинуть текст влево.
- **Назад можно только у файла.** У конвейера нет ни дескриптора, ни смещения;
  перечитать ступень заново — это уже не про `less`.
- **Кольцо на 256 смещений.** Растущий список на 14 МБ файла — 8700 записей по
  4 байта, и он упёрся бы в память ради того, чего никто не делает.
- **Страница дублируется в USB построчно.** У терминала мака нет нашего
  экрана, и молчание сделало бы `less` непроверяемым: ни в логе, ни в
  `pio device monitor` не было бы ничего.

при чтении кода рядом с местом, где они ломаются:

только залить с мака и прочитать, но и набрать на устройстве. До этого
единственным способом что-то записать был `echo текст > файл` — одна строка
без правки.

#### Ядро отдельно от экрана — та же граница, что у `pager`

Текст, курсор, клавиши, окно и поиск живут в `shell/editor.c`; модуль не
знает ни про матрицу, ни про VFS, ни про `soc/...`. Наружу он отдаёт клетки
строки, позицию курсора и события (`ED_CHANGED`, `ED_SAVE`, `ED_FIND`,
`ED_QUIT`, `ED_QUIT_DIRTY`, `ED_BELL`, `ED_NONE`), а файл и экран делает
`src/shell/main.c`.

Причина та же, что у `pager` и `hexdump`: ошибки редактора стоят вечера на
плате и секунды на маке. «После Enter пропала строка», «кириллица стёрлась
по половине», «стрелка вниз увела курсор влево» — на 53-колоночном экране
каждый такой случай ловится глазами, а в `test_editor` текст и позиции
сравниваются напрямую. 39 тестов: CRLF и BOM при загрузке, склейка и разрыв
строк, табуляция, горизонтальная прокрутка, вертикальная, кириллица, битый
UTF-8, поиск с переходом в начало, подтверждение выхода, полный буфер.

#### Текст — один буфер, курсор — байты, наружу — клетки

Текст хранится одним куском UTF-8 с `\n`, а не массивом строк. Массив строк
на 64 КБ потребовал бы индекса на несколько тысяч записей и отдельного
решения, что делать при вставке; один буфер даёт лишний проход на нажатие, зато
нет второго источника истины, который однажды разойдётся с текстом. Строка
ищется проходом от начала: 64 КБ проходятся за микросекунды, а человек делает
единицы нажатий в секунду.

Курсор — смещение в байтах (так проще резать буфер), наружу отдаётся в клетках
(`ed_cursor_screen`, `ed_line_col`): «Ж» — два байта и одна клетка. То же
правило, что в `lineedit`.

#### Решения, которые лучше было принять до кода

- **Длинная строка прокручивается по горизонтали, а не переносится.**
  Перенос, как в `less`, сделал бы стрелки вверх-вниз ходом по экранным
  строкам, и «одна строка файла — одна стрелка» перестала бы работать.
  `ed->left` сдвигает окно так, чтобы курсор был виден.
- **Сохранение — через `.tmp`.** У BFS нет атомарной замены: `bfs_rename`
  отказывает, если цель существует. Поэтому сначала целиком пишется
  `<имя>.tmp`, потом старый файл удаляется и `.tmp` переименовывается. Сбой
  посреди записи оставляет целый старый файл и мусорный `.tmp`; сбой между
  `unlink` и `rename` — только целый `.tmp`. Длинное имя, в которое суффикс не
  влезает (`BFS_NAME_MAX` = 24), уходит в `.edit.tmp` в том же каталоге.
- **Без отмены и без выделения.** Только движение, вставка, удаление,
  `Enter`/`Tab`, поиск, сохранение, выход. Отмена — это стек изменений и
  границы групп набора; для закрытия A7 их цена не оправдана.
- **64 КБ на файл** в PSRAM (fallback в SRAM). Больше — читается начало, в
  строке состояния честно написано «файл больше 64 КБ — читаю начало», и
  `Ctrl-S` для такого файла **отказывает**: запись затёрла бы хвост, который
  в буфер не влез. Молча обрезать файл нельзя, а листать его с диска редактор
  не умеет: вставка в середину требует сдвига хвоста.
- **На маке — альтернативный экран `CSI ?1049`, на плате — `text_clear()` и
  `present_dirty()`.** Мак после выхода возвращает прежний текст терминала,
  плата чистит матрицу и печатает приглашение. Строки перерисовываются только
  изменившиеся (сравнение с `s_edit_prev`): полная перерисовка на нажатие —
  это 16 полос по 6 КБ через SPI.
- **`Ctrl-Q`/`Ctrl-C` на изменённом файле просят подтверждение.** Первое
  нажатие даёт `ED_QUIT_DIRTY`, второе выходит; любая другая клавиша снимает
  взвод, иначе случайный `Ctrl-Q` через минуту выбрасывал бы из редактора.
- **Кнопка G0 отдаёт `0x03`, а не `'q'`.** `q` в редакторе — обычная буква.
  Общая функция чтения клавиши (`console_key`) теперь одна на `less` и `edit`.

#### Что поправили по ходу

- **`move_down` показывал лишнюю строку.** Для файла, кончающегося переводом
  строки (`"a\n"`), курсор уезжал на пустую строку за концом, и номер строки
  расходился с тем, что показывает `less`. Условие `end + 1 >= len` — отказ.
- **`console_key` выбрасывал накопленный ввод.** Хвост ввода нужно выбросить
  один раз на входе в полноэкранный режим (после `Enter` остаётся перевод
  строки), а не перед каждым нажатием: в редакторе накопившиеся байты — это
  набранные буквы, и защита от застрявшего `Enter` съедала бы их по восемь за
  нажатие. Теперь `console_key_ex(flush)`: `less` чистит всегда, `edit` и
  строка поиска — только на первом нажатии.
- **Строка состояния не должна занимать 53-ю клетку.** 53-я вызывает
  `newline()` и на последней строке экрана прокручивает весь экран — редактор
  «поехал» бы вверх на каждое нажатие. Поэтому в строке состояния и в строке
  поиска не больше `TEXT_COLS - 1` клеток.

Заодно в `help` появилась строка `edit`, а правило «команд, которые владеют
консолью, две» в `AGENTS.md` исправлено на три.

**Задача.** До этой вехи время в системе было только монотонным: `uptime`
рос, а календаря не было вовсе, и `ls` показывал размер без даты. Метка
времени файла — не украшение: без неё нельзя ни понять, что изменилось
последним, ни проверить, что `edit` действительно сохранил файл.

#### Главное решение: часы — это точка отсчёта плюс счётчик

RTC-периферия в ESP32-S3 есть, и соблазн взять её велик. Но у платы **нет
батарейки на VBAT**: при отключении USB RTC-домен сбрасывается вместе со всей
своей памятью. То есть преимущества перед обычным счётчиком нет, а кода
становится больше — медленные часы на 150 кГц, регистры, отдельная
инициализация.

Поэтому часы устроены проще и честнее:

```
clock_now = base_unix + (basalt_uptime_us() - base_mono) / 1000000
```

Второго источника времени в системе не появляется: часы не «тикают» сами, а
считаются от того же счётчика, что и `uptime`. Отсюда бесплатно выходит, что
время не может уехать относительно `sleep` и замеров.

Отдельный флаг `clock_synced` — не формальность. Без него «часы не
устанавливали» и «сейчас 1 января 1970-го» выглядели бы одинаково, и `ls -l`
показывал бы у новых файлов прошлый век. Теперь `date` прямо говорит
«календарь не установлен», а `ls -l` печатает прочерк.

#### Где хранится время и почему в файле

`/etc/clock` — обычный файл ФС с одной строкой `YYYY-MM-DD HH:MM:SS`.
Читается при старте **до** `/etc/rc` (иначе `ls -l` в стартовом файле дал бы
прочерк), пишется в `date set` и **перед `reboot`**: иначе после
перезагрузки часы поднимались бы с момента установки времени, а не с момента
выключения, и отставали бы на всю сессию.

Соблазн был завести отдельный раздел или поле в суперблоке. Не стали: файл в
ФС можно посмотреть (`cat /etc/clock`), поправить (`edit`), удалить (`rm`) и
залить с мака теми же командами, что и всё остальное. Отдельный формат
потребовал бы отдельного кода чтения и отдельного способа починить его, когда
он испортится.

Формат — `cal_text`, тот же, что печатает `date`. Один формат на запись и
чтение: разъехаться им негде.

#### Время в ФС: даёт вызывающий, а не ФС

Соблазн позвать `basalt_uptime_us()` прямо из `bfs.c` понятен, но он ломает
границу: `bfs.c` перестал бы собираться на маке (там нет `soc/...`), и 37
хостовых тестов ФС, включая обрыв питания, стали бы невозможны. Поэтому
наоборот:

- поле `mtime` в inode **уже было** в формате (128 байт, `fields[2]` в
  `tools/fsdump.py`), просто не заполнялось — версию ФС поднимать не нужно,
  CRC суперблока оно не трогает, а старые образы прочтут там ноль, что честно
  означает «время неизвестно»;
- `bfs_set_now(fs, unix)` и `vfs_set_now(unix)` передают значение внутрь;
- `bfs_create`, `bfs_mkdir`, `file_write`, `file_truncate` ставят метку.

`now == 0` **не затирает** уже известную метку. Иначе первый же старт без
`/etc/clock` (например, после `rm /etc/clock`) обнулил бы даты у всех файлов
при первой записи в них. Ноль значит «я не знаю, который час», а не «время
равно нулю».

Метка ставится и каталогам: в каталог содержимое пишется теми же
`dir_add`/`dir_remove`, и «когда менялся этот каталог» — такой же вопрос, как
про файл.

#### Календарь: формулы C++20, а не цикл по месяцам

Перевод «секунды с 1970-го» в дату пишут все и все ошибаются: то 1900-й
високосный, то февраль в 2000-м, то день недели съезжает на единицу. Поэтому
в `calendar.c` — формулы `civil_from_days`/`days_from_civil` (эра в 400 лет),
те же, что в `std::chrono::year_month_day`: они проверены на всём диапазоне, а
не на паре удобных дат.

Диапазон ограничен **1970–2106** — это границы 32-битного счётчика секунд.
За ними `cal_to_unix` отказывает: молча подставить соседний день хуже, чем
сказать «негодная дата», потому что опечатку в команде тогда никто не увидит.

Разбор текста понимает ровно **один** формат: `ГГГГ-ММ-ДД`, разделитель `T`
или пробел, `ЧЧ:ММ`, секунды необязательны, хвостовые `\r\n` допустимы (файл
на маке). Не «гибкий», а именно один: стоит разрешить `07.11.2026`, и однажды
окажется, что половина файлов на плате в одном порядке, а половина в другом.

#### Что ещё появилось

- **`ls -l`** — флаг отдельным словом (`-la` не поддерживается, пока других
  флагов нет: один флаг не стоит разбора строки). Дата `07.11 18:42`, размер
  в колонку из 6 знаков. При неизвестном времени — `--.-- --:--` **той же
  ширины**: иначе колонка разъезжается ровно там, где время неизвестно.
- **`stat`** показывает время изменения или честно говорит, что оно
  неизвестно.
- **`date`** без аргумента — дата, день недели и «(с запуска N с)». Возраст
  часов печатается не из любопытства: если время поднято из `/etc/clock`,
  дата отстаёт на время простоя, и знать это важно.
- **`sleep`** — `5` значит пять секунд, как в POSIX; плюс `300ms`, `1m30s`,
  `1h`. Ноль отвергается: `sleep 0` почти всегда опечатка (`sleep 0.5` без
  дробной части). Сон **непрерываемый**, и это осознанно: планировщика нет,
  консоль читается только в главном цикле, и изображать прерывание через
  кнопку, которую никто не нажмёт, было бы враньём.
- **`alarm`** — ждёт, но **с отменой** по G0 или `Ctrl-C`, затем 5 секунд
  мигает подсветкой и шлёт BEL в терминал. Пищалки на плате нет (`docs/board.md`),
  поэтому сигнал визуальный; мигание, а не текст, потому что его видно с
  другого конца стола. Отмена есть потому, что будильник на минуту вперёд,
  который нельзя прервать, раздражает сильнее, чем помогает.

#### Что поправили по ходу

- **`str_app` и `snprintf`.** Первая версия `date set` склеивала дату с
  временем через `snprintf`, что тянет newlib ради одной операции и ломает
  правило «вывод чисел без printf». Заменили на уже имеющийся `str_app`.
  При этом легко ошибиться ещё раз: `str_app` **сам** ставит ноль за последним
  символом, поэтому склейка обязана идти через возвращённую позицию
  (`at = str_app(...)`), а не через `at + 1` — такой шаг оставил бы ноль посреди
  строки, и `cal_parse` увидел бы только дату и отказал.
- **Прототипы часов.** `cmd_reboot` сохраняет время перед сбросом, а
  определения `shell_now`/`fs_save_clock` стоят ниже по файлу. Пришлось
  поднять объявления к `s_halt` — иначе компилятор видел неявное объявление
  `int()` и ругался на конфликт с `bool`/`int`.
- **Лишняя `}` в `bfs.c`** после переписывания `bfs_stat` — поймалась сборкой
  на маке сразу, на плате это стоило бы вечера.
- **`NULL` в `clock.h`.** `clock.c` использует `NULL`, а заголовок не включал
  `<stddef.h>`: на хосте это ошибка, на xtensa проходило. Тесты на маке
  поймали первыми.
- **`env:fs` перестал собираться.** Щуп ФС зовёт `bfs_stat`/`bfs_readdir`
  напрямую, а сигнатуры сменились на структуру. Это ровно то, ради чего
  `make verify` собирает все 14 env: сломанный щуп, который собирается только
  вручную, обнаруживают через неделю. Заодно щуп теперь ставит фиксированную
  метку `1794076923` перед записью и проверяет её после перемонтирования —
  лучшего места проверить, что `mtime` действительно лёг на диск, нет.
- **`tools/fsdump.py` показывает время.** Раз у файлов появилась дата, разбор
  дампа без платы должен её печатать: иначе `ls -l` на экране и дамп на маке
  отвечали бы на один вопрос по-разному. Формат тот же, включая прочерк.
- **Щуп ФС не усекал `/etc/rc`.** На пустом разделе это не видно, а на живой
  плате там уже лежит `/etc/rc`, написанный шеллом, и длиннее нашего. Запись
  с нуля без усечения оставила хвост, и сверка размера ругалась не на ошибку
  ФС, а на этот хвост. Поймалось при первом же прогоне `make fs` после
  переподключения кабеля — ровно поэтому щупы и запускают на железе.

| Что | Результат |
|---|---|

**Задача.** До этого шага в системе не было асинхронности вообще: всё шло
циклом событий, и `sleep` был ожиданием в этом цикле. Тик — первое, что
происходит **вне** обычного потока управления, и без него не бывает ни
вытеснения, ни таймаутов.

#### Решение: уровень 3, а не уровень 1

Соблазн взять уровень 1 велик: он маскируется сам и «самый внешний». Но на
XEA2 уровень 1 устроен хуже остальных:

- **Регистра `EPS_1` не существует.** Аппаратура сохраняет `PS` только для
  уровней 2..7 (`EPS_2..EPS_7`). Обработчику уровня 1 приходится сохранять
  `PS` и `EPC1` вручную и жить с `PS.EXCM=1` — то есть без вызова C.
- **У уровня 1 нет своего слота.** Прерывание приходит либо в слот исключения
  ядра (`0x300`), либо в пользовательский (`0x340`) — в зависимости от режима
  прерванного кода, и это пришлось бы разбирать по `EXCCAUSE` в обоих.
- **Ошибка в обработчике уровня 1 не даёт отчёта вообще.** Проверено на
  плате: плата замолкает до ручного сброса, в логе пусто.

Уровень 3 (`CCOMPARE1`, линия 15, слот `0x1C0`) даёт готовый слот, готовые
`EPS_3`/`EPC_3` и возврат одной инструкцией `rfi 3`.

#### Главная грабля: обработчик не пишет на стек прерванного кода

Первый вариант обработчика выделял кадр на стеке: `addi a1, a1, -24` и
`s32i` по смещениям 0/4/8/12. Собралось, тик работал, частота была верной —
а `crash` через раз давал не слот 9, а слот 10 (двойное исключение).

Причина нашлась по `DEPC`, которого до этого в отчёте не было: `DEPC
0x4037588f` → инструкция `s32e a4, a0, -32` в слоте **переполнения окна 8**,
где `a0` прочитан из `[a1-12]` как мусор.

Область `[sp-16 .. sp-4]` — это спилл окон ABI: там аппаратура хранит
регистры предка, когда окно переполняется, и обработчик переполнения читает
оттуда указатель кадра. Наш кадр 24 байта затирал ровно `[sp-12]`. Следующий
вызов функции в прерванном коде отдавал управление обработчику переполнения,
тот брал мусор как указатель и падал записью по случайному адресу.

Проявлялось это в одном прогоне из трёх — то есть выглядело как случайность.
Отсюда правило на будущее: **обработчик прерывания не трогает стек
прерванного кода вообще**.

Регистры теперь уходят в спецрегистры: `a0` на входе в уровень 3 аппаратура
уже сохранила в `EXCSAVE_3` (так делает и IDF в `_Level3Vector`), остальные
три — в `EXCSAVE_4..6`. Уровни 4..7 не используются, поэтому их `EXCSAVE`
свободны. Своя память вместо стека возможна потому, что обработчик не
вкладывается сам в себя: уровень 3 маскируется на время обработки.

#### `DEPC` в кадре паники

Без него отчёт двойного исключения врёт: `EPC1` остался от первого
исключения, а настоящий адрес сбоя аппаратура кладёт в `DEPC`. В отчёте
теперь есть строка `DEPC ... адрес сбоя внутри обработчика (это искать)` — и
именно она дала точную улику. Заполняется всегда, но печатается только для
слота 10: при остальных причинах там чужое значение.

#### Период берётся из конфигурации, а не предполагается

`CCOUNT` считает такты ядра, поэтому период = частота × секунды. На 80 МГц
то же число означало бы вдвое медленный тик. Частота берётся из
`CONFIG_ESP_DEFAULT_CPU_FREQ_MHZ`, а период передаётся из C в ассемблер через
поле состояния — так `vectors.S` не зависит от `sdkconfig`, и число живёт в
одном месте.

#### `wsr intset` не работает

Разрешение линии сделано чтением-или-записью `INTENABLE`, а не `wsr intset`.
В XEA2 `intset` — это алиас регистра `INTERRUPT`, а он только для чтения:
запись в него молча игнорируется. Проверено на плате: `wsr intset` собрался и
выполнился, бит в `INTENABLE` остался нулевым, линия просила обслуживания
(`INTERRUPT != 0`), а обработчик не вызывался.

#### `rsil` и clang

`rsil` требует литерал уровня, и GCC-ное ограничение `"I"` clang не знает
вообще: `invalid input constraint 'I' in asm`. Заменено на `"n"` — его
понимают оба компилятора, и в коде всё равно остаётся литерал (`rsil a8, 2`).

#### `sleep` пока не прерываемый

Тик есть, но вытеснения нет: `sleep` по-прежнему ждёт в цикле. Изображать
прерывание было бы враньём — прерывать нечем, пока нет второй задачи. Это
шаг 2.

### 07.11.2026. A6, шаг 1.5: сон до прерывания вместо холостого цикла

**Файлы:** `arch/xtensa/idle.c/.h` (новые), `src/CMakeLists.txt`,

**Проверки:** `pio test -e native` — 391 тест; `make verify` — 14 env SUCCESS;

сборка `env:shell` — RAM 86 784 Б (26.5 %), flash 227 801 Б (10.9 %);
`./tools/smoke.sh shell` — все строки на месте.

**Проверено на живой плате 07.11.2026:** `top` — «сон 2509 раз» при 2548
тиках (одно засыпание на тик); `sleep 2` и `sleep 500ms` просыпаются вовремя;

**Задача.** Главный цикл шелла заканчивался `basalt_delay_us(500)`: он честно
ждал полмиллисекунды, но всё это время крутился на счётчике. Для 500 мкс это
незаметно, для `sleep 10` — десять секунд полной загрузки процессора без
единой полезной работы. Тик к этому моменту уже есть, значит ждать можно не
опросом, а сном до прерывания.

#### Механизм

`waiti` останавливает ядро до ближайшего прерывания и продолжает с той же
инструкции. Отсюда весь цикл: проверить условие — уснуть — проснуться —
перепроверить. Перепроверка обязательна, потому что `waiti` возвращает
управление на **любом** прерывании, а не только на том, которого ждём.

Ожидание срока сделано как `while (basalt_uptime_us() < until) waiti;`, а не
как «поспать один раз до срока»: одно пробуждение может случиться раньше
из-за чужого прерывания, и тогда срок надо дождаться повторно.

#### Главная ловушка: в waiti можно погасить тактирование

На ESP32-S3 `waiti` умеет останавливать тактирование ядра — за это отвечает
`SYSTEM_CPU_WAIT_MODE_FORCE_ON` в `SYSTEM_CPU_PER_CONF_REG`, и IDF его
**очищает** при `cpu_waiti_clk_gate = 1`.

Для нас это смертельно, и не по общим соображениям, а по конкретной причине:
тик работает от `CCOUNT`, а `CCOUNT` считает **такты ядра**. Погасили
тактирование — счётчик встал, `CCOMPARE1` никогда не совпадёт, прерывание не
придёт, и `waiti` уснёт навсегда. Плата при этом не паникует: она просто
замолкает, и внешне это неотличимо от зависшего USB-JTAG.

Спасает то, что у бита сброс `1'b1`, а IDF-шную инициализацию RTC мы не зовём.
Но полагаться на состояние после сброса нельзя — загрузчик мог его тронуть.
Поэтому `basalt_idle_init()` ставит бит явно. Заодно это значит, что
**настоящего энергосбережения здесь нет**: тактирование остаётся, ток заметно
не падает, выигрыш только в отсутствии пустых инструкций. Настоящий сон
(гасить тактирование, просыпаться от `SYSTIMER`) — отдельная работа, и она
имеет смысл только когда тик перестанет быть единственным источником
пробуждения.

#### Почему `waiti 2`, а не `waiti 0`

Операнд `waiti` — уровень, до которого поднимается `PS.INTLEVEL` на время
ожидания. Тик у нас на уровне 3 и работает при `INTLEVEL = 2`
(`basalt_int1_init` опускает порог на уровень ниже). Значит `waiti 2` будит
ровно тик, а уровни 1–2 остаются замаскированными. `waiti 0` разрешил бы и
их, а у нас все неиспользуемые уровни ведут в панический обработчик: любое
случайное прерывание от периферии уводило бы систему в панику.

#### Сон доказан счётчиком, а не словами

«Сон включён» — это утверждение о коде. Чтобы оно стало утверждением о
плате, добавлен `basalt_idle_waits()` и строка «сон N раз» в `top`. При
простое число засыпаний должно быть примерно равно числу тиков; если оно
заметно больше — работу будят чужие прерывания, если ноль — сон не работает.
Замерено: 2509 засыпаний на 2548 тиков, то есть одно на тик. До этой правки
счётчик был бы нулевым.

#### Ввод при сне не теряется

Главный риск: USB-прерывание у нас не разрешено (консоль опрашивается), а
просыпаемся мы раз в 10 мс. FIFO у USB-JTAG — 64 байта. Значит длинная
вставка из буфера обмена могла бы упереться в FIFO и потерять хвост.

Проверено отдельным скриптом: строка в **200 байт** отправлена одним
`write`, без пауз, и вернулась целиком (серии по 210 `x` — эхо плюс ответ).
Причина, по которой это работает: хост получает NAK, пока FIFO полон, и
повторяет передачу, а не выбрасывает данные. Но полагаться на это в общем
случае не стоит: когда появится своё прерывание USB, опрос уйдёт и вопрос
закроется сам.

Шаг 2 — переключение контекста. Требование к нему, сформулированное после
шага 1: регистры задачи сохраняются в её собственную память, а не «на стек
сверху», иначе повторится порча спилла окон. Сон из этого шага станет
основой: задача, которой нечего делать, будет отдавать процессор, а не
крутиться.

### 07.11.2026. A6, шаг 2: переключение контекста, кооперативный вариант

#### Что это и зачем

Задача — это функция, у которой свой стек. «Переключение контекста» значит:
сохранить, где именно остановилась одна функция, взять стек другой и
продолжить её с того места, где она остановилась раньше. Для пользователя
это выглядит как «две программы идут одновременно»: шелл ждёт ввода, а
фоновая задача в это время считает.

Без этого ОС — просто один длинный цикл. Всё, что должно работать «само»
(часы, батарея, `beep`), пришлось бы вставлять в этот цикл вручную.

#### Почему кооперативный, а не вытесняющий

Вытесняющий вариант — «переключать по тику, не спрашивая задачу». Он лучше:
зациклившаяся задача не может занять процессор навсегда. Но на Xtensa он
означает смену стека **из обработчика прерывания**, а там окна регистров.
Обработчик тика уже научен не трогать стек прерванного кода (шаг 1) именно
потому, что эта область принадлежит механизму окон.

Кооперативный вариант проще: задача сама зовёт `basalt_task_yield()` в
удобном месте, обычно в верхнеуровневом цикле. Цена — зацикливание одной
задачи блокирует остальные. Это записано в ROADMAP как незакрытая часть
шага 3, а не спрятано.

#### Две вещи, которые оказались не нужны

**64 регистра сохранять не надо.** В оконном ABI `a1` — это регистр своего
окна. `retw` возвращает вызывающему его `a1` сам, из его кадра на стеке.
`SPILL_ALL_WINDOWS` раскладывает живые окна по кадрам предков на стеке
задачи. Поэтому на задачу сохраняются ровно два числа: указатель стека и
`PS`.

**`WINDOWSTART` сохранять не надо — и это неочевидно.** Первая версия
сохраняла маску живых окон на задачу (так делает `STACK_CTX` в
`espcoredump`). Плата замолкала ровно при возврате, каждый раз. Причина:
`retw` возвращается в окно предка через недобор и **восстанавливает
регистры из его кадра** — то есть маска окон и кадры на стеке обслуживают
друг друга. Готовая маска обходит механизм, который эти же кадры и
обслуживает. В `_frxt_dispatch_sol` FreeRTOS `WINDOWSTART` не трогает.

#### Три ошибки, каждая выглядела как «плата молчит»

**1. Задача писалась не в тот слот.** В `basalt_task_create` было
`s_tasks[s_count]` вместо `s_tasks[slot]`. Слот ищется как «первый
завершённый», и при его занятии `s_count` уже больше `slot` — задача уезжала
в чужой слот, а занятый оставался нулевым. Дальше `top` звал
`strlen(info.name)` при `name == NULL` и падал: причина 28, `EXCVADDR 0`,
`EPC1` в ROM (`strlen`), `A0` в `cmd_top`. Самое коварное — переключение при
этом не выполнялось ни разу, а лог выглядел как «упало переключение».

**2. `CALLINC` складывался, а не выставлялся.** Код был
`(ps & ~0x1F) | 2 | 0x10000`. Замеренный `PS` вызывающего уже содержал
`CALLINC=2`, и «или» давало 3 — то есть call12. При `CALLINC=3` пролог
раскладывает окно как после call12 и настраивает `a13`, а вызываемый по
call8 ищет свой указатель стека в `a9`. Задача получала в `a1` мусор и
падала в слоте переполнения окна. Правильно — **снимать** `CALLINC` и `OWB`
маской `~0x00030F1F`, а не выставлять поверх.

**3. Первая задача входила переходом `jx`, а не вызовом.** Это работало
ровно до первого вызова внутри задачи. У оконного ABI звенья цепочки кадров
строят аппаратура и обработчики переполнения: указатель стека предка лежит в
кадре потомка по смещению `-12`. При переходе предка нет, обработчик берёт
оттуда закраску стека и пишет регистры по адресу вида `0xC3C3C3A3` —
`EXCVADDR` в панике был ровно `0xC3C3C3A3`, то есть `TASK_PAINT - 32`.
Лечится двумя вещами: стек новой задачи готовится как в `SET_STACK`
(`sp = top - 64`, `*(sp-12) = top`), а вход делает `callx8`.

#### Ловушка чтения, которая уже стоила правки в ассемблере

`tickrate` печатал `PS` через `out_u64` — то есть **десятичным** после «0x».
`PS 0x395042` в логе означало `0x60722`, где `WOE=1`, `UM=1`, `CALLINC=2` —
нормальное рабочее состояние. Прочитав это как «WOE=0», я решил, что задачи
идут без окон, и добавил в `tasks.S` «нормализацию PS». Правка была основана
на ошибке чтения и откачена. Сейчас `tickrate` печатает `INTENABLE`,
`INTERRUPT` и `PS` через новый `out_hex` с фиксированным числом знаков.

### 08.11.2026. A6, шаг 3: сон задачи, сон системы и доли процессора

Шаг начался с находки, которая была в отчёте шага 2 и которую легко было
принять за норму.

```
задач 2
  * главная выполняется   стек 1968/8192 Б (24%), смен 128557
    пульс готова   стек 252/4096 Б (6%), смен 128557
переключений 257114
uptime 4 с, тиков 106 (100 Гц)
сон 0 раз
пульс 128557 итераций
```

**«Сон 0 раз».** В шаге 1.5 главный цикл уходил в `waiti`, когда отдавать
процессор было некому. Шаг 2 добавил `basalt_task_yield()` перед этим, и он
возвращает `true`, пока есть вторая готовая задача. «Пульс» был готов
постоянно — значит, `basalt_idle_wait()` не выполнялся ни разу, и сон из
шага 1.5 фактически выключился. Плата при этом работала: 150 тысяч
переключений в секунду вхолостую незаметны на глаз, но это ровно то, чего шаг
1.5 хотел избежать.

#### Что сделано

1. **Сон задачи** — `basalt_task_sleep_ms(ms)`. Задача переходит в
   `BASALT_TASK_BLOCKED`, получает срок `wake_at` и снимается с выбора.
   Остальные продолжают работать.
2. **Сон системы** — `basalt_task_wait()`. Разбудить просроченных и уйти в
   `waiti`. Зовётся, когда `yield` вернул `false`, то есть готовых нет.
3. **Пробуждение по сроку** — `basalt_task_wake_due()`, внутри
   `basalt_task_yield()`.
4. **Доли процессора** — `basalt_task_cpu_sample()`, раз в полсекунды из
   главного цикла. Время копится по `basalt_uptime_us()` и списывается на
   задачу при смене; доля сна — то, что осталось от 100 %.
5. **`sleep` в шелле** переведён с `basalt_idle_ms` на
   `basalt_task_sleep_ms`: раньше он останавливал всю систему.
6. **Вторая фоновая задача** «редкая» с периодом 1 с — чтобы в `top` было
   видно, что срок у каждой задачи свой.

#### Почему пробуждение в `yield`, а не в главном цикле

Главный цикл — не единственный, кто ждёт. `basalt_task_sleep_ms` крутится
внутри задачи, и до главного цикла управление не доходит, пока задача спит.
`waiti` в этом состоянии не разбудит никого: `wake_due` зовут выполняющиеся
задачи, а их нет.

В обработчик тика пробуждение тоже не поставить: обработчик не зовёт функций C
и не пишет на стек прерванного кода (см. JOURNAL от 07.11.2026). `yield` —
единственное место, которое проходит каждый и там же пересчитывается «кто
готов». Цена — обход таблицы (максимум четыре строки) на каждое переключение.

#### Ошибка, найденная разбором до платы

`basalt_task_exit` при отсутствии готовых задач уходил в `waiti` навсегда. До
шага 3 это было почти недостижимо: готовых не оставалось только если все
завершились. С шагом 3 появилось новое состояние — «все спят, ждут срока», и
в нём разбудить их некому: та задача, которая должна была проснуться, уже
завершилась.

Теперь `exit` крутится в цикле «выбрать следующего — если нет, поспать» через
`basalt_task_wait()`, который сам зовёт `wake_due`. Проверено на плате
временной правкой (`basalt_task_exit` после второй итерации «редкой»):

```
top
  * главная выполняется   стек 2000/8192 Б (24%), смен 32, 0%
    пульс спит   стек 284/4096 Б (7%), смен 33, 0%
    редкая завершена   стек 272/4096 Б (7%), смен 2, 0%
переключений 67, сон 100%
uptime 9 с, тиков 665 (100 Гц)
засыпаний 664 раз
пульс 432 итераций (10 мс), редкая 2 (1 с)
```

Система продолжила работать: «пульс» вырос с 432 до 768 итераций, «редкая»
осталась завершённой.

#### Почему проценты по времени, а не по переключениям

Первая версия считала долю как `switches` задачи к сумме `switches` всех
задач. Это неверно при разной цене итерации: главная за один круг читает USB,
рисует экран и опрашивает кнопки, а «пульс» делает `+= 1`. При равенстве
переключений вышло бы 50/50, и это выглядело бы как ошибка учёта.

Теперь `switch_to` и `basalt_task_cpu_sample` списывают прошедшее время на ту
задачу, которая работала. Время сна копится отдельно в `s_idle_us` и в
интервале участвует, поэтому сумма «задачи + сон» = 100 %.

Отдельно пришлось не отдавать остаток от округления задачам: он и есть сон.
Сначала остаток уходил последней задаче с ненулевой долей, и «сон 98 %» при
сумме долей задач 2 % не сходилось. Теперь остаток — сну.

#### Два разных «сна» в отчёте

В `top` теперь:

```
переключений 66, сон 10%
засыпаний 61 раз
```

Это разные вещи, и путать их нельзя: «сон M %» — доля времени в `waiti` за
последний интервал, «засыпаний N раз» — счётчик входов в `waiti` за всё
время (он же показывает, что сон из шага 1.5 вернулся). До правки обе строки
назывались «сон», и в одном отчёте стояло «сон 98 %» и «сон 65 раз».

#### Переносимая часть и тесты

`arch/xtensa/sched.c` — `sched_pick`, `sched_next_wake`, `sched_wake_due`.
Только массивы состояний и сроков, ни одного регистра, поэтому проверяется на
маке: `test/test_sched`, 17 тестов. Ошибки здесь тихие: задача, выбранная
дважды подряд, выглядит как «работает медленнее», а не выбранная ни разу — как
«зависла».

Отдельно проверена граница `wake_at == now` — срок наступил:

```c
// Срок ровно `now` уже наступил. Строгое `<` оставило бы задачу спать до
// следующего тика без причины - это и есть тот случай, который проверяем.
TEST_ASSERT_EQUAL_size_t(1, sched_wake_due(st, wake, 1, 1000));
```

И спящая задача с `wake_at == 0`: такой срок не разбудит никто, поэтому
`sched_next_wake` её игнорирует, а `sched_wake_due` не будит. Иначе она либо
задавала бы «ближайший срок 0» (система решила бы, что просыпаться некому),
либо просыпалась бы немедленно и занимала процессор навсегда.

### 08.11.2026. A6, шаг 4: кадр тика и полный контекст прерванной задачи

Первый кусок вытеснения — и намеренно только первый. Самой смены задачи из
тика здесь ещё нет; проверяется то, без чего она невозможна.

#### Зачем это вообще нужно

До этого шага «параллельность» держалась на вежливости: задача отдаёт
процессор сама, вызвав `basalt_task_yield()`. Пока все так делают, всё
работает. Но если одна задача зациклится — например, в ней появится `while`
без выхода или тяжёлый расчёт, — остальные не получат процессора никогда.
Дисплей замрёт, шелл не отзовётся на ввод, и отличить это от зависания
железа будет нечем.

Вытеснение означает: раз в 10 мс приходит тик и **сам** решает, не пора ли
отдать процессор другой задаче. Задаче больше не нужно быть вежливой.

#### Почему это делается в четыре приёма, а не за один вечер

Чтобы сменить задачу из прерывания, нужно одновременно: сохранить всё
состояние прерванной задачи, сбросить окна регистров именно в её стек, не
затереть область, которой пользуется аппаратура, и вернуться через `rfi 3`
с чужим `PS`. Ошибка в любом из этих мест выглядит не как «не собралось», а
как молчащая плата — и искать её придётся без единой подсказки.

Поэтому шаг 4 — только сохранение: обработчик тика кладёт на стек прерванной
задачи полный кадр и сбрасывает окна, но задачу не меняет и возвращается в ту
же. Всё, что могло сломаться в записи, ломается здесь — и видно сразу.

#### Что уже было и чего не хватало

Обработчик тика с шага 1 прятал четыре рабочих регистра в `EXCSAVE_4..6` и
стека не касался вовсе — этого хватало, чтобы считать тики. Для вытеснения
этого мало: сохранять надо регистры задачи, её `PS`, `PC`, `SAR` и регистры
циклов, а «своей памяти» у прерывания нет. Значит, кадр на стеке задачи —
единственный вариант.

#### Решение: кадр свой, а не `XtExcFrame` из IDF

Соблазн взять готовую раскладку IDF (`XtExcFrame`) есть, и он плохой. В
IDF-шном кадре 192 байта: там есть место под `exccause`, `excvaddr` и 36 байт
состояния сопроцессоров, которых у нас нет. Нам нужны `PS`, `PC`, `a0` и
`a2..a15`, `SAR` и три регистра циклов — это 112 байт. Меньше кадр — меньше
шансов, что стек задачи в 4 КБ кончится в самый неудобный момент, а задача
может быть прервана на любой глубине вызова.

Формат кадра — наше дело: его читает и пишет только наш код. Из паники кадр
прерывания не восстанавливают, а в отчёт паники он тоже не попадает.

#### Почему верхние 16 байт кадра — не наши

Это самое важное место шага, и оно уже один раз стоило вечера на шаге 1.

Область `[sp-16 .. sp-4]` над указателем стека — не свободная память. Это
спилл окон ABI: туда аппаратура кладёт регистры предка, когда окно
переполняется, и обработчик переполнения читает оттуда (через `[a1-12]`)
указатель кадра предка. Кадр занимает `[S-112 .. S)`, поэтому его последние
16 байт приходятся ровно на эту область. Так и задумано: спилл должен писать
в кадр прерванной задачи, а не ниже него.

Первый вариант обработчика на шаге 1 клал кадр в 24 байта — то есть затирал
`[sp-12]` — и следующий вызов функции в прерванном коде падал двойным
исключением в одном прогоне из трёх. Выглядело это как случайность. Ещё раз
наступить на это в вытеснении было бы дороже всего.

#### Спилл окон из прерывания

Чтобы сбросить окна, нужны те же четыре шага, что в `basalt_task_switch`:
снять `EXCM`, поднять `INTLEVEL` до `XCHAL_EXCM_LEVEL`, сбросить окна, вернуть
`PS` и `EPC1`. Причины те же, и они в комментарии к `tasks.S`.

Из прерывания к ним добавляется одна тонкость: `PS` и `EPC1` прерывания надо
спрятать, пока идёт спилл, потому что обработчики переполнения окон пишут в
`EPC1` и меняют `PS`. Они уходят в `EXCSAVE_6` и `EXCSAVE_4`, а `EXCSAVE_5`
держит указатель кадра, пока `a1` переставлен на настоящий стек задачи.

#### Признак типа кадра

Планировщик хранит на задачу одно число — указатель стека на точке остановки.
А остановиться задача может двумя способами: сама (`basalt_task_switch`,
возврат через `retw`) или по тику (`rfi 3`). Восстанавливать их надо
по-разному, и различить их больше нечем. Поэтому в первом слове кадра лежит
тип: 0 у кооперативного, 1 у кадра тика. У кооперативного кадра в этом слове
и так 0 — там лежит адрес возврата, а ноль адресом быть не может.

#### Проверка на плате 08.11.2026

Задача шага — «ничего не сломалось», поэтому проверялось именно это:

#### Что осталось и какая ловушка ждёт

Смена задачи из тика: войти в чужой кадр через `rfi 3` и решить, когда это
делать.

Ловушка, которую придётся закрыть тогда же: во время стирания и записи flash
драйвер гасит кэш, а обработчик тика исполняется из IRAM. Пока обработчик был
чистым ассемблером, это было безразлично. Когда он начнёт звать C-функцию
выбора задачи — а та лежит во flash, — вызов при погашенном кэше уронит
систему ровно посреди записи файла. Значит, линию надо маскировать на время
операции: пара `hold`/`release` в драйвере flash и маска в `INTENABLE`.

### 08.11.2026. A6, шаг 5: тик учится переключать задачу — и упирается в окна

Запись о **неудаче**, и она важнее удачи: три раза казалось, что причина
найдена, и три раза плата это опровергла. Веха A6 остаётся открытой.

#### Что поставлено на место

Механика вытеснения собрана целиком:

- тик вызывает C-функцию выбора задачи на **своём** стеке в 2 КБ. Стек задачи
  для этого не годится: у неё 4 КБ, и обработчик, добавляющий к ним свои
  кадры, испортил бы память ровно там, где задача ближе всего к пределу;
- обмен идёт через память (`basalt_task_exchange[2]`), а не через регистры
  возврата. Вызов из прерывания через `callx4` корректен: `call4` сам копирует
  `a1` вызывающего в `a5` вызываемого, поэтому `mov a1, a3` перед `callx4`
  достаточно. Здесь тоже была гипотеза («C получает стек из `a5`, который мы
  не задали») — она проверена и отброшена;
- кадр уходящей задачи сохраняется **всегда**, даже когда решено не
  переключаться. Без этого получался порочный круг: задача становится
  вытесняемой только после того, как тик на неё переключился, а переключиться
  нельзя, пока она не вытесняема. Симптом ровно такой: тик идёт, итерации
  растут, «из них по тику 0»;
- возврат в задачу, остановленную тиком, через `rfi 3` работает — в том числе
  когда тик «вытесняет» задачу саму в себя;
- запись во flash больше не может съесть тик: драйвер держит линию в
  `INTENABLE` парой `basalt_int1_hold/release`;
- `top` показывает «из них по тику» отдельно от общего числа смен.

#### Три опыта, три опровержения

Сначала выяснилось главное: **`retw` из прерывания в чужой кадр не работает**.
Задача, сохранённая кооперативно, при возобновлении из тика роняет плату.

Первое объяснение: «`retw` крутит окно относительно текущей `WINDOWBASE`, а из
прерывания она чужая». Правка: сохранять `WINDOWBASE` на задачу и подставлять
в `PS.OWB` перед `rfi`. Паника та же — адреса сдвинулись на `0x10`, то есть
правка применилась и не помогла.

Второе объяснение: «дело в `WINDOWSTART` — маске живых окон». Правка:
восстанавливать маску из контекста задачи. Паника та же.

Третье: «маску надо не восстанавливать, а наоборот — оставить живым только
текущее окно», как `SET_STACK` в IDF (`WINDOWSTART = 1 << WINDOWBASE`). Паника
сместилась: вместо `WindowOverflow12` — выборка по мусорному адресу,
`EPC1 0x8200500b`.

**Что дали эти паники.** Адрес `DEPC 0x40375900` из первой — это ровно начало
вектора `WindowOverflow12`. То есть `retw` считал окно предка **живым** и брал
регистры из регистрового файла вместо кадра на стеке. А вывод из третьего
опыта закрывает вопрос: `WINDOWBASE` нельзя записать напрямую — его задаёт
только `rfi` (из `PS.OWB`) или `rotw`. Значит возврат в задачу обязан идти
через `rfi`, а `rfi` умеет возвращать только кадр тика.

Отсюда единственный путь: **один формат кадра на все случаи, включая `yield`**.

#### Цена временного ограничения — измерена

Пока кадры разные, в `basalt_task_preempt` стоит условие «не переключаться на
задачу с кооперативным кадром». Проверено прямым опытом: задача без `yield`
считала в цикле, и `top` показал «смен 1, из них по тику 0» — то есть она
отработала 20 млн итераций одна. Это и есть прямое доказательство, что обход
не решает веху, а только откладывает.

Первая версия опыта была опаснее: цикл без счётчика повесил плату намертво,
и оживить её удалось только кнопкой (G0 + RST). После этого проверка делалась
на ограниченном цикле, а после — убрана из кода совсем.

#### Что осталось

`basalt_task_switch` должен строить кадр тика вместо своего 48-байтного;
ветка `retw` в `basalt_task_resume` уходит; условие `ctx.preempt == 0`
снимается вместе с причиной.

#### Как проверить, что веха закрыта

```bash
~/.venvs/pio314/bin/pio run -e shell -t upload
# на устройстве:
top                          # «из них по тику» растёт, а не ноль
```

Признак успеха: на плате с задачей, не вызывающей `yield`, шелл продолжает
отвечать на `top`. Пока этого нет, вытеснения нет — какие бы числа ни
показывал счётчик смен.
